# Проверка на сервере: от чистой машины до зелёных тестов и живого прогона

Документ описывает ровно тот путь, который мы обсудили: проект едет на сервер,
там ставится PostgreSQL, прогоняются все автотесты, после чего выполняется
живой E2E-прогон в MAX по семи сценариям из §68 ТЗ.

Транспорт — **webhook** (у сервера есть публичный HTTPS-адрес, туннель не
нужен).

---

## 0. Что понадобится от вас

| Что | Где взять | Когда нужно |
|---|---|---|
| Сервер с публичным HTTPS-доменом | любой VPS, Ubuntu 22.04/24.04 | шаг 1 |
| `BOT_TOKEN` | `@MasterBot` в MAX → создать бота | шаг 4 |
| 4 тестовых чата | создать в MAX и добавить туда бота | шаг 6 |
| Ваш MAX user id | команда `/whoami` боту | шаг 6 |

Тестовые чаты (названия любые, важна только роль):

1. **Распределение** — сюда падают все новые обращения;
2. **Согласование** — сюда уходят подготовленные ответы;
3. **Профильный: Хозяйственные вопросы** (`FACILITY`);
4. **Профильный: IT** — второй нужен, чтобы проверить, что обращение не может
   уйти в две сферы и что кнопки чужого чата не срабатывают.

Плюс для сценария 7 нужен **второй аккаунт MAX** (коллега или второй телефон) —
без него нельзя доказать главное свойство системы: два человека получают каждый
свой ответ.

## 0.1. Обязательно: сертификаты MAX

`*.max.ru` подписан цепочкой **Russian Trusted Sub CA → Russian Trusted Root
CA** (Минцифры РФ). Этого корня нет в стандартном наборе CA, поэтому Node и
curl рвут соединение с `platform-api2.max.ru` с ошибкой
`fetch failed` / `curl exit=60`, хотя весь остальной интернет по HTTPS работает.

В проекте корень лежит в `deploy/russian-trusted-ca.pem` и подключается
**только к процессу бота** через `NODE_EXTRA_CA_CERTS` — в системное хранилище
он не ставится и на другие контейнеры не влияет. Это уже настроено в
`docker-compose.yml`, делать ничего не нужно.

Для инструментов, запускаемых на хосте (`npm run doctor`, скрипты webhook),
переменную надо выставить вручную:

```bash
export NODE_EXTRA_CA_CERTS=/opt/incident-bot/deploy/russian-trusted-ca.pem
```

Отпечатки для независимой сверки:

```
Root CA  D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31
Sub CA   BB:BD:E2:10:3E:79:0B:99:9E:C6:2B:D0:3C:F6:25:A5:A2:E7:C3:16:E1:0A:FE:6A:49:0E:ED:EA:D8:B3:FD:9B
```

Проверить, что корень действительно валидирует MAX:

```bash
echo | openssl s_client -connect platform-api2.max.ru:443 \
  -servername platform-api2.max.ru -CAfile deploy/russian-trusted-ca.pem 2>&1 \
  | grep 'Verify return code'      # ожидается: 0 (ok)
```

## 3. Автотесты (97 штук) — до всякого MAX

Этот шаг **не требует ни токена, ни чатов**. Он проверяет всю бизнес-логику,
включая то, что нельзя проверить руками: гонки, лимиты, транзакции.

### 3.1 Поднять PostgreSQL

```bash
docker compose up -d postgres
docker compose exec postgres psql -U incident -c 'CREATE DATABASE incident_test'
```

### 3.2 Прогнать всё

```bash
TEST_DATABASE_URL='postgresql://incident:incident@localhost:5432/incident_test?schema=public' npm test
```

Схема в тестовую базу накатывается сама (`prisma db push`).

**Ожидаемый результат: 97 passed, 0 skipped.** Если видите `26 skipped` —
переменная `TEST_DATABASE_URL` не подхватилась.

Что именно тут проверяется (это и есть §61 ТЗ):

| Набор | Проверяет |
|---|---|
| Регистрация | 150 и 151 символ, эмодзи как один символ, фото, видео, аудио, пустой текст, заблокированный пользователь |
| Дневной лимит | первое, второе, третье обращение; **6 параллельных запросов** дают ровно 2 обращения; лимит одного пользователя не влияет на другого; ошибка формата лимит не тратит |
| Распределение | обычное; **два диспетчера одновременно** — побеждает один, второй получает имя победителя; повторное нажатие; отклонение с причиной; нельзя отклонить уже распределённое |
| Ответы | версии 1→2→3, отказ для видео, **два одновременных ответа** дают одну запись |
| Согласование | approve, возврат, второй возврат, согласование после правок, **два одновременных approve** — одна доставка |
| SLA | дедлайн ровно `+72h`; правки **не** двигают дедлайн; предупреждения 24ч и 6ч ровно по одному разу; просрочка ставит `isOverdue`, но не ломает статус |
| Безопасность | заявитель не может нажать кнопку диспетчера; ответственный не может согласовать; действие из чужого чата отклоняется; webhook без секрета → 401, с неверным секретом → 401, повторная доставка → не обрабатывается второй раз |
| **Доставка** | два обращения от разных людей — каждый получает строго свой ответ |

Дополнительно:

```bash
npm run check   # typecheck + сборка + тесты одной командой
```

npx prisma generate

### 5.1. Юридические документы — включать только после проверки юристом

Пока в документах есть жёлтые поля и пометка «ПРОЕКТ», оставьте:

```env
LEGAL_CONSENT_REQUIRED=false
```

Перед боевым запуском заполните реквизиты, дату и контакт, получите одобрение
юриста, экспортируйте окончательные PDF и положите их в `legal/public` под
фиксированными именами:

```text
user-agreement.pdf
privacy-policy.pdf
personal-data-consent.pdf
```

Далее вычислите SHA-256 каждого файла, задайте публичный адрес каталога,
редакцию и три контрольные суммы в `.env`. Только после этого установите
`LEGAL_CONSENT_REQUIRED=true`. Команда `npm run doctor` скачает опубликованные
файлы и не даст считать проверку успешной, если хотя бы один файл недоступен
или отличается от указанной контрольной суммы.

Seed создаёт шесть сфер: `IT`, `FACILITY`, `SECURITY`, `HR`, `LEGAL`, `OTHER`.
Чаты у них пока не заданы — это нормально.

## 6. Узнать ID чатов и свой MAX ID

Запустите бота в фоне:

```bash
npm run build && npm start
```

Он предупредит, что `DISTRIBUTION_CHAT_ID` и `REVIEW_CHAT_ID` не заданы — так и
задумано.

Теперь:

1. **Добавьте бота во все 4 тестовых чата.** При добавлении он сам напишет в
   чат его ID. Запишите все четыре.
2. **Напишите боту `/whoami` в личку** — он ответит вашим MAX ID.
3. Остановите бота (`Ctrl+C`) и допишите `.env`:

```env
DISTRIBUTION_CHAT_ID=<id чата распределения>
REVIEW_CHAT_ID=<id чата согласования>

ADMINS=<ваш MAX ID>
DISPATCHERS=<ваш MAX ID>
APPROVERS=<ваш MAX ID>
RESPONDERS=<ваш MAX ID>
```

> В MVP это допустимо: ТЗ прямо разрешает, чтобы APPROVER и DISPATCHER были
> одними и теми же людьми. Для проверки разграничения прав на шаге 9.6 мы
> временно уберём часть ролей.

4. Запустите `npm run seed`: он создаст темы и зафиксированный каталог из 50
   ответственных групп. Проверить или изменить привязку можно командами:

```
/groups
/group_chat EA_TRANSPORT <id профильного чата>
```

## 9. Живой E2E-прогон: 7 сценариев из §68

Для каждого сценария указано, что делать и что должно произойти. Логи удобно
смотреть параллельно: `docker compose logs -f app` или `journalctl -fu <unit>`.

### 9.1 Сценарий 1 — базовый путь

1. Личка боту: `/start` → полноценное приветствие и меню из четырёх кнопок.
2. «📝 Создать обращение» → ввести тестовые ФИО и номер телефона.
3. В списке сфер выбрать **«Хозяйственные вопросы»**.
4. Выбрать территорию и, если бот предложит, населённый пункт.
5. Отправить: `Не работает освещение возле входа.` При желании приложить фото.

✅ Бот показывает итоговую карточку со всеми введёнными данными и кнопками
«Всё верно» / «Исправить». В рабочей БД и чате распределения обращения пока нет.

6. Нажать «Исправить», изменить одно поле и убедиться, что остальные поля
   сохранились. Затем нажать «Всё верно».

✅ Пользователь получает `✅ Обращение зарегистрировано` с номером
`INC-<дата>-0001`, датой и ссылкой на раздел «Мои обращения». Внутренний срок
ответа пользователю не показывается.
✅ В чате распределения — карточка `🆕 НОВОЕ ОБРАЩЕНИЕ` с номером, автором,
темой, территорией, текстом, сроком и тремя кнопками.

7. В чате распределения: «Распределить» → один из трёх разделов → профильная группа.

✅ Карточка распределения заменяется на `✅ ... распределено` с именем
диспетчера.
✅ В выбранном профильном чате — карточка `📥 НОВОЕ ОБРАЩЕНИЕ` с кнопками.

8. В профильном чате: «Взять в работу» → карточка обновляется, появляется
   `👤 В работе: <имя>`.
9. «Подготовить ответ» → бот просит текст. Отправить:
   `Освещение восстановлено. Выполнена замена светильника.`

✅ В чате согласования — `📝 ОТВЕТ НА СОГЛАСОВАНИЕ`, версия 1.

10. В чате согласования: «✅ Согласовать».

✅ **Именно исходный пользователь** получает `✅ Получен ответ по вашему
обращению` с его номером, его текстом обращения и ответом.
✅ В профильном чате — уведомление о согласовании.

### 9.2 Сценарий 2 — «Иное»

Повторить 9.1, но тему выбрать **«Иное»**, затем выбрать территорию.

✅ В карточке распределения `Сфера пользователя: Иное`.
✅ После выбора «Органы местного самоуправления» подходящая по территории
группа стоит первой с отметкой «рекомендуется».
✅ Рекомендация ничего не назначает автоматически: диспетчер может выбрать
любую группу, обращение уходит ровно в один чат.

### 9.3 Сценарий 3 — возврат на доработку

Перед ним отдельно проверьте региональный путь: распределите обращение в
«Калужская область», в профильном чате нажмите «Подготовить ответ» и отправьте
текст от пользователя с ролью `DISPATCHER`.

✅ Ответ сразу получает заявитель, в чат согласования карточка не приходит.
✅ Участник регионального чата без роли `DISPATCHER` или `ADMIN` ответить не
может.

Для остальных групп продолжайте обычный сценарий согласования ниже.

Довести обращение до чата согласования (шаги 1–7 из 9.1), затем:

1. «↩️ На доработку» → бот просит причину.
2. Отправить: `Необходимо уточнить срок устранения проблемы.`

✅ В профильном чате — `↩️ ОТВЕТ ВОЗВРАЩЁН НА ДОРАБОТКУ` с причиной, версией
ответа, первоначальным дедлайном и строкой `⚠️ Дедлайн НЕ изменён.`

3. «Исправить ответ» → отправить исправленный текст.

✅ В чате согласования новая карточка с **версией 2**.

4. «✅ Согласовать» → пользователь получает исправленный ответ.

**Ключевая проверка** — сверьте дедлайн:

```
/incident INC-<номер>
```

✅ Поле «Дедлайн» совпадает с тем, что было в самой первой карточке.
✅ «Правок: 1».

### 9.4 Сценарий 4 — дневной лимит

С одного аккаунта создать третье обращение за сутки.

✅ `Вы уже отправили 2 обращения сегодня.`
✅ Третьей карточки в чате распределения нет.

Отдельно проверьте, что ошибки формата лимит **не** тратят: отправьте текст
длиннее 150 символов и видео.

✅ `Сообщение слишком длинное…` и `Видео к обращениям прикреплять нельзя…`
✅ После этого обращение всё ещё можно создать.

### 9.5 Сценарий 5 — блокировка

1. В чате распределения на любой карточке: «Заблокировать автора» → указать
   причину.

✅ Подтверждение в чате.

2. С заблокированного аккаунта попробовать создать обращение.

✅ `Отправка обращений для вашей учётной записи временно недоступна.` — без
технических деталей.

3. Разблокировать: `/unban <MAX_USER_ID>` → обращения снова создаются.

### 9.6 Сценарий 6 — Excel и разграничение прав

В рабочем чате:

```
/report today
/report 7d
/report 2026-08-01 2026-08-31
```

✅ Приходит файл `incident-report-<период>.xlsx` с правильным именем.
✅ Одно обращение — одна строка; заполнены дата обращения, дата ответа, номер,
текст обращения, текст ответа, категории, статус, число доработок, дедлайн,
признак просрочки, автор.

Проверка прав:

- `/report` в **личке** → `Эта команда доступна только в рабочем чате.`
- Уберите свой ID из `DISPATCHERS` и `ADMINS`, перезапустите, попробуйте
  `/report` → `У вас нет прав для этого действия.`
- Уберите себя из `APPROVERS`, перезапустите, нажмите «✅ Согласовать» →
  отказ. Это и есть проверка «responder не может согласовать без права».
- Нажмите кнопку из карточки профильного чата `FACILITY`, находясь в чате `IT`
  → `Это действие доступно только в профильном чате этого обращения.`
- Верните роли обратно.

### 9.7 Сценарий 7 — два пользователя, два ответа (критический)

Здесь нужен второй аккаунт.

1. Аккаунт **A** создаёт обращение: `Не работает освещение возле входа.`
2. Аккаунт **B** создаёт обращение: `Не открывается дверь на складе.`
3. Оба распределить в `FACILITY`.
4. Подготовить **разные** ответы:
   - для A: `Освещение восстановлено. Выполнена замена светильника.`
   - для B: `Замок отремонтирован, доступ восстановлен.`
5. Согласовать оба.

✅ Аккаунт A получил ответ **только** про освещение и **только** со своим
номером.
✅ Аккаунт B получил ответ **только** про замок и **только** со своим номером.
✅ Ни один не получил чужой номер или чужой текст.

Усложнённый вариант: подготовьте оба ответа **одновременно** (два оператора в
профильном чате параллельно) и согласуйте их подряд без пауз. Результат должен
быть тем же.

### 9.8 Дополнительно: SLA и webhook

**SLA.** Дожидаться 72 часов не нужно — сдвиньте дедлайн в базе:

```bash
docker compose exec postgres psql -U incident -d incident \
  -c "UPDATE \"Incident\" SET \"deadlineAt\" = now() + interval '5 hours' WHERE \"publicCode\"='INC-...';"
```

Затем в рабочем чате: `/sla_check`.

✅ В профильном чате `⚠️ ... осталось менее 6 часов.`
✅ Повторный `/sla_check` — второго такого же сообщения нет.

Аналогично с `now() - interval '1 hour'`:

✅ `🚨 ПРОСРОЧЕНО`, у обращения `isOverdue = true`, но статус рабочий и работа
продолжается.

**Webhook.** Проверьте, что чужой запрос не проходит:

```bash
curl -i -X POST https://<домен>/webhook/max \
  -H 'content-type: application/json' \
  -d '{"update_type":"message_created","timestamp":1}'
```

✅ `401`. С правильным `X-Max-Bot-Api-Secret` тот же запрос даст `200`, а
повторная отправка — `{"ok":true,"duplicate":true}`.

## 10. Что смотреть в логах

Каждая строка бизнес-процесса содержит `incidentId`, `publicCode`, `maxUserId`,
`chatId`, `action`. Проследить обращение целиком:

```bash
docker compose logs app | grep INC-20260823-0001
```

Ожидаемая последовательность: `incident registered` → `distribution card
published` → `incident assigned to sector` → `sector card published` →
`incident taken in work` → `answer submitted for review` → `review card
published` → `answer approved and delivered` → `answer delivered to requester`.

Полная история любого обращения есть и в БД:

```sql
SELECT action, "fromStatus", "toStatus", "actorMaxUserId", "createdAt"
FROM "IncidentHistory" h
JOIN "Incident" i ON i.id = h."incidentId"
WHERE i."publicCode" = 'INC-20260823-0001'
ORDER BY h."createdAt";
```

`BOT_TOKEN` и `WEBHOOK_SECRET` в логах не появляются — Pino их вырезает.

## 11. Очистка тестовых данных

После прогона:

```bash
docker compose exec postgres psql -U incident -d incident -c '
TRUNCATE TABLE "IncidentHistory","AnswerAttachment","IncidentAnswer",
"IncidentAttachment","OperatorSession","Incident","Ban","ProcessedUpdate",
"IncidentCounter" RESTART IDENTITY CASCADE;'
```

Сферы, пользователи и роли при этом сохраняются. Вложения при
`MEDIA_STORAGE=local` лежат в `data/uploads` — каталог можно очистить отдельно.

# Параллельная обработка и фотографии MAX

Изменения согласованы владельцем: новые фотографии не хранить на сервере,
при недоступности запрашивать повторно; разные пользователи обслуживаются одновременно.

## Обработка событий

- `INBOX_CONCURRENCY=8` по умолчанию, диапазон 1–32. Это число обрабатываемых
  действий, а не лимит пользователей или обращений.
- Входящие события сохраняются в PostgreSQL до ответа HTTP 200. Один пользователь,
  включая его нажатия и сообщения из разных чатов, занимает одну последовательную
  очередь. Другие пользователи могут обрабатываться независимо.
- Поле `sequence` устраняет неопределённость при одинаковом времени поступления.
- При остановке новые события не запускаются, активные завершаются. Защита
  конкурентных изменений одного обращения остаётся в бизнес-транзакциях.
- Поддерживается один процесс приложения. Это изменение не разрешает запускать
  несколько реплик: startup-recovery и блокировки очередей рассчитаны на один процесс.
- Исходящие API-вызовы ограничены интервалом 45 мс; отправки в один адрес — 550 мс.
  Повторные сетевые попытки проходят те же ограничения. Рабочая очередь исходящих
  сообщений сохраняется; мгновенная доставка всех карточек не обещается.

## Фотографии

- Новый `storageKey` вида `max-photo:<encoded token>` — ссылка, не путь к файлу.
  Обычные пути старых вложений остаются читаемыми. Для ссылок `size=0` обозначает
  отсутствие сохранённых байтов в нашем файловом хранилище, а не размер фото в MAX.
- Все новые входящие фотографии требуют токен MAX. URL не используется как
  долговременная ссылка. Предпросмотр отправляет токен сразу и только после успешного
  ответа MAX переводит черновик к подтверждению. При отказе данные черновика сохраняются.
- Очередь доставки сохраняет токены; повтор после перезапуска не скачивает фото.
- Явный отказ MAX из-за недоступного изображения отделён от сетевых сбоев и ожидания
  обработки изображения. Временные ошибки повторяются обычным способом.
- При постоянном отказе карточка распределения/профильного чата публикуется с явным
  предупреждением без фото, с кнопками маршрутизации/уточнения. Неудавшийся оригинал
  остаётся в списке проблем доставки. Неполный ответ не отмечается доставленным,
  оценка под уведомлением об ошибке не предлагается.
- Для недоступного фото ответа профильный чат получает «Заменить недоступное фото».
  Только явное действие сотрудника возвращает последнюю недоставленную версию
  на доработку. Новый текст и фотографии проходят обычное согласование; прежний
  дедлайн сохраняется. Действие проверяет профильный чат, версию, статус доставки
  и фиксируется в истории. Отправка старой версии после возврата запрещается.
- Очистка через 90 дней удаляет ссылки из базы, не пытаясь удалить файлы в MAX.
  Старые локальные фото и файлы сотрудников по-прежнему удаляются по прежним правилам.
- Старые фотографии и резервные копии этой работой не удаляются. Режим хранения
  файлов сотрудников и Excel не меняется.

## Проверка и развёртывание

Миграция: `20260906180000_inbox_partitions`. Для существующих событий ключ пользователя
восстанавливается из сохранённого payload. Настройка числа обработчиков не обязательна:
значение по умолчанию — 8.

Резервная копия перед изменениями: `backups/daily-20260906-170530`.
Исходники: `backups/pre-parallel-max-photos-20260906/code.tar.gz`.
Сохранённый образ: `incident-bot-app:pre-parallel-max-photos-20260906`.

После приёма новых фотографий нельзя слепо откатываться на старый код: он не умеет
читать ссылки `max-photo:`. При откате требуется оставить совместимый обработчик
таких ссылок. Новые столбцы inbox сами по себе совместимы со старым кодом.

Проверки используют отдельную базу `incident_test` и подменённый транспорт MAX.
Они проверяют очередь и сценарии, но не измеряют полную пропускную способность
боевого MAX и не подтверждают бессрочную доступность токенов.

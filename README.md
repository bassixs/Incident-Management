# Incident Management Bot для мессенджера MAX

> **Развёрнут и работает.** Что где стоит, что проверено, какие грабли уже
> найдены и что осталось переключить перед боевым запуском —
> [RUNBOOK.md](RUNBOOK.md). Развёртывание с нуля — [DEPLOY.md](DEPLOY.md).

Бот сопровождает обращение по всему жизненному циклу:

```
Пользователь → бот → чат распределения → профильный чат → чат согласования → пользователь
```

Каждое обращение имеет неизменный внутренний `id` (UUID) и человекочитаемый
`publicCode` вида `INC-20260823-0001`. Вся связь «обращение → автор → сфера →
версия ответа → согласование → доставка» строится только по `Incident.id`,
поэтому ответ физически не может уйти не тому пользователю.

---

## 1. Требования

| Компонент | Версия |
|---|---|
| Node.js | 20+ (рекомендуется 22 LTS) |
| PostgreSQL | 14+ (проверено на 16) |
| Docker + Docker Compose | опционально, для локального запуска и продакшена |
| Бот в MAX | токен от `@MasterBot` |

Для продакшена дополнительно нужен HTTPS-домен для Webhook и, при
`MEDIA_STORAGE=s3`, S3-совместимое хранилище (AWS S3, MinIO, любое другое).

> **Сертификаты MAX.** `*.max.ru` подписан корнем Russian Trusted Root CA
> (Минцифры РФ), которого нет в стандартном наборе CA — без него любой вызов
> API падает с `fetch failed`. Корень лежит в `deploy/russian-trusted-ca.pem` и
> подключается только к процессу бота через `NODE_EXTRA_CA_CERTS`; в
> `docker-compose.yml` это уже настроено. Подробности — в
> [DEPLOY.md](DEPLOY.md), раздел 0.1.

## 3. Создание `.env`

```bash
cp .env.example .env
```

Минимально обязательные переменные:

| Переменная | Назначение |
|---|---|
| `BOT_TOKEN` | токен бота MAX (секрет, никогда не коммитить) |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `WEBHOOK_SECRET` | 5–256 символов; MAX присылает его в заголовке `X-Max-Bot-Api-Secret` |
| `WEBHOOK_URL` | публичный HTTPS-адрес, оканчивающийся на `WEBHOOK_PATH` |
| `DISTRIBUTION_CHAT_ID` | ID чата распределения |
| `REVIEW_CHAT_ID` | ID чата согласования |
| `DELIVERY_ALERT_CHAT_ID` | ID закрытого чата технических предупреждений |
| `ADMINS` | MAX ID первых администраторов через запятую |

Полный список с комментариями — в [.env.example](.env.example).

Секреты (`BOT_TOKEN`, `WEBHOOK_SECRET`, ключи S3) никогда не попадают в логи:
Pino настроен на их редактирование.

## 8. Регистрация Webhook

В продакшене используется только Webhook.

```env
NODE_ENV=production
BOT_MODE=webhook
WEBHOOK_URL=https://bot.example.com/webhook/max
WEBHOOK_PATH=/webhook/max
WEBHOOK_SECRET=<случайная строка 32+ символов>
```

При старте с `WEBHOOK_AUTO_REGISTER=true` (по умолчанию) бот сам создаёт
подписку. Вручную:

```bash
npm run webhook:register
```

Проверить текущие подписки:

```bash
npm run webhook:info
```

Удалить подписку (например, чтобы вернуться к Long Polling):

```bash
npm run webhook:delete
```

Endpoint принимает только запросы с корректным заголовком
`X-Max-Bot-Api-Secret`, отвечает `200 OK` немедленно и обрабатывает событие
асинхронно. Повторная доставка одного и того же Update распознаётся по
детерминированному ключу в таблице `ProcessedUpdate` и не выполняется дважды.

Служебные эндпоинты: `GET /health` (liveness), `GET /ready` (проверяет БД).

## 9. Настройка chat ID

1. Добавьте бота в чат распределения, чат согласования и в каждый профильный
   чат.
2. При добавлении бот сам напишет ID чата. Его же можно получить командой
   `/chatid` (доступна сотрудникам).
3. Пропишите `DISTRIBUTION_CHAT_ID` и `REVIEW_CHAT_ID` в `.env` и перезапустите
   бота.
4. Профильные чаты задаются в БД, без перезапуска:

```
/category_chat IT -1001234567890
/category_chat FACILITY -1000987654321
/categories
```

Сферы полностью управляются данными — добавить, переименовать, скрыть или
перепривязать чат можно в любой момент, без перезапуска и без правок кода:

```
/categories                          список, сгруппированный по готовности
/category_add TRANSPORT Транспорт
/category_chat TRANSPORT <CHAT_ID>
/category_name TRANSPORT Общественный транспорт
/category_authority TRANSPORT Министерство транспорта Калужской области
/category_template TRANSPORT Здравствуйте.\n\nОбращение № {{incidentCode}} рассмотрено.\n{{result}}
/category_off TRANSPORT
```

Под ответом житель видит, какое ведомство его подготовило. Подпись
подставляется автоматически по сфере обращения — сотрудник её не пишет и не
может забыть. Ведомство задаётся отдельным полем, а не названием сферы: сфера
«Дороги» нужна для маршрутизации, а в подписи должно стоять «Министерство
транспорта Калужской области». Если ведомство не задано, блок подписи просто
не выводится.

Сфера **без рабочего чата диспетчеру не показывается**: кнопки, которая упадёт
после нажатия, быть не должно. Она появится в списке сама, как только чат будет
задан.

Заявителю сферы показываются страницами по шесть, со стрелками «⬅️ Назад» и
«Вперёд ➡️»; «Не знаю» закреплено сверху на каждой странице. Выбор заявителя —
только предположение (§8): маршрут определяет диспетчер.

## 10. Настройка ролей

Роли резолвятся как «роли из БД ∪ роли из `.env`». Переменные окружения нужны
только чтобы у первой установки сразу были администраторы:

```env
ADMINS=1234567
DISPATCHERS=1234567,7654321
APPROVERS=1234567
RESPONDERS=
```

Дальше роли выдаются командой (только ADMIN):

```
/role 7654321 DISPATCHER,APPROVER
/role 7654321 -          # сбросить роли
```

После записи хотя бы одного `ADMIN` в БД проверьте результат через
`npm run doctor`, очистите стартовые списки ролей в `.env` и пересоздайте
контейнер приложения. Роли из `.env` складываются с ролями из БД, поэтому
оставленный там ID продолжит получать права даже после команды их сброса.

| Роль | Что может |
|---|---|
| `REQUESTER` | создать обращение, посмотреть свои обращения (есть у всех) |
| `DISPATCHER` | распределить, отклонить, заблокировать автора, отчёты |
| `RESPONDER` | взять в работу, подготовить ответ |
| `APPROVER` | согласовать, вернуть на доработку |
| `ADMIN` | всё перечисленное + управление категориями, ролями, банами |

Действия дополнительно ограничены чатом: кнопки диспетчера работают только в
чате распределения, кнопки согласования — только в чате согласования, а
действия ответственного — только в профильном чате именно этого обращения.

### Надёжная доставка и повторные нажатия

Каждый принятый webhook сначала сохраняется в `InboundUpdate`, и только затем
сервер отвечает MAX `200 OK`. Каждое обычное исходящее сообщение сначала
попадает в `OutboundMessage`; при временной ошибке MAX фоновый worker повторяет
отправку с увеличивающейся паузой. Состояние очередей доступно администратору:

```
/delivery_status
/delivery_errors             # показать последние проблемы и их короткие коды
/delivery_retry a1b2c3d4     # повторить только выбранную исходящую доставку
/delivery_retry              # повторить сразу все исходящие со статусом FAILED
```

Успешные записи очередей хранятся 30 дней. Неудачная исходящая доставка после
12 попыток остаётся в `FAILED` до ручного повтора. Прерванное входящее
бизнес-действие автоматически второй раз не запускается: оно остаётся в
`FAILED` для безопасной проверки, чтобы не создать обращение повторно.

Если задан `DELIVERY_ALERT_CHAT_ID`, бот раз в минуту проверяет новые записи
`FAILED` и группирует их в одно предупреждение в закрытом техническом чате.
В сообщении есть только тип проблемы и номер обращения — без текста обращений,
пользовательских данных и секретов. Одна проблема сообщается один раз. Если
MAX временно недоступен, отметка остаётся в БД и предупреждение уйдёт после
восстановления связи. Технические предупреждения не используют обычную
исходящую очередь, поэтому ошибка такого предупреждения не создаёт бесконечный
цикл новых предупреждений.

`/delivery_errors` показывает администратору время, обращение, получателя,
краткий контекст сообщения и причину сбоя. Персональные данные при наличии в
рабочем сообщении не вырезаются, так как они нужны для разбора обращения;
пароли, токены и ключи всегда скрываются. Входящие события нельзя повторять
автоматически: команда прямо помечает их как требующие ручной проверки.

Повторные нажатия кнопок блокирует короткая lease-запись `ActionLock`. Если
обработка занимает больше 600 мс, пользователь сразу получает уведомление
«Принято, обрабатываю…»; следующий клик не запускает вторую операцию. После
ошибки lease снимается, после аварии истекает автоматически.

MAX [`POST /messages`](https://dev.max.ru/docs-api/methods/POST/messages) не
предоставляет ключ идемпотентности. Поэтому при аварии
после фактической отправки, но до отметки `SENT` в БД, очередь выбирает более
безопасный вариант «доставить как минимум один раз»: возможен редкий дубль,
зато важный ответ не теряется.

## 12. Excel-отчёт

Доступно ADMIN и DISPATCHER, только в рабочем чате (не в личном диалоге).

Проще всего отправить `/report` без аргументов — бот покажет кнопки периода:
«Сегодня», «Неделя», «30 дней», «Этот месяц», «Всё время» и «📅 Указать
период». Последняя просит прислать даты одним сообщением:

```
01.08.2026 - 10.08.2026
```

Одна дата означает отчёт за этот день. Разделитель не важен: `-`, `—` или
пробел. Права проверяются повторно при нажатии кнопки — карточка остаётся в
истории чата, и нажать её может кто угодно.

Тем, кому удобнее печатать, прежний синтаксис работает без изменений:

```
/report today
/report 7d
/report 30d
/report month
/report all
/report 01.08.2026 - 10.08.2026
/report 2026-08-01 2026-08-31
```

Бот присылает файл `incident-report-<период>.xlsx`. Одно обращение — одна
строка. Колонки: дата обращения, дата ответа, уникальный номер, обращение,
ответ, категория пользователя, итоговая категория, статус, количество
доработок, дедлайн, признак просрочки, пользователь, MAX ID, ответственный,
распределил, согласовал, причина отклонения.

Другие команды сотрудников:

```
/incident INC-20260823-0001   — карточка обращения
/resend INC-20260823-0001     — повторить доставку согласованного ответа
/sla_check                    — принудительная проверка сроков (ADMIN)
/ban <MAX_USER_ID> <причина>  — блокировка (ADMIN)
/unban <MAX_USER_ID>          — снятие блокировки (ADMIN)
```

## 13. Персональные данные и внешние сервисы

В проекте **нет ИИ и нет ни одной передачи текста обращения во внешний сервис.**
Классификация, AI-черновик и AI-модерация удалены целиком: обращение жителя —
это персональные данные (имя, контакт, часто адрес и сведения о здоровье или
имуществе), а передача таких данных стороннему обработчику требует отдельного
правового основания.

Что это значит на практике:

* единственный внешний адресат, куда уходит текст обращения, — сам мессенджер MAX;
* всё остальное живёт в PostgreSQL и в хранилище вложений на вашем сервере;
* в зависимостях нет ни одного SDK моделей, а в `.env` нет ключей к ним;
* маршрутизацию по сферам делает только диспетчер, текст ответа пишет только
  сотрудник — вручную или по шаблону сферы (`/category_template`).

Если ИИ когда-нибудь понадобится, возвращать его нужно не раньше, чем будет
решён вопрос с персональными данными: либо модель в контуре заказчика, либо
согласие заявителя и договор с обработчиком. Историю удалённого кода можно
поднять из git — коммит до удаления содержит каталог `src/ai/` целиком.

## 14. Резервное копирование БД

Регулярный дамп (данные обращений, история и роли живут только в PostgreSQL):

```bash
docker compose exec -T postgres pg_dump -U incident -d incident -Fc > backup-$(date +%F).dump
```

Восстановление:

```bash
docker compose exec -T postgres pg_restore -U incident -d incident --clean --if-exists < backup-2026-08-23.dump
```

Без Docker:

```bash
pg_dump "$DATABASE_URL" -Fc > backup-$(date +%F).dump
pg_restore -d "$DATABASE_URL" --clean --if-exists backup-2026-08-23.dump
```

Отдельно копируйте вложения:

* `MEDIA_STORAGE=local` — каталог `MEDIA_LOCAL_PATH` (по умолчанию
  `./data/uploads`, в Docker — том `uploads`);
* `MEDIA_STORAGE=s3` — средствами объектного хранилища (версионирование
  бакета, репликация).

Таблицу `ProcessedUpdate` можно чистить от старых записей — она нужна только
для защиты от повторной доставки Webhook.

## 15. Тесты

```bash
npm test           # unit-тесты
npm run typecheck  # строгая проверка типов
```

Юнит-тесты не требуют инфраструктуры. Интеграционные тесты проверяют то, что
принципиально нельзя подделать (advisory-локи, условные UPDATE, уникальные
индексы) и требуют реального PostgreSQL:

```bash
docker compose up -d postgres
createdb incident_test        # или psql -c 'CREATE DATABASE incident_test'
TEST_DATABASE_URL=postgresql://incident:incident@localhost:5432/incident_test npm test
```

Без `TEST_DATABASE_URL` интеграционные наборы помечаются `skipped`, а не
проходят молча. Схема в тестовую БД накатывается автоматически
(`prisma db push`).

Пошаговый прогон на сервере — от чистой машины до живого E2E по семи сценариям
ТЗ — описан в [DEPLOY.md](DEPLOY.md). Перед живым запуском полезно выполнить
`npm run doctor`: он проверит токен, членство бота в каждом настроенном чате,
состояние webhook-подписки, миграции и хранилище вложений.

Покрыто, в частности:

* регистрация: 150 символов, 151 символ, эмодзи, фото, видео, аудио, пустой
  текст, заблокированный пользователь;
* дневной лимит: первое, второе, третье обращение и шесть параллельных попыток;
* распределение: обычное, два диспетчера одновременно, повторное нажатие;
* ответы: версии, отказ для видео, два одновременных ответа;
* согласование: approve, возврат, второй возврат, согласование после правок;
* SLA: дедлайн `+72h`, неизменность дедлайна после возврата, предупреждения
  24ч/6ч ровно по одному разу, статус `isOverdue` без потери workflow-статуса;
* безопасность: заявитель не может нажать кнопку диспетчера, ответственный не
  может согласовать, действие из чужого чата отклоняется, повторный webhook не
  выполняется дважды;
* **доставка**: два обращения от разных людей — каждый получает строго свой
  ответ (acceptance-тест, есть и в unit-, и в интеграционном виде).

## 16. Архитектура

```
src/
  app/container.ts        композиционный корень (вся сборка зависимостей)
  bot/
    bot.ts                регистрация обработчиков
    handlers/             маршрутизация сообщений, диалог заявителя, сессии операторов
    callbacks/            обработка кнопок
    commands/             слэш-команды
    keyboards/            inline-клавиатуры
    middleware/           авторизация (роль + чат)
    views/                тексты карточек
  incidents/              incident.service, repository, state machine, история
  distribution/           чат распределения
  sector/                 профильные чаты
  review/                 чат согласования
  answers/                версии ответов
  delivery/               единственная точка отправки заявителю
  categories/ users/ bans/ sessions/
  media/                  MediaStorage: local / S3
  reports/                XLSX
  sla/                    контроль сроков
  max/                    клиент MAX, разбиение сообщений, callback payload, idempotency key
  server/                 webhook, long polling, диспетчер апдейтов
  database/ config/ utils/
```

Обработчики только валидируют вход, вызывают сервис и рендерят ответ —
бизнес-логики в них нет.

### Ключевые инварианты

| Инвариант | Как обеспечен |
|---|---|
| Номер уникален и не меняется | `INSERT … ON CONFLICT DO UPDATE … RETURNING` по таблице `IncidentCounter`, уникальный индекс на `publicCode` |
| Не более 2 обращений в сутки | транзакция + `pg_advisory_xact_lock` по автору; календарные сутки считаются в `APP_TIMEZONE` |
| Обращение не уходит в две сферы | `UPDATE … WHERE id = ? AND status = 'DISTRIBUTION'`; проигравший получает имя победителя |
| Двойное согласование невозможно | тот же приём на `WAITING_REVIEW`, плюс `IncidentAnswer.deliveredAt` как защита от повторной отправки |
| Дедлайн не продлевается | `deadlineAt` вычисляется один раз при создании и не входит ни в один последующий `UPDATE` |
| Ответ уходит своему автору | `RequesterDeliveryService` — единственный, кто пишет заявителю, и получателя он берёт только как `incident → requester → maxUserId` |
| Состояние переживает рестарт | сессии операторов, маркеры SLA, маркер long polling и дедуп Webhook лежат в PostgreSQL |
| Повторный Webhook безвреден | детерминированный ключ + уникальный индекс `ProcessedUpdate.externalUpdateKey` |
| История не теряется | `IncidentHistory` только пополняется; старые версии ответов не удаляются |

## 17. Пользовательский сценарий

1. `/start` → приветствие и меню: «📝 Создать обращение», «🔎 Мои обращения»,
   «ℹ️ Правила».
2. «Создать обращение» → выбор сферы или «Не знаю». Выбор пользователя — только
   предположение: обращение в любом случае идёт в чат распределения.
3. Одно сообщение до 150 символов, при желании с фотографией. Видео и аудио не
   принимаются, и такие попытки не расходуют дневной лимит.
4. Пользователь получает номер и дату. Срок ответа — 72 часа.
5. Диспетчер в чате распределения видит карточку и выбирает сферу, отклоняет
   обращение с причиной или блокирует автора.
6. В профильном чате сотрудник берёт обращение в работу и готовит ответ —
   вручную или по шаблону сферы.
7. Ответ уходит в чат согласования. Согласующий либо отправляет его
   пользователю, либо возвращает на доработку с причиной — дедлайн при этом не
   меняется.
8. После согласования ответ и вложения получает именно автор обращения.

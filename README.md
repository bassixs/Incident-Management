# Incident Management Bot для мессенджера MAX

> **Развёрнут и работает.** Что где стоит, что проверено, какие грабли уже
> найдены и что осталось переключить перед боевым запуском —
> [RUNBOOK.md](RUNBOOK.md). Развёртывание с нуля — [DEPLOY.md](DEPLOY.md).

Бот сопровождает обращение по всему жизненному циклу:

```
Пользователь → тема и территория → чат распределения → ответственная группа → согласование → пользователь
```

Для группы «Калужская область» согласование пропускается: распределитель
готовит ответ в её профильном чате, и бот отправляет его пользователю сразу.

Каждое обращение имеет неизменный внутренний `id` (UUID) и человекочитаемый
`publicCode` вида `INC-20260823-0001`. Вся связь «обращение → автор → тема → территория → ответственная группа →
версия ответа → согласование → доставка» строится только по `Incident.id`,
поэтому ответ физически не может уйти не тому пользователю.

---

## 1. Требования

| Компонент | Версия |
|---|---|
| Node.js | 20+ (рекомендуется 22 LTS) |
| PostgreSQL | 14+ (проверено на 16) |
| Docker + Docker Compose | опционально, для локального запуска и продакшена |
| Бот в MAX | токен от `@MasterBot` |

Для продакшена дополнительно нужен HTTPS-домен для Webhook и, при
`MEDIA_STORAGE=s3`, S3-совместимое хранилище (AWS S3, MinIO, любое другое).

> **Сертификаты MAX.** `*.max.ru` подписан корнем Russian Trusted Root CA
> (Минцифры РФ), которого нет в стандартном наборе CA — без него любой вызов
> API падает с `fetch failed`. Корень лежит в `deploy/russian-trusted-ca.pem` и
> подключается только к процессу бота через `NODE_EXTRA_CA_CERTS`; в
> `docker-compose.yml` это уже настроено. Подробности — в
> [DEPLOY.md](DEPLOY.md), раздел 0.1.

## 3. Создание `.env`

```bash
cp .env.example .env
```

Минимально обязательные переменные:

| Переменная | Назначение |
|---|---|
| `BOT_TOKEN` | токен бота MAX (секрет, никогда не коммитить) |
| `DATABASE_URL` | строка подключения к PostgreSQL |
| `WEBHOOK_SECRET` | 5–256 символов; MAX присылает его в заголовке `X-Max-Bot-Api-Secret` |
| `WEBHOOK_URL` | публичный HTTPS-адрес, оканчивающийся на `WEBHOOK_PATH` |
| `DISTRIBUTION_CHAT_ID` | ID чата распределения |
| `REVIEW_CHAT_ID` | ID чата согласования |
| `DELIVERY_ALERT_CHAT_ID` | ID закрытого чата технических предупреждений |
| `ADMINS` | MAX ID первых администраторов через запятую |
| `LEGAL_CONSENT_REQUIRED` | включает обязательное раздельное подтверждение документов; до юридической готовности должно быть `false` |
| `LEGAL_DOCUMENTS_BASE_URL` | публичный адрес каталога PDF, например `https://bot.example.ru/documents` |
| `LEGAL_USER_AGREEMENT_VERSION` | отдельная редакция соглашения; если не задана, используется `LEGAL_DOCUMENT_VERSION`. Позволяет обновить соглашение без повторного согласия на ПДн |

Полный список с комментариями — в [.env.example](.env.example).

Секреты (`BOT_TOKEN`, `WEBHOOK_SECRET`, ключи S3) никогда не попадают в логи:
Pino настроен на их редактирование.

## 8. Регистрация Webhook

В продакшене используется только Webhook.

```env
NODE_ENV=production
BOT_MODE=webhook
WEBHOOK_URL=https://bot.example.com/webhook/max
WEBHOOK_PATH=/webhook/max
WEBHOOK_SECRET=<случайная строка 32+ символов>
```

При старте с `WEBHOOK_AUTO_REGISTER=true` (по умолчанию) бот сам создаёт
подписку. Вручную:

```bash
npm run webhook:register
```

Проверить текущие подписки:

```bash
npm run webhook:info
```

Удалить подписку (например, чтобы вернуться к Long Polling):

```bash
npm run webhook:delete
```

Endpoint принимает только запросы с корректным заголовком
`X-Max-Bot-Api-Secret`, отвечает `200 OK` немедленно и обрабатывает событие
асинхронно. Повторная доставка одного и того же Update распознаётся по
детерминированному ключу в таблице `ProcessedUpdate` и не выполняется дважды.

Служебные эндпоинты: `GET /health` (liveness), `GET /ready` (проверяет БД).

## 9. Настройка chat ID

1. Добавьте бота в чат распределения, чат согласования и в каждый профильный
   чат.
2. При добавлении бот сам напишет ID чата. Его же можно получить командой
   `/chatid` (доступна сотрудникам).
3. Пропишите `DISTRIBUTION_CHAT_ID` и `REVIEW_CHAT_ID` в `.env` и перезапустите
   бота.
4. Профильные чаты ответственных групп задаются в БД, без перезапуска:

```
/group_chat EA_TRANSPORT -1001234567890
/groups
```

Темы обращения и ответственные группы — разные справочники. Тема описывает,
о чём пишет пользователь, но ничего не маршрутизирует:

```
/categories                          список тем
/category_add TRANSPORT Транспорт
/category_name TRANSPORT Общественный транспорт
/category_off TRANSPORT
```

Получатель, его чат, подпись и шаблон настраиваются отдельно:

```
/groups
/group_chat EA_TRANSPORT <CHAT_ID>
/group_name EA_TRANSPORT Министерство транспорта
/group_authority EA_TRANSPORT Министерство транспорта Калужской области
/group_template EA_TRANSPORT Здравствуйте.\n\nОбращение № {{incidentCode}} рассмотрено.\n{{result}}
/group_off EA_TRANSPORT
```

Группа без рабочего чата диспетчеру не показывается. Подпись ответа
подставляется из ответственной группы автоматически.

Заявителю сферы показываются страницами по шесть, со стрелками «⬅️ Назад» и
«Вперёд ➡️»; «Иное» закреплено сверху на каждой странице. Выбор заявителя —
только предположение (§8): маршрут определяет диспетчер.

## 10. Настройка ролей

Участники настроенных рабочих чатов получают права автоматически:

- распределение — `DISPATCHER`;
- согласование — `APPROVER`;
- активный профильный чат — `RESPONDER`;
- группа с прямым ответом (например, «Калужская область») — дополнительно
  `DISPATCHER` в этом чате для существующего сценария без согласования;
- системный чат аналитики и проблем (`DELIVERY_ALERT_CHAT_ID`) — отчёты по всем
  обращениям, просмотр обращений, состояния и ошибок очередей, повтор исходящей
  доставки; без доступа к административным настройкам. `/report`, кнопки периода
  и ввод своих дат отправляют Excel в этот же системный чат.

Права действуют в текущем рабочем чате и вычисляются по его актуальной настройке
на каждом сообщении/нажатии. Они не записываются в глобальные `User.roles` и не
переносятся в личный диалог или посторонние группы. Уже состоящие в чатах сотрудники
могут работать сразу, без повторного вступления. При отключении/перепривязке группы
старый чат перестаёт давать права. `/role ... -` снимает ручные роли, но не доступ
участника рабочего чата: для его отзыва удалите человека из чата.

`/info` и `/help` показывают назначение текущего чата, порядок работы и доступные
команды. Новичок получает короткое приветствие с подсказкой `/info`. События
`user_added`/`user_removed` включены в подписку; для их получения бот должен быть
администратором чата. При выходе удаляется незавершённый ввод сотрудника только
в этом чате. Даже если событие вступления пропущено, права доступны при первом
действии в рабочем чате. Права администратора бота автоматически не выдаются.

Ручные роли сохраняются как «роли из БД ∪ роли из `.env`». Переменные окружения
нужны для первоначального назначения администратора:

```env
ADMINS=1234567
DISPATCHERS=1234567,7654321
APPROVERS=1234567
RESPONDERS=
```

Дополнительные ручные роли выдаются командой (только ADMIN):

```
/role 7654321 DISPATCHER,APPROVER
/role 7654321 -          # сбросить роли
```

После записи хотя бы одного `ADMIN` в БД проверьте результат через
`npm run doctor`, очистите стартовые списки ролей в `.env` и пересоздайте
контейнер приложения. Роли из `.env` складываются с ролями из БД, поэтому
оставленный там ID продолжит получать права даже после команды их сброса.

| Роль | Что может |
|---|---|
| `REQUESTER` | создать обращение, посмотреть свои обращения (есть у всех) |
| `DISPATCHER` | распределить, отклонить, заблокировать автора, отчёты |
| `RESPONDER` | взять в работу, подготовить ответ |
| `APPROVER` | согласовать, вернуть на доработку |
| `ADMIN` | всё перечисленное + управление темами, группами, ролями, банами |

Действия дополнительно ограничены чатом: кнопки диспетчера работают только в
чате распределения, кнопки согласования — только в чате согласования, а
действия ответственного — только в профильном чате именно этого обращения.
Участники группы «Калужская область» автоматически получают необходимые права
для прямого ответа. Просмотр, история и повтор ответа в профильном чате ограничены
обращениями, назначенными этому чату (кроме ручного ADMIN).

### Надёжная доставка и повторные нажатия

Регистрация, распределение, отклонение, подготовка и согласование ответа,
возврат на доработку и предупреждения SLA сохраняют изменение состояния,
историю и задание на отправку одной транзакцией PostgreSQL. Если записать
задание не удалось, изменение откатывается; если процесс остановился после
успешного сохранения, исходящая очередь продолжает отправку после запуска.
Подтверждение черновика закрывается в той же транзакции, чтобы повторное
нажатие не создало второе обращение. Вложения подготавливаются до транзакции;
очередь использует ссылки на сохранённые оригиналы и не удаляет их после отправки.

Согласование ответа и его доставка — разные события. При недоступности MAX
сотрудники видят «ожидает доставки»; это же правило действует для прямого
ответа «Калужской области» и команды `/resend`. Зелёное «ОТРАБОТАНО» появляется
только после фактической доставки. При успешном автоматическом повторе очередь
сама обновляет рабочие карточки и отправляет одно уведомление профильной группе.

Каждый принятый webhook сначала сохраняется в `InboundUpdate`, и только затем
сервер отвечает MAX `200 OK`. Каждое обычное исходящее сообщение сначала
попадает в `OutboundMessage`; при временной ошибке MAX фоновый worker повторяет
отправку с увеличивающейся паузой.

`OUTBOX_CONCURRENCY=8` задаёт число параллельных фоновых отправок разным
получателям (допустимо 1–32). В одном чате сообщения идут по сохранённому
порядковому номеру `sequence`, включая все части длинного сообщения. Прямые
отправки используют ту же блокировку получателя. Повтор после временной ошибки
задерживает только этот чат; после окончательного `FAILED` следующие задания
могут идти дальше. Отложенные до оценки приглашения и приостановленные
напоминания не блокируют обычные сообщения. Ограничения частоты запросов к MAX
сохраняются. Очередь рассчитана на один процесс приложения; несколько реплик
без отдельной координации запускать нельзя.

Состояние очередей доступно администратору:

```
/delivery_status
/delivery_errors             # показать последние проблемы и их короткие коды
/delivery_retry a1b2c3d4     # повторить только выбранную исходящую доставку
/delivery_retry              # повторить сразу все исходящие со статусом FAILED
```

Успешные записи очередей хранятся 30 дней. Неудачная исходящая доставка после
12 попыток остаётся в `FAILED` до ручного повтора. Прерванное входящее
бизнес-действие автоматически второй раз не запускается: оно остаётся в
`FAILED` для безопасной проверки, чтобы не создать обращение повторно.

Если задан `DELIVERY_ALERT_CHAT_ID`, бот раз в минуту проверяет новые записи
`FAILED` и группирует их в одно предупреждение в закрытом техническом чате.
В сообщении есть только тип проблемы и номер обращения — без текста обращений,
пользовательских данных и секретов. Одна проблема сообщается один раз. Если
MAX временно недоступен, отметка остаётся в БД и предупреждение уйдёт после
восстановления связи. Технические предупреждения не используют обычную
исходящую очередь, поэтому ошибка такого предупреждения не создаёт бесконечный
цикл новых предупреждений.

`/delivery_errors` показывает администратору время, обращение, получателя,
краткий контекст сообщения и причину сбоя. Персональные данные при наличии в
рабочем сообщении не вырезаются, так как они нужны для разбора обращения;
пароли, токены и ключи всегда скрываются. Входящие события нельзя повторять
автоматически: команда прямо помечает их как требующие ручной проверки.

Повторные нажатия кнопок блокирует короткая lease-запись `ActionLock`. Если
обработка занимает больше 600 мс, пользователь сразу получает уведомление
«Принято, обрабатываю…»; следующий клик не запускает вторую операцию. После
ошибки lease снимается, после аварии истекает автоматически.

MAX [`POST /messages`](https://dev.max.ru/docs-api/methods/POST/messages) не
предоставляет ключ идемпотентности. Поэтому при аварии
после фактической отправки, но до отметки `SENT` в БД, очередь выбирает более
безопасный вариант «доставить как минимум один раз»: возможен редкий дубль,
зато важный ответ не теряется.

npm ci

## 12. Excel-отчёт

Доступно ADMIN и DISPATCHER, только в рабочем чате (не в личном диалоге).

Проще всего отправить `/report` без аргументов — бот покажет кнопки периода:
«Сегодня», «Неделя», «30 дней», «Этот месяц», «Всё время» и «📅 Указать
период». Последняя просит прислать даты одним сообщением:

```
01.08.2026 - 10.08.2026
```

Одна дата означает отчёт за этот день. Разделитель не важен: `-`, `—` или
пробел. Права проверяются повторно при нажатии кнопки — карточка остаётся в
истории чата, и нажать её может кто угодно.

Тем, кому удобнее печатать, прежний синтаксис работает без изменений:

```
/report today
/report 7d
/report 30d
/report month
/report all
/report 01.08.2026 - 10.08.2026
/report 2026-08-01 2026-08-31
```

Бот присылает файл `incident-report-<период>.xlsx`. Одно обращение — одна
строка. Колонки: дата обращения, дата ответа, уникальный номер, обращение,
ответ, оценка ответа от 1 до 5, тема пользователя, округ или город, населённый
пункт, ответственная группа, статус, количество доработок, срок ответа, признак
просрочки, пользователь, телефон, MAX ID, ответственный, распределил,
согласовал, причина отклонения. Если пользователь ещё не поставил оценку,
соответствующая ячейка остаётся пустой.

Второй лист «Просроченные» содержит все текущие нерешённые обращения, у которых
на момент формирования истёк срок ответа (17:00 третьего рабочего дня), независимо
от выбранного периода первого листа. Решённые и отклонённые исключаются;
обращения на согласовании и доработке включаются. Отбор идёт по сроку ответа,
поэтому не зависит от времени последней проверки SLA. Сначала показаны самые
давние просрочки. На листе указаны дата формирования, номер обращения, дата
регистрации, срок ответа, просрочка в часах, статус, группа и ответственный,
описание, тема, территория и контакты заявителя. Если просроченных нет,
на втором листе будет соответствующая отметка. При пустом первом листе и
наличии просроченных бот всё равно отправляет файл.

Завершённые обращения доступны для отчётов 90 календарных дней после ответа
или отклонения. Затем исходные записи удаляются, поэтому месячный отчёт нужно
формировать в начале следующего месяца. `/report all` показывает только ещё
не удалённые обращения.

Другие команды сотрудников:

```
/incident INC-20260823-0001   — карточка обращения
/history INC-20260823-0001    — полная хронология обращения
/resend INC-20260823-0001     — повторить доставку согласованного ответа
/sla_check                    — принудительная проверка сроков (ADMIN)
/retention_preview            — показать, что удалится по правилу 90 дней (ADMIN)
/retention_run УДАЛИТЬ        — вручную запустить подтверждённую очистку (ADMIN)
/clear_data                   — выбор периода удаления обращений (ADMIN, чат аналитики)
/clear_users                  — отдельный сброс сохранённых жителей (ADMIN, чат аналитики)
/audit                        — последние административные изменения (ADMIN)
/ban <MAX_USER_ID> <причина>  — блокировка (ADMIN)
/unban <MAX_USER_ID>          — снятие блокировки (ADMIN)
```

Ручная очистка доступна только администраторам бота в `DELIVERY_ALERT_CHAT_ID`.
`/clear_data` предлагает сегодня, 7/30/90 дней, всё время или свои даты:
`/clear_data 01.09.2026 - 07.09.2026`. Выбор идёт по дате создания обращения
в часовом поясе приложения, включая незавершённые обращения. Удаляются
обращения и связанные ответы, уточнения, история, вложения и задания доставки;
профили жителей не сбрасываются.

`/clear_users` отдельно сбрасывает сохранённые ФИО, телефон и согласия всех
пользователей, включая сотрудников и администраторов, независимо от периода
обращений. Для прохождения сценария заново после сброса отправьте `/start`
в личном чате с ботом. Полностью удаляются только профили жителей без обращений;
учётные записи сотрудников, их MAX-профиль, рабочие права и рабочие сессии
сохраняются. Сохраняются также данные внутри существующих обращений. Черновики новых обращений сбрасываются у всех.

Обе команды сначала показывают подсчёт. Подтверждение — та же команда со
словом `confirm` и выданным кодом; код привязан к автору, чату и виду очистки,
действует 10 минут. `cancel` отменяет предварительный подсчёт. Повторный запуск,
изменившиеся данные или отозванные права не дают выполнить старое подтверждение.
Снимок ограничен моментом подсчёта: новые обращения не входят в старый выбор.
Во время удаления фоновые работы и обработчики приостановлены; новые webhook
сохраняются в очереди. Удаление записей и аудит коммитятся одной транзакцией,
физические файлы удаляются с устойчивой к перезапуску повторной попыткой.

Настройки чатов, блокировки, счётчики номеров, журнал администратора,
резервные копии и уже отправленные в MAX сообщения/фото/отчёты не удаляются.
Это очистка рабочих записей бота, а не полное удаление всех копий персональных
данных из MAX, технических журналов и резервных копий. Плановая очистка по
правилу 90 дней остаётся отдельным механизмом.

## 13. Персональные данные и внешние сервисы

В проекте **нет ИИ и нет ни одной передачи текста обращения во внешний сервис.**
Классификация, AI-черновик и AI-модерация удалены целиком: обращение жителя —
это персональные данные (имя, контакт, часто адрес и сведения о здоровье или
имуществе), а передача таких данных стороннему обработчику требует отдельного
правового основания.

Что это значит на практике:

* единственный внешний адресат, куда уходит текст обращения, — сам мессенджер MAX;
* всё остальное живёт в PostgreSQL и в хранилище вложений на вашем сервере;
* в зависимостях нет ни одного SDK моделей, а в `.env` нет ключей к ним;
* маршрутизацию по ответственным группам делает только диспетчер, текст ответа
  пишет сотрудник — вручную или по шаблону группы (`/group_template`).

Если ИИ когда-нибудь понадобится, возвращать его нужно не раньше, чем будет
решён вопрос с персональными данными: либо модель в контуре заказчика, либо
согласие заявителя и договор с обработчиком. Историю удалённого кода можно
поднять из git — коммит до удаления содержит каталог `src/ai/` целиком.

## 14. Резервное копирование БД

Регулярный дамп (данные обращений, история и роли живут только в PostgreSQL):

```bash
docker compose exec -T postgres pg_dump -U incident -d incident -Fc > backup-$(date +%F).dump
```

Восстановление:

```bash
docker compose exec -T postgres pg_restore -U incident -d incident --clean --if-exists < backup-2026-08-23.dump
```

Без Docker:

```bash
pg_dump "$DATABASE_URL" -Fc > backup-$(date +%F).dump
pg_restore -d "$DATABASE_URL" --clean --if-exists backup-2026-08-23.dump
```

Новые фотографии жителей и сотрудников остаются в MAX. Бот сохраняет токены,
использует их для предпросмотра, рабочих карточек и ответов, без скачивания
фотографий и без локальных/S3-копий. Размер и формат таких изображений контролирует MAX;
если размер известен из метаданных, дополнительно применяется `MEDIA_MAX_FILE_MB`.
При отсутствии токена бот просит отправить фото повторно. Гарантии долговременной
доступности фотографий у бота нет: этот риск согласован с владельцем проекта.

Файлы сотрудников и старые локальные фотографии продолжают использовать хранилище.
Их скачивание ограничено 20 МБ (`MEDIA_MAX_FILE_MB`, допустимо 1–100), с проверкой
фактически полученных байтов. Отчёты Excel также сохраняются в очереди до отправки.

Отдельно копируйте вложения:

* `MEDIA_STORAGE=local` — каталог `MEDIA_LOCAL_PATH` (по умолчанию
  `./data/uploads`, в Docker — том `uploads`);
* `MEDIA_STORAGE=s3` — средствами объектного хранилища (версионирование
  бакета, репликация).

Автоматическая очистка завершённых обращений устанавливается отдельным
systemd-таймером из `deploy/incident-bot-retention.*`. До ручного запуска всегда
используйте безопасный просмотр:

```bash
docker compose exec -T app npm run retention:preview
docker compose exec -T app npm run retention:run
```

Очистка удаляет записи обращения, ответы, историю, связанные служебные
сообщения и файлы обеих сторон из подконтрольного боту хранилища. Копии,
которые уже были доставлены в MAX или сохранены получателями, находятся вне
локального хранилища бота.

Таблицу `ProcessedUpdate` можно чистить от старых записей — она нужна только
для защиты от повторной доставки Webhook.

## 15. Тесты

```bash
npm test           # unit-тесты
npm run typecheck  # строгая проверка типов
```

Юнит-тесты не требуют инфраструктуры. Интеграционные тесты проверяют то, что
принципиально нельзя подделать (advisory-локи, условные UPDATE, уникальные
индексы) и требуют реального PostgreSQL:

```bash
docker compose up -d postgres
createdb incident_test        # или psql -c 'CREATE DATABASE incident_test'
TEST_DATABASE_URL=postgresql://incident:incident@localhost:5432/incident_test npm test
```

Без `TEST_DATABASE_URL` интеграционные наборы помечаются `skipped`, а не
проходят молча. Схема в тестовую БД накатывается автоматически
(`prisma db push`).

Пошаговый прогон на сервере — от чистой машины до живого E2E по семи сценариям
ТЗ — описан в [DEPLOY.md](DEPLOY.md). Перед живым запуском полезно выполнить
`npm run doctor`: он проверит токен, членство бота в каждом настроенном чате,
состояние webhook-подписки, миграции и хранилище вложений.

Покрыто, в частности:

* регистрация: 150 символов, 151 символ, эмодзи, фото, видео, аудио, пустой
  текст, заблокированный пользователь;
* дневной лимит: первое, второе, третье обращение и шесть параллельных попыток;
* распределение: обычное, два диспетчера одновременно, повторное нажатие;
* ответы: версии, отказ для видео, два одновременных ответа;
* согласование: approve, возврат, второй возврат, согласование после правок;
* SLA: срок ответа в 17:00 третьего рабочего дня, неизменность срока ответа после возврата, предупреждения
  во второй и третий рабочий день ровно по одному разу, тихие часы и выходные, статус `isOverdue` без потери workflow-статуса;
* безопасность: заявитель не может нажать кнопку диспетчера, ответственный не
  может согласовать, действие из чужого чата отклоняется, повторный webhook не
  выполняется дважды;
* **доставка**: два обращения от разных людей — каждый получает строго свой
  ответ (acceptance-тест, есть и в unit-, и в интеграционном виде).

```

    views/                тексты карточек
  incidents/              incident.service, repository, state machine, история
  distribution/           чат распределения
  sector/                 профильные чаты
  review/                 чат согласования
  answers/                версии ответов
  delivery/               единственная точка отправки заявителю
  categories/ users/ bans/ sessions/
  media/                  MediaStorage: local / S3
  reports/                XLSX
  retention/              просмотр и удаление завершённых обращений старше 90 дней
  sla/                    контроль сроков
  max/                    клиент MAX, разбиение сообщений, callback payload, idempotency key

  database/ config/ utils/
```

Обработчики только валидируют вход, вызывают сервис и рендерят ответ —
бизнес-логики в них нет.

### Ключевые инварианты

| Инвариант | Как обеспечен |
|---|---|
| Номер уникален и не меняется | `INSERT … ON CONFLICT DO UPDATE … RETURNING` по таблице `IncidentCounter`, уникальный индекс на `publicCode` |
| Не более 2 обращений в сутки | транзакция + `pg_advisory_xact_lock` по автору; календарные сутки считаются в `APP_TIMEZONE` |
| Обращение не уходит в две сферы | `UPDATE … WHERE id = ? AND status = 'DISTRIBUTION'`; проигравший получает имя победителя |
| Двойное согласование невозможно | тот же приём на `WAITING_REVIEW`, плюс `IncidentAnswer.deliveredAt` как защита от повторной отправки |
| Срок ответа не продлевается | `deadlineAt` вычисляется один раз при создании и не входит ни в один последующий `UPDATE` |
| Ответ уходит своему автору | `RequesterDeliveryService` — единственный, кто пишет заявителю, и получателя он берёт только как `incident → requester → maxUserId` |
| Состояние переживает рестарт | сессии операторов, маркеры SLA, маркер long polling и дедуп Webhook лежат в PostgreSQL |
| Повторный Webhook безвреден | детерминированный ключ + уникальный индекс `ProcessedUpdate.externalUpdateKey` |
| История доступна в срок хранения | `IncidentHistory` и старые версии ответов сохраняются вместе с обращением 90 дней после завершения, затем удаляются одной операцией |

## 17. Пользовательский сценарий

1. `/start` → приветствие и меню: «📝 Создать обращение», «🔎 Мои обращения»,
   «📄 Документы», «ℹ️ Правила».
2. При первом создании обращения пользователь открывает три документа и
   отдельно нажимает «Принимаю пользовательское соглашение», затем «Даю
   согласие на обработку персональных данных». Бот сохраняет время, редакцию,
   контрольную сумму документа и идентификатор нажатия. Для новой редакции
   нужны новые подтверждения.
3. При первом обращении бот запрашивает обязательные ФИО и телефон. В MAX
   телефон можно передать штатной кнопкой «Поделиться контактом» либо ввести
   вручную. После подтверждения итоговой карточки данные сохраняются в профиле
   и автоматически подставляются в следующие обращения; исправление карточки
   обновляет профиль. Правило хранения 90 дней продолжает действовать: после
   удаления неактивного профиля данные при новом обращении запрашиваются снова.
4. Пользователь выбирает тему или «Иное». Тема не определяет получателя.
5. Пользователь выбирает город или округ. Для округа можно выбрать населённый
   пункт, написать другой вручную или нажать «Пропустить».
6. Одно сообщение до 150 символов, при желании с фотографиями. Видео и аудио не
   принимаются, и такие попытки не расходуют дневной лимит.
7. Бот показывает итоговую карточку. Пользователь подтверждает её либо отдельно
   исправляет ФИО, телефон, тему, территорию, текст или фотографии. До нажатия
   «Всё верно» обращение не регистрируется и в рабочие чаты не отправляется.
8. После подтверждения пользователь получает номер и дату. Внутренний SLA ему
   не показывается; он используется только сотрудниками и автоматическим
   контролем просрочек.
9. Диспетчер выбирает «Калужская область», «Органы местного самоуправления»
   или «Органы исполнительной власти». В муниципальном списке подходящая по
   территории группа показывается первой как рекомендация. Выбор остаётся за
   диспетчером, одно обращение направляется ровно в одну группу.
10. В профильном чате сотрудник берёт обращение в работу и готовит ответ —
   вручную или по шаблону группы.
11. Обычно ответ уходит в чат согласования. Согласующий либо отправляет его
   пользователю, либо возвращает на доработку с причиной — срок ответа при этом не
   меняется.
12. Для «Калужской области» распределитель отвечает без согласования. В обоих
   вариантах ответ и вложения получает именно автор обращения. Под ответом
   доступны кнопки оценки от 1 до 5; сохранить можно только первую оценку по
   своему уже доставленному ответу. Оценка попадает в Excel-отчёт.

### Напоминания о сроках в рабочих чатах

Срок: три рабочих дня, пн–пт, 08:00–17:00 МСК. Будний день поступления до 17:00
считается первым (в том числе до 08:00); после 17:00 и в выходные отсчёт начинается
со следующего буднего дня. Срок ответа — 17:00 третьего рабочего дня. Пятница до 17:00
→ вторник 17:00; пятница после 17:00 или выходные → среда 17:00.
Бот напоминает со второго и третьего рабочего дня в 08:00. Просрочка отмечается
при наступлении срока ответа, уведомление отправляется в ближайшее рабочее время.
Все напоминания о сроках и очереди разрешены только пн–пт, 08:00–17:00 МСК.
Праздничный календарь отдельно не применяется: рабочие дни определяются по дням недели.
Проверка выполняется каждые `SLA_CHECK_INTERVAL_MINUTES` минут (по умолчанию 10),
поэтому уведомление приходит при ближайшей проверке после соответствующего срока.
Каждая ступень ставится в очередь один раз; после простоя выбирается только
последняя актуальная ступень. Старое предупреждение за 6 часов больше не создаётся.

Напоминание приходит ответом на исходную карточку в назначенный профильный чат:
нажатие на цитату позволяет перейти к обращению. В тексте указаны номер, статус,
срок ответа, группа и сотрудник, взявший обращение в работу. До распределения бот
отвечает на карточку в чате распределения. На согласовании и доработке обращения
остаются открытыми; RESOLVED и REJECTED исключаются.

Метка ступени, история и сообщение сохраняются одной транзакцией. При повторной
доставке бот заново читает статус, ответственных и идентификатор карточки;
устаревшее напоминание после закрытия или перехода к следующей ступени пропускается.
Если карточка ещё не доставлена, напоминание ждёт её через обычную очередь повторов.

### Предложение подписаться после решения обращения

После доставки итогового ответа житель выбирает оценку 1–5. Только после
сохранения оценки бот отправляет отдельное предложение подписаться на каналы
https://max.ru/Shapsha_VV и https://max.ru/pravitelstvo40 с двумя кнопками-ссылками.
Кнопки оценки остаются на сообщении с ответом. Предложение ставится в очередь
одной транзакцией с оценкой, один раз на обращение.
До выбора оценки оно не отправляется; при сбое отправки самого предложения
очередь повторяет только его. Для отклонённых обращений предложение не создаётся.

### Изменение порядка работы 08.09.2026

Запросы уточнений у жителей отключены. Старые кнопки не запускают вопрос или
ответ на уточнение. При первом запуске обновления незавершённые вопросы отменяются,
сроки возобновляются с учётом прошедшей паузы. Ранее полученные сведения и история
сохраняются. Повторный запуск не продлевает срок повторно.

На обоих листах Excel используется колонка «Тема обращения». На листе
«Просроченные» она расположена сразу после номера обращения. Выбор без конкретной
тематики отображается как «Иное» в кнопках, карточках и отчётах.

### Очередь распределения

До назначения организации диспетчер может исправить тему кнопкой «Изменить тему».
Выбранная тема обновляется в карточке и Excel; история TOPIC_CHANGED сохраняет
прежнее и новое значение и автора. Исправление не меняет получателя, статус или срок
ответа и защищено тем же закреплением за оператором, что и распределение.

Жителю в «Моих обращениях» доступны только «В работе» и «Закрыто» (RESOLVED/REJECTED).
Промежуточные этапы доступны сотрудникам. «Иное» — последний вариант только на
последней странице тем. После оценки ответа предложение подписки содержит текст
«Подписывайтесь на наши каналы в MAX».

В профильных чатах и согласовании также доступны `/queue` и одна закреплённая
панель: следующее старейшее свободное, список, мои обращения и сводка за сегодня.
Профильная очередь включает ASSIGNED/IN_PROGRESS/REVISION_REQUIRED только своей
организации. Взятие атомарно переводит обращение в IN_PROGRESS. Согласование включает
WAITING_REVIEW: резервирование в ActionLock на 15 минут блокирует чужое согласование
и возврат, его можно освободить раньше. Панели обновляются раз в минуту.

`/today` во всех рабочих чатах показывает текущие статусы обращений, созданных
сегодня по Москве, с пагинацией. Профильный чат видит свою организацию, распределение,
согласование и системная аналитика — все организации. Завершение отделено от ожидания
доставки. Долговечные задания обновляют кнопки исходных карточек согласования,
доработки и копий очереди после смены этапа и после запоздалой публикации.
Фотографии и файлы ответов сохраняются при обновлении кнопок. Устаревшие сессии
подготовки ответа и возврата на доработку автоматически сбрасываются.

Бот поддерживает одну панель в чате распределения: количество ожидающих, свободных,
закреплённых за операторами, задержанных более 30/60 минут и возраст самого старого.
Она обновляется раз в минуту. `/queue` открывает список и запрашивает обновление панели.
Бот закрепляет актуальную панель. Перед редактированием проверяет существование
сообщения: подтверждённое удаление восстанавливает панель, сетевая ошибка не создаёт копию.

«Следующее обращение» выдаёт самое старое свободное обращение с кнопками распределения
и цитатой исходной карточки. «Посмотреть список» показывает все нераспределённые
по 10 на страницу, старейшие первыми. Очередь читается из БД и переживает перезапуск.
Доступ есть только у ADMIN/DISPATCHER в назначенном чате распределения.

Одному оператору выдаётся одно обращение на 15 минут. Повторное нажатие возвращает
его же; «Освободить обращение» позволяет вернуть его раньше. Через 15 минут
другой оператор может взять его автоматически. Закрепление действует и при работе
с исходными карточками: чужое активное закрепление блокирует распределение и
отклонение. Истечение закрепления не меняет статус или срок ответа обращения.
Обращение исчезает из очереди только после распределения или отклонения.

Напоминания о распределении приходят по будням с 08:00 включительно до 17:00
исключительно по Москве. Через час ожидания приходит общая сводка в чат распределения,
через два часа — сигнал о необходимости помощи в DELIVERY_ALERT_CHAT_ID.
При очереди от 30 обращений оба сигнала разрешены сразу. На каждый чат создаётся
не более одной сводки за календарный час. Перед доставкой повторно проверяются
график, актуальный час и остаток очереди; ночные и устаревшие сводки пропускаются.
Настройки: DISTRIBUTION_QUEUE_ENABLED, WORKDAY_START,
WORKDAY_END, DISTRIBUTION_OVERLOAD_COUNT. Ночью приём и очередь работают;
общий срок считается по рабочим дням (INCIDENT_SLA_WORKDAYS=3).

Проверка раз в минуту восстанавливает отсутствующие задания публикации карточек
нераспределённых обращений. Существующие повторы и ошибки доставки обслуживает
общая очередь; FAILED не сбрасывается бесконечно этой проверкой.

## Короткая справка и подробные инструкции

`/info` и `/help` показывают короткую памятку для текущего чата. Кнопка
«Подробная инструкция (PDF)» отправляет файл для текущего чата: распределение,
согласование, аналитика либо профильная работа (с согласованием или прямым
ответом). В личном диалоге отправляется руководство жителя. Администратору также
доступна отдельная инструкция. Права и принадлежность рабочего чата
проверяются заново при нажатии кнопки; просмотр справки не сбрасывает ввод.

Готовые PDF находятся в `output/pdf/` и включаются в Docker-образ.
Исходник текстов и вёрстки: `scripts/generate-chat-guides.py`.
Для пересборки нужны Python, `reportlab`, `pypdf` и шрифты Arial либо DejaVu Sans:

```powershell
python scripts/generate-chat-guides.py --font-dir C:/Windows/Fonts
```

После изменения текста пересоберите PDF, проверьте страницы визуально и
обновите файлы в репозитории. Выбор файлов в `src/bot/views/chat-guide.ts`
должен соответствовать текущему назначению чата. При совмещении нескольких
назначений отправляются только соответствующие им инструкции. При изменении порядка
работы бота обновляйте также памятку и соответствующий раздел PDF.

### Единое закрепление и возврат на перераспределение

В распределении, профильных чатах и согласовании карточки показывают текущего
сотрудника и время окончания закрепления (15 минут), либо «Свободно».
Кнопка «Освободить обращение» доступна владельцу; она отменяет незавершённый ввод,
но сохраняет обращение, ответы, историю и срок. Истёкшее закрепление больше не
блокирует коллег; фоновая проверка обновляет карточки раз в минуту.
В профильном чате подготовка ответа автоматически закрепляет обращение.
В согласовании есть «Взять на согласование»; начало ввода замечаний также закрепляет ответ.

Исполнитель до отправки ответа может нажать «Вернуть на перераспределение» и
указать причину (1–1000 символов). Возврат атомарно очищает текущее назначение и
закрепления, сохраняет историю REDISTRIBUTION_REQUESTED, уведомляет распределение
и возвращает обращение в очередь по исходным createdAt/id. Срок ответа не продлевается.
Повторное назначение создаёт новую профильную карточку, включая возврат в тот же чат;
старые карточки и запоздалые задания доставки не возвращают старые кнопки.

### Отклонение с предварительной проверкой

В распределении «Отклонить» предлагает восемь причин по пунктам `/rules` и «Иное».
Шаблон или введённая причина (до 2000 символов) сначала показываются сотруднику.
«Верно» сохраняет отказ и ставит уведомление жителю в очередь; «Исправить» возвращает
к вводу текста, «Отмена» закрывает подготовку без отклонения. Черновик привязан к
сотруднику, чату, обращению и действующему закреплению на 15 минут. Устаревшие
подтверждения, чужие кнопки и повторная отправка блокируются.

Excel содержит колонку «Отклонил (ФИО сотрудника)»: сохранённое имя сотрудника из MAX
в истории отказа, включая прежние отказы с такими данными. Переименование профиля
не изменяет имя в отчёте. Если полное ФИО в MAX не указано, выводится доступное имя;
недостающие сведения не дополняются автоматически.

### Личная работа сотрудников (пилот)

В карточках распределения, исполнения и согласования доступна кнопка «Работать лично».
Она закрепляет обращение за сотрудником и показывает ссылку «Продолжить в боте».
Рабочий чат сохраняет общую очередь и статусы, а ввод и проверка текста происходят
в личном диалоге. Кнопка «Моя работа» и команда `/work` возвращают к обращениям;
«Меню жителя» переключает диалог обратно в обычный режим, сохраняя рабочий черновик.
Тексты ответов, замечаний и причин перераспределения проходят предварительный просмотр;
назначение организации и согласование требуют отдельного подтверждения.

Черновики и текущий шаг хранятся в `PrivateWorkItem`, переживают перезапуск и окончание
15-минутного закрепления. Для отправки после его окончания нужно заново взять обращение.
В последние две минуты фоновая проверка может прислать одно личное напоминание.
«Освободить» сохраняет личный черновик, «Отменить действие» удаляет его.
«Исправить» ожидает новый текст со всеми нужными фото/файлами одним сообщением.

Каждое личное действие проверяет членство сотрудника в исходном рабочем чате через MAX,
даже для администратора. При недоступности проверки доступ закрывается. Подтверждения
привязаны к сотруднику, обращению, этапу, версии ответа и действующему закреплению.
Групповой ввод не обрабатывается, если действие открыто лично. Прежние групповые
сценарии остаются доступны для постепенного перехода. Перед запуском применить
аддитивную миграцию `20260911150000_private_employee_workspace`.

## 3. Грабли, на которые уже наступили

Здесь то, что стоило времени и наверняка встретится снова.

### 3.1 Сертификаты MAX — самое важное

`*.max.ru` подписан цепочкой **Russian Trusted Sub CA → Russian Trusted Root CA**
(Минцифры). Этого корня нет в стандартном наборе CA, поэтому любой вызов MAX API
падает с `fetch failed`, при том что остальной HTTPS с сервера работает.

Корень лежит в `deploy/russian-trusted-ca.pem` и подключается **только к
процессу бота** через `NODE_EXTRA_CA_CERTS` — в системное хранилище не ставится
и на другие контейнеры не влияет. В `docker-compose.yml` это уже настроено.

**Для любого ручного запуска на хосте переменную надо задать самому:**

```bash
NODE_EXTRA_CA_CERTS=/opt/incident-bot/deploy/russian-trusted-ca.pem npm run doctor
```

`/etc/profile.d/max-ca.sh` существует, но **неинтерактивная SSH-сессия его не
читает** — скрипт, запущенный через `ssh host "команда"`, переменную не увидит и
упадёт на `fetch failed`. Один раз это уже привело к тому, что скрипт привязки
чатов снял две существующие привязки и умер на первой же проверке. Повторный
прогон с переменной всё восстановил, но осадок остался: **всегда указывайте
переменную явно.**

### 3.2 Составные сообщения в MAX

Проверено на живом API, а не по документации:

| Что | Результат |
|---|---|
| текст + фото + кнопки в одном сообщении | **работает** |
| правка сообщения без поля `attachments` | фото и кнопки **сохраняются** |
| правка с передачей `attachments` | список заменяется целиком |

Отсюда три метода в `MaxMessageService`: `send` (всё одним сообщением),
`editCardText` (правит текст, вложения не трогает), `finalizeCard` (гасит
карточку: ни медиа, ни кнопок). Разносить текст и фото по разным сообщениям, как
было сделано изначально, не требуется — второе сообщение появляется только если
в ответе одновременно и фото, и файл (MAX группирует вложения по типу).

### 3.3 tsx не проверяет типы

`npx tsx script.ts` выполнит код с ошибкой типов, а `npm run build` на ней
упадёт. Один раз так и вышло: скрипт отработал, а сборка образа сломалась бы на
следующем деплое. **Перед деплоем всегда `npm run typecheck`** (или `npm run
check`, который делает typecheck + сборку + тесты).

## 4.1 Нагрузочные замеры

Измерено на этом же сервере (2 vCPU, 3.8 ГБ), а не оценено на глаз.

| Слой | Пропускная способность | Задержка |
|---|---|---|
| Приём webhook (HTTPS → Caddy → Fastify → дедуп) | 460–500 запр/с, 100% успеха при 100 параллельных | медиана 82 мс, p95 275 мс |
| Регистрация обращения (транзакция + счётчик + INSERT) | ~146 обр/с — потолок CPU и БД | при 500 одновременных p95 3.3 с |
| Покой | app 70 МБ, postgres 60 МБ, caddy 15 МБ | из 3.9 ГБ |

Всплеск в 500 одновременных регистраций проходит целиком: запросы встают в
очередь, но не отбиваются.

### Что было исправлено по итогам замеров

Первый прогон 500 одновременных регистраций дал **152 отказа** с
`Unable to start a transaction in the given time`. Причина: Prisma по умолчанию
берёт пул `num_cpus*2+1` — на двух ядрах это 5 соединений, — и даёт всего 2
секунды на ожидание свободного. Сама работа занимает ~60 мс, то есть отказы
были чистой очередью, а не нехваткой ресурсов.

Исправлено двумя настройками:

* `connection_limit=20` в `DATABASE_URL` (см. `DB_CONNECTION_LIMIT` в `.env`);
* явные `maxWait`/`timeout` для транзакций — константа `TRANSACTION_OPTIONS`
  в `src/database/prisma.ts`.

После этого 500 из 500 проходят. Пропускная способность не изменилась (~146/с —
это реальный потолок), но вместо отказа человек просто ждёт. Для бота это
правильный размен: MAX уже получил свой `200 OK`, пользователь ждёт лишь
сообщение с номером.

Все тесты после изменения проходят — гарантия «не более 2 обращений в
сутки» и защита от гонок не пострадали.

### Что упрётся раньше сервера

1. **Люди.** 26 сфер; каждое обращение требует маршрутизации, ответа и
   согласования. Это на порядки меньше 146/с.
2. **Лимиты MAX API.** Не измерялись намеренно — нагружать чужой прод нельзя.
   Если появятся `429`, встроенный retry с экспоненциальной паузой их отработает.
3. **Вложения.** Каждое фото — скачивание из MAX и повторная загрузка. Это
   упирается в канал, а не в CPU, и в замеры выше не входило.

Для ориентира: 146 обр/с — это 525 000 обращений в час. При лимите 2 обращения
на человека в сутки, чтобы это исчерпать, нужно 146 разных людей **каждую
секунду**. Запас относительно любого реалистичного муниципального потока —
трёхзначный.

## 4.2 Усиление доступа к PostgreSQL (2 сентября 2026)

Перед изменениями создан и проверен комплект
`backups/pre-hardening-20260902-105312/`: дамп PostgreSQL, архив вложений,
Compose, закрытая копия `.env` и SHA-256. Дамп читается через
`pg_restore --list`; копия данных и вложений также вынесена с сервера.

PostgreSQL больше не опубликован на всех интерфейсах: host-порт `5432`
привязан только к `127.0.0.1`, а приложение продолжает подключаться через
внутреннюю Docker-сеть. Внешняя TCP-проверка подтверждает, что порт закрыт.

Стандартный пароль роли `incident` заменён случайным длинным значением.
`POSTGRES_PASSWORD` и `DATABASE_URL` синхронизированы, секрет хранится только
в серверном `.env` с правами `600`. Старый пароль проверенно отклоняется через
Docker-сеть, новый принимается. После пересоздания PostgreSQL и приложения все
11 обращений остались на месте, `/ready` отвечает, `npm run doctor` завершает
33 проверки без предупреждений и ошибок.

### Резервное копирование

Ежедневный проверяемый бэкап запускает systemd-таймер
`incident-bot-backup.timer`. Расписание — `00:30 UTC` (03:30 МСК) плюс
случайная задержка до 10 минут; `Persistent=true` догоняет пропущенный запуск
после включения сервера.

Скрипт `deploy/backup.sh` атомарно создаёт в `/opt/incident-bot/backups/`:

* PostgreSQL custom dump (`incident.dump`);
* архив локальных вложений (`uploads.tar.gz`);
* закрытые копии `.env` и `docker-compose.yml`;
* метаданные и `SHA256SUMS`.

До публикации каталога скрипт проверяет все SHA-256, читает дамп через
`pg_restore --list` и архив через `tar -tzf`. Незавершённый каталог удаляется,
а `latest` указывает только на полностью проверенную копию. Права каталога —
`700`, файлов — `600`.

Хранение: 14 дней ежедневных, 70 дней еженедельных и 400 дней ежемесячных
копий. Недельная копия создаётся по воскресеньям, месячная — первого числа;
они используют hard links и не дублируют неизменившиеся файлы на диске.

Проверка и ручной запуск:

```bash
systemctl list-timers incident-bot-backup.timer --all
systemctl status incident-bot-backup.timer
systemctl start incident-bot-backup.service
journalctl -u incident-bot-backup.service -n 100 --no-pager

cd /opt/incident-bot/backups/latest
sha256sum -c SHA256SUMS
cd /opt/incident-bot
docker compose exec -T postgres pg_restore --list \
  < backups/latest/incident.dump >/dev/null
```

Первый прогон `daily-20260902-112610` успешно проверен: 96 объектов в дампе,
архив вложений читается, приложение осталось `ready`, все 11 обращений на
месте. Локальная автоматизация не заменяет внешнюю копию: до production нужно
настроить отправку проверенного комплекта на отдельный сервер или S3.

## 7. Что решили и почему

Короткие обоснования, чтобы не переоткрывать вопросы заново.

**26 сфер выбираются страницами по 6.** Один список на 27 кнопок — длинная
прокрутка на телефоне. «Не знаю» закреплено сверху на каждой странице: выбор
пользователя по §8 ТЗ всё равно только предположение, маршрут определяет
диспетчер.

**ИИ убран из проекта целиком (сентябрь 2026).** Классификация, AI-черновик и
AI-модерация работали и были измерены (90–98% попадания по сфере, 1.4–2.2 с,
~2 копейки за вызов), но каждый вызов означал отправку текста обращения жителя
стороннему обработчику. Обращение — это персональные данные, и без отдельного
правового основания такая передача недопустима, поэтому выключением флага
ограничиваться не стали: удалён код (`src/ai/`), зависимость на SDK моделей,
переменные `AI_*` и столбцы `ai*` в БД. Возвращать имеет смысл только с моделью
в контуре заказчика либо с согласием заявителя и договором с обработчиком;
предыдущая реализация лежит в git, в коммите до удаления.

**Отчёты — кнопками.** `/report` без аргументов показывает периоды; ручной ввод
принимает `01.08.2026 - 10.08.2026` в любом написании. Прежний синтаксис
(`/report 7d`, ISO-даты) сохранён, чтобы не ломать скрипты и привычки.

**Права проверяются при нажатии, а не при показе кнопок.** Карточка остаётся в
истории чата, нажать её может кто угодно позже — поэтому факт существования
кнопки ничего не разрешает.

**Сфера без чата скрыта от диспетчера, но это не ошибка в доктора.** Это
состояние внедрения; если считать его ошибкой, доктор будет вечно красным и
перестанет что-либо значить.

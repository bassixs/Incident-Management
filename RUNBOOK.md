## 3. Грабли, на которые уже наступили

Здесь то, что стоило времени и наверняка встретится снова.

### 3.1 Сертификаты MAX — самое важное

`*.max.ru` подписан цепочкой **Russian Trusted Sub CA → Russian Trusted Root CA**
(Минцифры). Этого корня нет в стандартном наборе CA, поэтому любой вызов MAX API
падает с `fetch failed`, при том что остальной HTTPS с сервера работает.

Корень лежит в `deploy/russian-trusted-ca.pem` и подключается **только к
процессу бота** через `NODE_EXTRA_CA_CERTS` — в системное хранилище не ставится
и на другие контейнеры не влияет. В `docker-compose.yml` это уже настроено.

**Для любого ручного запуска на хосте переменную надо задать самому:**

```bash
NODE_EXTRA_CA_CERTS=/opt/incident-bot/deploy/russian-trusted-ca.pem npm run doctor
```

`/etc/profile.d/max-ca.sh` существует, но **неинтерактивная SSH-сессия его не
читает** — скрипт, запущенный через `ssh host "команда"`, переменную не увидит и
упадёт на `fetch failed`. Один раз это уже привело к тому, что скрипт привязки
чатов снял две существующие привязки и умер на первой же проверке. Повторный
прогон с переменной всё восстановил, но осадок остался: **всегда указывайте
переменную явно.**

### 3.2 Составные сообщения в MAX

Проверено на живом API, а не по документации:

| Что | Результат |
|---|---|
| текст + фото + кнопки в одном сообщении | **работает** |
| правка сообщения без поля `attachments` | фото и кнопки **сохраняются** |
| правка с передачей `attachments` | список заменяется целиком |

Отсюда три метода в `MaxMessageService`: `send` (всё одним сообщением),
`editCardText` (правит текст, вложения не трогает), `finalizeCard` (гасит
карточку: ни медиа, ни кнопок). Разносить текст и фото по разным сообщениям, как
было сделано изначально, не требуется — второе сообщение появляется только если
в ответе одновременно и фото, и файл (MAX группирует вложения по типу).

### 3.3 tsx не проверяет типы

`npx tsx script.ts` выполнит код с ошибкой типов, а `npm run build` на ней
упадёт. Один раз так и вышло: скрипт отработал, а сборка образа сломалась бы на
следующем деплое. **Перед деплоем всегда `npm run typecheck`** (или `npm run
check`, который делает typecheck + сборку + тесты).

## 4.1 Нагрузочные замеры

Измерено на этом же сервере (2 vCPU, 3.8 ГБ), а не оценено на глаз.

| Слой | Пропускная способность | Задержка |
|---|---|---|
| Приём webhook (HTTPS → Caddy → Fastify → дедуп) | 460–500 запр/с, 100% успеха при 100 параллельных | медиана 82 мс, p95 275 мс |
| Регистрация обращения (транзакция + счётчик + INSERT) | ~146 обр/с — потолок CPU и БД | при 500 одновременных p95 3.3 с |
| Покой | app 70 МБ, postgres 60 МБ, caddy 15 МБ | из 3.9 ГБ |

Всплеск в 500 одновременных регистраций проходит целиком: запросы встают в
очередь, но не отбиваются.

### Что было исправлено по итогам замеров

Первый прогон 500 одновременных регистраций дал **152 отказа** с
`Unable to start a transaction in the given time`. Причина: Prisma по умолчанию
берёт пул `num_cpus*2+1` — на двух ядрах это 5 соединений, — и даёт всего 2
секунды на ожидание свободного. Сама работа занимает ~60 мс, то есть отказы
были чистой очередью, а не нехваткой ресурсов.

Исправлено двумя настройками:

* `connection_limit=20` в `DATABASE_URL` (см. `DB_CONNECTION_LIMIT` в `.env`);
* явные `maxWait`/`timeout` для транзакций — константа `TRANSACTION_OPTIONS`
  в `src/database/prisma.ts`.

После этого 500 из 500 проходят. Пропускная способность не изменилась (~146/с —
это реальный потолок), но вместо отказа человек просто ждёт. Для бота это
правильный размен: MAX уже получил свой `200 OK`, пользователь ждёт лишь
сообщение с номером.

Все тесты после изменения проходят — гарантия «не более 2 обращений в
сутки» и защита от гонок не пострадали.

### Что упрётся раньше сервера

1. **Люди.** 26 сфер; каждое обращение требует маршрутизации, ответа и
   согласования. Это на порядки меньше 146/с.
2. **Лимиты MAX API.** Не измерялись намеренно — нагружать чужой прод нельзя.
   Если появятся `429`, встроенный retry с экспоненциальной паузой их отработает.
3. **Вложения.** Каждое фото — скачивание из MAX и повторная загрузка. Это
   упирается в канал, а не в CPU, и в замеры выше не входило.

Для ориентира: 146 обр/с — это 525 000 обращений в час. При лимите 2 обращения
на человека в сутки, чтобы это исчерпать, нужно 146 разных людей **каждую
секунду**. Запас относительно любого реалистичного муниципального потока —
трёхзначный.

## 4.2 Усиление доступа к PostgreSQL (2 сентября 2026)

Перед изменениями создан и проверен комплект
`backups/pre-hardening-20260902-105312/`: дамп PostgreSQL, архив вложений,
Compose, закрытая копия `.env` и SHA-256. Дамп читается через
`pg_restore --list`; копия данных и вложений также вынесена с сервера.

PostgreSQL больше не опубликован на всех интерфейсах: host-порт `5432`
привязан только к `127.0.0.1`, а приложение продолжает подключаться через
внутреннюю Docker-сеть. Внешняя TCP-проверка подтверждает, что порт закрыт.

Стандартный пароль роли `incident` заменён случайным длинным значением.
`POSTGRES_PASSWORD` и `DATABASE_URL` синхронизированы, секрет хранится только
в серверном `.env` с правами `600`. Старый пароль проверенно отклоняется через
Docker-сеть, новый принимается. После пересоздания PostgreSQL и приложения все
11 обращений остались на месте, `/ready` отвечает, `npm run doctor` завершает
33 проверки без предупреждений и ошибок.

### Полный справочник команд бота

Ниже перечислены **все команды, которые сейчас понимает бот**. Обозначения:

- `<ЗНАЧЕНИЕ>` — обязательный параметр, угловые скобки писать не нужно;
- `[ЗНАЧЕНИЕ]` — необязательный параметр;
- `-` — удалить ранее заданное значение или специальные роли;
- **личный чат** — диалог один на один с ботом;
- **рабочий чат** — групповой чат MAX, куда добавлен бот.

Если бот отвечает «У вас нет прав», сначала проверьте `/whoami`, затем роль и
нужный рабочий чат. Команды администратора технически работают и в личном, и
в групповом чате; для настроек пользователей безопаснее использовать личный
диалог, а для ошибок доставки — закрытый чат «Проблемы».

| `/delivery_retry` | Возвращает в очередь **все** неудачные исходящие отправки. | Используйте только когда понятно, что общая причина устранена. Входящие события эта команда не повторяет. |

Кнопки «Распределить», «Взять в работу», «Согласовать» и другие действия на
карточках не являются отдельными slash-командами. Они описаны в сценариях
работы ниже и защищены от повторных быстрых нажатий.

### История обращений и аудит администраторов

`/history <НОМЕР>` читает уже существующую неизменяемую историю обращения.
Записи идут от создания к последнему событию и показывают, когда менялся
статус, кто выполнил действие, куда распределили обращение, версии ответа,
причины возврата или отклонения, SLA-предупреждения и факт доставки. Команда
доступна всем сотрудникам, но только в рабочем чате.

`/audit` — отдельный журнал успешных команд `ADMIN`. В него записываются:

- блокировка и разблокировка пользователей;
- назначение и снятие ролей;
- создание, включение, отключение и изменение сфер;
- изменение чата, ведомства и шаблона сферы;
- ручной запуск SLA-проверки;
- выборочный или массовый повтор исходящей доставки.

Аудит дополняется только новыми строками: бот не предоставляет команду для
изменения или удаления записей. Тексты обращений туда не копируются; причины
блокировок и понятное описание настройки сохраняются. Токены, пароли, ключи и
строки подключения не записываются. Исторические административные команды,
выполненные до появления таблицы `AdminAuditLog`, задним числом не создаются.

### Управление ролями — без перезапуска

Роли хранятся в базе данных и применяются сразу. Подключаться к серверу или
перезапускать бот при обычном назначении сотрудников не нужно.

| Роль | Кому назначать | Что разрешает |
|---|---|---|
| `DISPATCHER` | сотруднику распределения | распределять и отклонять обращения, блокировать авторов, делать отчёты |
| `RESPONDER` | сотруднику профильного отдела | служебный поиск обращений; работа с карточками своей сферы |
| `APPROVER` | сотруднику согласования | принимать ответ или возвращать его на доработку |
| `ADMIN` | только доверенному администратору | все действия и управление ролями, сферами и блокировками |

У каждого пользователя также автоматически есть базовая роль `REQUESTER`:
создание и просмотр собственных обращений. Назначать её вручную не нужно.

Кроме роли, добавьте сотрудника в нужный рабочий чат MAX: диспетчера — в чат
распределения, согласующего — в чат согласования, ответственного — в чат его
профильной сферы. Для ответственного именно членство в профильном чате даёт
доступ к кнопкам карточек этой сферы; роль не открывает чужие профильные чаты.

#### Назначить роль

1. Сотрудник пишет боту в личном диалоге команду `/whoami` и передаёт
   администратору свой `MAX ID`.
2. Администратор пишет боту одну из команд:

```
/role 7654321 DISPATCHER
/role 7654321 RESPONDER
/role 7654321 APPROVER
/role 7654321 ADMIN
```

Один человек может совмещать несколько функций. Роли перечисляются через
запятую **без пробелов**:

```
/role 7654321 DISPATCHER,APPROVER
```

Команда каждый раз задаёт пользователю полный список специальных ролей. Если
у человека уже был `DISPATCHER`, команда `/role 7654321 APPROVER` заменит его
на `APPROVER`; для сохранения обеих нужно указать
`DISPATCHER,APPROVER`.

#### Проверить или снять роли

После назначения сотрудник снова отправляет `/whoami`: бот должен показать
новую роль. Общие количества назначенных ролей также выводит `npm run doctor`.

Чтобы снять все специальные права и оставить человека обычным заявителем:

```
/role 7654321 -
```

Изменять роли может только `ADMIN`. Кнопки дополнительно ограничены рабочими
чатами: наличие роли само по себе не позволяет выполнять действие из личного
или постороннего чата.

#### Важная защита от потери доступа

Не снимайте роль у последнего `ADMIN`, пока второй администратор не назначен и
не проверил `/whoami`. Сейчас в базе один `ADMIN`, поэтому снимать с него роль
нельзя.

Если последний администратор всё же удалён, временно укажите его MAX ID в
`ADMINS` серверного `.env`, пересоздайте контейнер `app`, верните постоянную
роль командой `/role <MAX_ID> ADMIN`, затем снова очистите `ADMINS` и
пересоздайте `app`. Списки ролей в `.env` предназначены только для такого
первичного или аварийного доступа: оставленный там ID нельзя лишить прав
обычной командой `/role`.

### Очереди доставки и защита кнопок

Принятые webhook сохраняются в таблице `InboundUpdate` до ответа `200 OK`.
Исходящие сообщения, включая текст, кнопки и временные ссылки на сохранённые
вложения, сначала попадают в `OutboundMessage`. Worker запускается вместе с
приложением, делает немедленную попытку и при сбое повторяет отправку через
30 секунд, 1, 5, 15, 30 и далее 60 минут. После 12 неудач запись получает
`FAILED` и не удаляется автоматически.

Проверка без подключения к серверу — командой администратора в MAX:

```
/delivery_status   # сколько входящих и исходящих ждут или требуют внимания
/delivery_errors   # последние ошибки, получатели, контекст и короткие коды
/delivery_retry a1b2c3d4  # повторить одну выбранную исходящую доставку
/delivery_retry    # вернуть все FAILED исходящие в автоматическую очередь
```

Те же показатели входят в `npm run doctor`; наличие хотя бы одной записи
`FAILED` делает диагностику красной. Входящие `FAILED` нельзя массово
перезапускать вслепую: сначала нужно проверить, успела ли операция изменить
обращение до сбоя.

Команда `/delivery_errors` доступна только `ADMIN`. Она показывает рабочий
контекст, включая данные получателя, если они присутствуют в сообщении, но
обязательно скрывает токены, пароли и ключи. Для выборочного повтора скопируйте
восьмизначный код из списка: `/delivery_retry <КОД>`. Без кода команда, как и
раньше, повторяет все неудачные исходящие сообщения. Входящие ошибки этой
командой не перезапускаются из-за риска повторно выполнить бизнес-действие.

Выборочное управление ошибками развёрнуто 2 сентября 2026 после бэкапа
`daily-20260902-132637`. Полный прогон — 130/130 тестов; после перезапуска
`/delivery_errors` доступна, активных проблем нет, `npm run doctor` — 35/35.

### Чат технических предупреждений

Укажите закрытый технический чат в серверном `.env`:

```env
DELIVERY_ALERT_CHAT_ID=-123456789
```

После пересоздания `app` бот проверяет новые ошибки раз в минуту. Несколько
ошибок объединяются в одно сообщение; полные тексты обращений, MAX ID
пользователей и секреты туда не попадают. Запись получает отметку только после
успешной отправки предупреждения. Поэтому при недоступности MAX бот сообщит о
накопившейся проблеме после восстановления связи. Само предупреждение идёт
мимо обычной outbox-очереди и не может зациклить оповещения.

Проверка доступа бота к этому чату входит в `npm run doctor`. Команда
`npm run doctor -- --send` дополнительно отправляет в чат безвредное
контрольное сообщение.

Функция включена на сервере 2 сентября 2026 после бэкапа
`daily-20260902-130618`. Миграция `20260902163000_delivery_alerts` проверена
на отдельной пустой базе; полный прогон — 128/128 тестов. Контрольное сообщение
из рабочего контейнера доставлено, `npm run doctor` — 35/35.

Каждое нажатие кнопки получает короткую блокировку в `ActionLock`. Повторный
клик отвечает «Уже обрабатывается» и не запускает действие ещё раз. Если
операция длится больше 600 мс, первый клик сразу получает «Принято,
обрабатываю…». При обычной ошибке блокировка снимается, при падении процесса
истекает сама; постоянные изменения статуса дополнительно защищены условными
атомарными обновлениями PostgreSQL.

Успешные записи inbox/outbox хранятся 30 дней. MAX не поддерживает ключ
идемпотентности для `POST /messages`, поэтому авария ровно между приёмом
сообщения MAX и записью `SENT` может дать редкий дубль. Политика намеренно
выбрана в пользу гарантированной доставки, а не молчаливой потери ответа.

### Хранение и автоматическое удаление обращений

Завершённое обращение хранится 90 календарных дней после окончательного ответа
или отклонения. Активные обращения не удаляются независимо от их возраста.
Ежедневная очистка запускается в `00:00 UTC` (03:00 МСК) плюс случайная задержка
до двух минут — до резервного копирования в 03:30 МСК.

Порядок безопасный: сначала удаляются фотографии и файлы заявителя и ответа,
затем в одной транзакции PostgreSQL удаляются обращение, ответы, история,
сессии, блокировки кнопок и связанные записи доставки. Если хранилище файлов
недоступно, запись остаётся в базе и следующая ежедневная попытка повторяет
удаление. Одновременно может идти только одна очистка.

Установка таймера на сервере:

```bash
install -m 644 deploy/incident-bot-retention.service /etc/systemd/system/
install -m 644 deploy/incident-bot-retention.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now incident-bot-retention.timer
systemctl list-timers incident-bot-retention.timer --all
```

Ручной безопасный просмотр и запуск с сервера:

```bash
cd /opt/incident-bot
docker compose exec -T app npm run retention:preview
docker compose exec -T app npm run retention:run
journalctl -u incident-bot-retention.service -n 100 --no-pager
```

То же доступно администратору в закрытом рабочем чате командами
`/retention_preview` и `/retention_run УДАЛИТЬ`. Ручной запуск записывается в
`/audit`. Ошибки автоматического запуска отправляются в технический чат,
заданный через `DELIVERY_ALERT_CHAT_ID`.

Отчёт содержит все ещё хранящиеся поля обращения. Поэтому ежемесячный отчёт
за прошедший месяц нужно формировать в начале следующего месяца; запас в 90
дней позволяет сделать это повторно. После очистки исходный подробный отчёт за
старый период сформировать уже нельзя.

Важно: удаляются только копии, подконтрольные боту. Сообщения и файлы, уже
доставленные в MAX или сохранённые получателем, локальная очистка удалить не
может. После восстановления старого бэкапа до допуска пользователей выполните
`npm run retention:preview`, затем `npm run retention:run` внутри контейнера.

Резервные копии с данными теперь хранятся не дольше 90 дней: ежедневные — 14,
еженедельные — 70, ежемесячные — 90. Ручные копии с другими именами скрипт не
удаляет; перед production их нужно отдельно проверить и назначить владельца
за удаление.

Функция развёрнута 3 сентября 2026 после проверенного бэкапа
`daily-20260903-130902`. На отдельной базе `incident_test` прошли 138/138
тестов. Первый запуск `incident-bot-retention.service` завершился успешно:
удалено 0 обращений, 0 файлов и 0 профилей, ошибок нет; повторный preview также
показал ноль объектов. Таймер включён, рабочая база сохранила все 14 обращений,
`npm run doctor` — 35/35, очереди доставки пусты.

### Резервное копирование

Ежедневный проверяемый бэкап запускает systemd-таймер
`incident-bot-backup.timer`. Расписание — `00:30 UTC` (03:30 МСК) плюс
случайная задержка до 10 минут; `Persistent=true` догоняет пропущенный запуск
после включения сервера.

Скрипт `deploy/backup.sh` атомарно создаёт в `/opt/incident-bot/backups/`:

* PostgreSQL custom dump (`incident.dump`);
* архив локальных вложений (`uploads.tar.gz`);
* закрытые копии `.env` и `docker-compose.yml`;
* метаданные и `SHA256SUMS`.

До публикации каталога скрипт проверяет все SHA-256, читает дамп через
`pg_restore --list` и архив через `tar -tzf`. Незавершённый каталог удаляется,
а `latest` указывает только на полностью проверенную копию. Права каталога —
`700`, файлов — `600`.

Хранение: 14 дней ежедневных, 70 дней еженедельных и 90 дней ежемесячных
копий. Недельная копия создаётся по воскресеньям, месячная — первого числа;
они используют hard links и не дублируют неизменившиеся файлы на диске.

Проверка и ручной запуск:

```bash
systemctl list-timers incident-bot-backup.timer --all
systemctl status incident-bot-backup.timer
systemctl start incident-bot-backup.service
journalctl -u incident-bot-backup.service -n 100 --no-pager

cd /opt/incident-bot/backups/latest
sha256sum -c SHA256SUMS
cd /opt/incident-bot
docker compose exec -T postgres pg_restore --list \
  < backups/latest/incident.dump >/dev/null
```

Первый прогон `daily-20260902-112610` успешно проверен: 96 объектов в дампе,
архив вложений читается, приложение осталось `ready`, все 11 обращений на
месте. Локальная автоматизация не заменяет внешнюю копию: до production нужно
настроить отправку проверенного комплекта на отдельный сервер или S3.

## 7. Что решили и почему

Короткие обоснования, чтобы не переоткрывать вопросы заново.

**26 сфер выбираются страницами по 6.** Один список на 27 кнопок — длинная
прокрутка на телефоне. «Не знаю» закреплено сверху на каждой странице: выбор
пользователя по §8 ТЗ всё равно только предположение, маршрут определяет
диспетчер.

**ИИ убран из проекта целиком (сентябрь 2026).** Классификация, AI-черновик и
AI-модерация работали и были измерены (90–98% попадания по сфере, 1.4–2.2 с,
~2 копейки за вызов), но каждый вызов означал отправку текста обращения жителя
стороннему обработчику. Обращение — это персональные данные, и без отдельного
правового основания такая передача недопустима, поэтому выключением флага
ограничиваться не стали: удалён код (`src/ai/`), зависимость на SDK моделей,
переменные `AI_*` и столбцы `ai*` в БД. Возвращать имеет смысл только с моделью
в контуре заказчика либо с согласием заявителя и договором с обработчиком;
предыдущая реализация лежит в git, в коммите до удаления.

**Отчёты — кнопками.** `/report` без аргументов показывает периоды; ручной ввод
принимает `01.08.2026 - 10.08.2026` в любом написании. Прежний синтаксис
(`/report 7d`, ISO-даты) сохранён, чтобы не ломать скрипты и привычки.

**Права проверяются при нажатии, а не при показе кнопок.** Карточка остаётся в
истории чата, нажать её может кто угодно позже — поэтому факт существования
кнопки ничего не разрешает.

**Сфера без чата скрыта от диспетчера, но это не ошибка в доктора.** Это
состояние внедрения; если считать его ошибкой, доктор будет вечно красным и
перестанет что-либо значить.

# Подтверждённые изменения комплекта r2

Проверен именно `Na-svyazi-region40-full-2026-09-30.zip`, SHA-256 `9b524d0140dac26b903e2cf889afa4b38cbcb0adb221408146c90657f847b553`, включая внутренние SHA256SUMS. Не изменять этот архив.

## Что было не так

- В `project/.env.example` отсутствовали POSTGRES_USER, POSTGRES_DB, POSTGRES_PASSWORD. Compose молча использовал стандартные значения. При этом START-HERE уже предписывал добавить их: инструкция и шаблон были несогласованы.
- NODE_ENV/LOG_PRETTY в шаблоне были ориентированы на разработку. WEBHOOK_AUTO_REGISTER=true расходился с требованием установочного check env=false. То же рабочее значение true было в отдельно переданной точной копии серверного `.env`; сама копия не являлась установочным шаблоном.
- Проверка трёх режимов выдавала общую строку без фактических значений. Для ошибок Prisma/пустой базы check database скрывал причину общей фразой. Разработчик подтвердил: после восстановления дампа проверка прошла.
- Старый автоматический прогон проверял восстановление в изолированном PostgreSQL, но не проверял пароль по TCP (использовался trust). В r2 отдельный smoke-тест создаёт БД с паролем, подключается из app по сети Compose и проверяет реальный отказ при неправильном пароле.

## Что НЕ было ошибкой полного архива

- Внутри действительно `data/database.dump`; START-HERE уже ставил pg_restore перед check database. Путаница с именем возникла в переписке. Уточнены явные этапы и диагностика пустой базы, дамп не менялся.
- Требование пароля от 20 символов и набор символов уже были в таблице START-HERE до запуска PostgreSQL, но отсутствовали в шаблоне и обнаруживались пользователем слишком поздно. Сейчас повторены возле POSTGRES_PASSWORD и перед первым запуском. Это политика комплекта/подстановки URL, не минимальная длина, навязанная PostgreSQL.
- Ручной Bearer был ошибкой команды из переписки. MAX SDK 0.2.5 в приложении использует `Authorization: token` и адрес `https://platform-api2.max.ru`. Клиент не менялся, TLS не отключался.
- Архив обновления предполагал сохранение данных и не мог восстановить удалённую установку. Полный комплект предназначен для чистой установки; теперь выбор сценария стоит в начале инструкции.

## Границы редакции

Код приложения, зависимости, Dockerfile, основной Compose, схема/миграции и файлы data/ не меняются относительно соответствующей основы. Меняются шаблоны, документация, отдельный пассивный check и инструменты воспроизводимой сборки/тестирования комплекта. `.env` с действующими секретами, дамп и вложения в Git не добавлять.

`check connection` проверяет только подключение и подходит после запуска. `check database` сверяет точный исходный снимок до запуска приложения; расхождения в рабочей БД нельзя исправлять повторным импортом старого дампа.

## Воспроизводимые проверки

Локально: `node --test deploy/handover/check.test.cjs`. Проверяются коды, переключатели, пустая/неполная схема и отсутствие секретов в сообщениях об ошибках, в том числе MAX с подменёнными ответами.

Сборка из закоммиченного состояния:

```bash
python3 tools/build_handover_revision.py --previous /path/to/Na-svyazi-region40-full-2026-09-30.zip --out /path/to/r2
```

На тестовом Linux с Docker/Compose v2:

```bash
node tools/handover-smoke.cjs /path/to/r2/Na-svyazi-region40-full-2026-09-30-r2.zip /path/to/NEW-isolated-test-directory
```

Smoke-тест собирает образ из упакованного project/, создаёт отдельный Compose-проект с внутренней сетью и без опубликованных портов, проверяет настройки, пустую БД, импорт именно data/database.dump, uploads, сверку 26 таблиц, миграции, неверный пароль, неполную схему, изменённые данные и недоступный PostgreSQL. Тестовая база/тома принадлежат только уникальному handover-smoke-* проекту и убираются в конце. Рабочие базы не используются. Приложение/очереди, Caddy и MAX-вебхуки не запускаются. Образы и слои сборки могут браться из локального кэша; это не проверка скачивания всего набора на машине без Интернета.

После успешного smoke-теста сборщик принимает `--acceptance /path/to/acceptance-result.json` и добавляет отчёт в итоговый архив. Контрольные суммы данных и скрипта, а также коммит в отчёте сверяются с выпускаемой редакцией. Сумма кандидатного ZIP в отчёте отличается от финальной, поскольку в финальный ZIP добавлен сам отчёт.

Текущую установку Минцифры ради этой редакции не повторять. Они восстановили дамп и прошли check database; продолжать начатый запуск. Реальные права нового бота, его HTTPS/вебхук, закрепления и живой пользовательский сценарий проверяются на их стороне в согласованное время.

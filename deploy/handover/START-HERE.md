```bash

# Восстановление разрешено только в пустую БД. ON_ERROR_STOP обязателен.
dc exec -T postgres sh -c 'exec psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
DO $$ BEGIN
 IF EXISTS(SELECT 1 FROM pg_tables WHERE schemaname NOT IN ('pg_catalog','information_schema'))
 THEN RAISE EXCEPTION 'Database is not empty. Preserve existing data and stop.'; END IF;
END $$;
SQL
dc exec -T postgres sh -c 'exec pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --no-privileges --exit-on-error --single-transaction' < "$PACKAGE/data/database.dump"
```

## 4. Новый бот — проверки ДО запуска

Проверка `check identity` использует штатный SDK проекта: API **https://platform-api2.max.ru**, заголовок **Authorization: сам_токен**, без Bearer. HTTP 401 в ручной команде с Bearer не доказывает неправильный токен. Для диагностики не нужны curl с токеном в аргументах или вывод полных ответов; используйте check identity. TLS не отключать. `MAX_AUTH_401` указывает на отказ авторизации, `MAX_ACCESS_403/404` — доступ/права, `MAX_TEMPORARY_*` — временный ответ, `MAX_TLS/MAX_NETWORK` — сертификаты/сеть.

Добавьте **вашего** бота во все 55 рабочих чатов: распределение, 52 профильных, согласование, аналитика. Нужны администратор, отправка сообщений, чтение истории/участников, закрепление панелей и редактирование собственных сообщений. Права людей и названия чатов не менять. Сотрудники и жители должны открыть личный диалог именно с НОВЫМ ботом и нажать «Начать»/`/start`; старый личный диалог не переносится. Для сотрудников доступ к рабочим действиям определяется ролями и членством, `/work` открывает личную рабочую панель. Массовых личных уведомлений о переезде не запускаем.

Проверка требует отсутствия подписок до запуска, проверяет администратора/отправку и доступность истории панелей. Если история слишком длинная или права отсутствуют, запуск откладывается до разбора. Новый бот не будет использовать старые ID из `handover_archive`. Старый бот выключен, его кнопки не обслуживаются; после запуска администратор чата отдельно проверяет старые копии и при необходимости убирает их, не затрагивая карточки жителей. Не поручайте новому боту редактировать сообщения старого.

Теперь обработчики уже запущены, очереди создают/обновляют панели. Дождитесь готовности HTTPS (сертификат Caddy может потребовать время), проверьте `https://ВАШ-ДОМЕН/health` и все три PDF по `/documents/`. `/ready` проверяется внутри контейнера: штатный Caddy не публикует этот маршрут.

Только после восстановления БД, проверки нового bot ID и готовности HTTPS. WEBHOOK_AUTO_REGISTER оставляем false; регистрацию выполняет следующая явная команда с вашим токеном:

```bash
dc exec -T app node dist/scripts/register-webhook.js
dc exec -T app node dist/scripts/webhook-info.js
dc exec -T app node dist/scripts/doctor.js
# Через 1–2 минуты штатного обновления панелей:
check panels "$NEW_BOT_ID"
dc exec -T postgres sh -c 'exec psql -X -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT status,count(*) FROM "InboundUpdate" GROUP BY status;
SELECT status,count(*) FROM "OutboundMessage" GROUP BY status;
SQL
dc ps
dc logs --since 10m --tail 150 app caddy
```

Нужны health/ready=200, ваш ID/URL вебхука, доступные документы, 54 панели с совпадающими ID/автором/закреплением и ожидаемыми кнопками. Плановые задания обновления панелей допустимы; зависшие PROCESSING/SENDING и FAILED требуют разбора. `doctor` выполнять **без `--send`**. Живой прогон кнопок, телефона и подачи сообщения этими проверками не заменяется: отдельно провести согласованный тест, не отклонять рабочие сообщения ради проверки. Секреты и содержимое пользовательских сообщений из журналов в переписку не копировать.

## 7. Если запуск не удался

Не запускайте старого бота. На новой установке сначала остановите приложение и сохраните всё, что успело появиться:

```bash
dc stop -t 75 app
APP_ID=$(dc ps -a -q app)
test -n "$APP_ID"
docker update --restart=no "$APP_ID"
FAILBACK="$BACKUP/after-failed-start-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir "$FAILBACK"
dc exec -T postgres sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$FAILBACK/database.dump"
dc run --rm --no-deps -T --entrypoint sh app -c 'tar -czf - -C /app/data/uploads .' > "$FAILBACK/uploads.tar.gz"
cp -p .env "$FAILBACK/env"
dc logs --no-color --tail 500 app > "$FAILBACK/app.log"
# Проверить ID/URL нового бота; при необходимости остановить доставку на него:
dc run --rm --no-deps -T --entrypoint node app dist/scripts/webhook-info.js
dc run --rm --no-deps -T --entrypoint node app dist/scripts/delete-webhook.js
```

Последняя команда удаляет подписку URL из ВАШЕГО `.env`; этот URL уже проверен обязательной предварительной проверкой. PostgreSQL и тома не удалять. Базу `database-before-start.dump` не восстанавливать поверх текущей: после запуска могли появиться сообщения, события и ID новых панелей. Сначала разобраться со свежим снимком и очередями. У чистой установки нет прежнего рабочего образа для автоматического отката на старую версию: сохранённый образ позволяет повторно развернуть именно проверенную сборку после устранения причины, сохраняя текущие данные. Возврат на другой код/бот требует отдельной сверки и согласования.

Пакет содержит реальные данные и ID сотрудников; передавать напрямую разработчику по согласованному защищённому каналу, не публиковать в GitHub. Наших токена, пароля БД, секрета вебхука и рабочего `.env` внутри нет.

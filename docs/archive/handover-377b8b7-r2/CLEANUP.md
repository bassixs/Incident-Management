# Отдельная очистка тестовых сообщений — только по явному решению

Использовать только исправленный пакет r2 и планы version=2. Старые apply/retry
не выполнять. Для замены инструментов и разбора уже запущенной старой очистки
см. PATCH-TOOLS.md. Новый инструмент отказывает в исполнении планов version=1.

Эта процедура НЕ выполняется обновлением. Она удаляет все имеющиеся Incident,
ответы, уточнения, историю и оценки, связанные рабочие сессии/личные рабочие
карточки и текущие черновики жителя. Сохранены User, права, Category,
ResponsibleGroup, настройки, рабочие панели и IncidentCounter.
Не использовать `/clear_users`. `/clear_data` не удаляет карточки MAX и не заменяет
эту процедуру. Скрипт пакета не запускает index.js и не отправляет сообщения.

Перед началом убедиться, что все записи действительно тестовые. Прекратить ввод
пользователей, остановить все конкурирующие экземпляры/cron. Подписку вебхука
не удалять. Во время остановки новые запросы должны получать ошибку (не ложный
200), чтобы MAX мог повторить доставку. Не держать остановку неопределённо долго.

## 1. Новая резервная копия после живого прогона

Переменная PKG — полный путь к распакованному проверенному пакету обновления.

```bash
set -euo pipefail
umask 077
cd "$HOME/incident-transfer/project"
dc () { docker compose -p incident-bot -f docker-compose.yml "$@"; }
CLEANBACK="$HOME/incident-before-cleanup-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -m 700 "$CLEANBACK"
dc stop -t 75 app
APP=$(dc ps -a -q app)
test -n "$APP"
test "$(docker inspect "$APP" --format '{{.State.Running}}')" = false
dc exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "$CLEANBACK/database.dump"
dc run --rm --no-deps -T --user root --entrypoint tar app -czf - -C /app/data/uploads . > "$CLEANBACK/uploads.tar.gz"
cp -p .env "$CLEANBACK/runtime.env"
dc exec -T postgres pg_restore --list < "$CLEANBACK/database.dump" > "$CLEANBACK/database.list"
tar -tzf "$CLEANBACK/uploads.tar.gz" > "$CLEANBACK/uploads.list"
(cd "$CLEANBACK" && sha256sum database.dump uploads.tar.gz runtime.env > SHA256SUMS)
```

Ожидается успешная остановка и читаемые дамп/архив. При ошибке ничего не удалять.
Для S3 этот порядок не применим без отдельной копии bucket. Сохранить путь CLEANBACK.

## 2. Только предварительный просмотр

```bash
dc run --rm --no-deps -T --user root -e LOG_LEVEL=silent -v "$PKG/config:/ops:ro" -v "$CLEANBACK:/review" --entrypoint node app /ops/cleanup-test-data.cjs plan /review/plan.json
python3 - "$CLEANBACK/plan.json" <<'PY'
import json,sys
p=json.load(open(sys.argv[1]))
print('Сообщения:', ', '.join(p['codes']))
print('Состав:',p['counts'])
print('Неразобранные задания:',p['blockers'])
print('Отпечаток:',p['fingerprint'])
PY
```

План не изменяет БД и MAX. plan.json содержит ID выбранных записей, известные
ID сообщений MAX (включая operation.messageIds) и ключи файлов; текстов сообщений и телефонов нет. Проверить
список номеров, активные сообщения, все выбранные черновики и counts.

`blockers` должен быть пустым. Если остался входящий PENDING/PROCESSING либо
исходящее задание с вложением (например, отчёт), которое нельзя достоверно
связать с выбранными данными, очистка блокируется. Нельзя
удалять всю очередь. Отложить очистку, разобрать конкретное задание/дождаться
штатной обработки, затем снова остановить приложение, снять новую копию и план.
Если передумали, `dc start app`, затем `bash "$PKG/config/wait-ready.sh"`;
план не исполняется автоматически.

## 3. Явное подтверждение и выполнение

Выполнить ТОЛЬКО после проверки плана и копии; ранее согласованное «обновить»
само по себе не запускает этот шаг. Скопировать отпечаток из своего plan.json.

```bash
test "$(docker inspect "$APP" --format '{{.State.Running}}')" = false
read -r -p 'Введите отпечаток подтверждённого плана: ' CONFIRM
dc run --rm --no-deps -T --user root -e LOG_LEVEL=silent -e CLEANUP_APP_STOPPED=YES -v "$PKG/config:/ops:ro" -v "$CLEANBACK:/review" --entrypoint node app /ops/cleanup-test-data.cjs apply /review/plan.json "$CONFIRM"
```

Перед транзакцией повторно считается состав. Если он изменился — удаления нет,
нужен новый план. Сервисные очереди панелей и недельных отчётов не удаляются.
Связанные исходящие задания удаляются; обработанные входящие сохраняют ключ
идемпотентности, но выбранные payload очищаются и статус становится PROCESSED:
повторная доставка того же события не восстанавливает удалённое.
Отдельные файлы, на которые ещё ссылаются сохранённые сессии/задания, не удаляются.

До удаления из БД в той же транзакции сохраняется служебный журнал
`maintenance.package-cleanup:<отпечаток>`. После commit создаётся также
plan.json.journal.json. Сначала удаляются записи БД и связанные задания,
затем известные сообщения MAX и файлы. MAX-карточка удаляется только после
проверки автора (именно текущий бот), исключения панелей и защитных ID.
HTTP 404 при чтении или удалении остаётся неоднозначным: ID сохраняется
в remainingMessages. При ошибке чтения автор не подтверждён и DELETE не вызывается.
Удаление подтверждается только явным success=true от DELETE. Стадия, безопасный
код и время попытки записываются в messageResults. Содержимое сообщений и сырые
ответы API в журнал не попадают. Иной автор и защита панели тоже сохраняют ID
для ручной проверки. Неудалённые файлы остаются в remainingFiles.

Нулевые remainingMessages допустимы только после подтверждённых удалений всех
запланированных карточек. Неоднозначный 404 сохраняет ненулевой остаток даже после
повтора. Не исключать такой ID из плана: сверить журнал и провести ручную проверку.
После всех подтверждённых операций ожидаются databaseDeleted=true,
remainingMessages=0 и remainingFiles=0.
Код 2 означает остатки, а не откат транзакции. При сбое питания/сети данные
журнала остаются в БД. Тот же план и отпечаток повторно выполняются безопасно:

```bash
dc run --rm --no-deps -T --user root -e LOG_LEVEL=silent -e CLEANUP_APP_STOPPED=YES -v "$PKG/config:/ops:ro" -v "$CLEANBACK:/review" --entrypoint node app /ops/cleanup-test-data.cjs retry /review/plan.json "$CONFIRM"
```

Повторять при остановленной обработке. Не удалять plan/journal/копию. Если MAX
недоступен длительно, можно после фиксации остатков вернуть приложение и
согласовать отдельное окно повтора: прежние задания доставки уже убраны, сами
данные не вернутся. Счётчик номера остаётся прежним. Панели сохраняют ID и при
штатном запуске обновляют содержимое под пустую очередь.

## 4. Проверить и вернуть обработку

```bash
dc run --rm --no-deps -T -e LOG_LEVEL=silent -v "$PKG/config:/ops:ro" --entrypoint node app /ops/snapshot.cjs --offline > "$CLEANBACK/after-cleanup.json"
dc start app
bash "$PKG/config/wait-ready.sh"
dc run --rm --no-deps -T -e LOG_LEVEL=silent -v "$PKG/config:/ops:ro" --entrypoint node app /ops/snapshot.cjs > "$CLEANBACK/after-start.json"
```

wait-ready.sh ограничивает ожидание готовности после запуска 120 секундами.
При ошибке не продолжать процедуру до разбора состояния и журналов приложения.

Проверить нулевые Incident/ответы/связанные черновики до запуска, сохранность
пользователей/групп/тем/счётчика, прежние ID и закрепления панелей после запуска.
Не сравнивать полный SystemSetting по хешу: добавлен журнал очистки.
Новые события, поступившие уже после очистки, являются новым вводом.

## Границы очистки и отката

Скрипт обрабатывает ID, сохранённые в базе, JSON-данных сессий/истории и outbox.
Старые копии/фрагменты MAX, чьи ID ранее потеряны, он не объявляет удалёнными.
После выполнения вручную просмотреть рабочие чаты по номерам из плана; старые
копии подтверждать по автору и содержимому, исключая панели. Удалить их правами
администратора отдельно и записать результат. Нельзя автоматически объявить
полностью чистыми чаты без такого просмотра. Чужие сообщения/исходные сообщения
жителей не удаляются этим инструментом. Медиа по max-photo: — ссылка MAX, не
локальный файл; удаление сообщения не является обещанием физического удаления
файла со всей инфраструктуры MAX.

Откат приложения не восстанавливает удалённые сообщения MAX. Восстановление БД
после очистки — отдельная операция с остановкой, сохранением текущего состояния
и сверкой новых данных/несуществующих MAX ID. Нельзя просто вернуть старый дамп
и запустить его очереди: это может повторно доставить сообщения. Поэтому
автоматической команды восстановления удалённого в эту инструкцию не включено.

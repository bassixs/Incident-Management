# Только замена инструментов для уже обновлённого приложения

Редакция **update-377b8b7-r2** исправляет пакет, не приложение. Код приложения
остаётся 377b8b7837037e8aaad4e98530d02588f086edb2. Пересборка, повторная установка,
восстановление БД, изменение .env, вебхука или перезапуск приложения для замены
этих файлов не нужны. Это не исторический full-r2 для чистой установки.

Прежний ZIP сохраняется, но его cleanup apply/retry больше не использовать.
Если старый процесс очистки ещё выполняется, сначала остановить именно этот
процесс/одноразовый контейнер, сохранить план и журнал, дождаться завершения
его запросов. Не запускать два инструмента одновременно. Не останавливать
базу и не удалять контейнеры/тома для замены инструментов.

## 1. Проверить и распаковать новую редакцию отдельно

```bash
set -euo pipefail
umask 077
cd "$HOME"
sha256sum -c Na-svyazi-region40-update-377b8b7-r2.zip.sha256
PATCH_STAGE=$(mktemp -d "$HOME/incident-tools-r2.XXXXXX")
unzip -q Na-svyazi-region40-update-377b8b7-r2.zip -d "$PATCH_STAGE"
PKG="$PATCH_STAGE/Na-svyazi-region40"
(cd "$PKG" && sha256sum -c SHA256SUMS > "$PATCH_STAGE/checksums.log")
```

Ожидается успешная проверка сумм. При ошибке ничего не заменять. Папку project/
из нового пакета в действующую установку не копировать, если приложение уже обновлено.

## 2. Установить инструменты отдельно, сохранив прежние

```bash
TOOLS="$HOME/incident-transfer/config/update-377b8b7-r2"
test ! -e "$TOOLS"
mkdir -m 700 "$TOOLS"
cp -p "$PKG/config/"* "$TOOLS/"
cp -p "$PKG/START-HERE.md" "$PKG/CLEANUP.md" "$PKG/PATCH-TOOLS.md" "$TOOLS/"
printf '%s\n' "$TOOLS" > "$PATCH_STAGE/installed-tools-path.txt"
cd "$HOME/incident-transfer/project"
dc () { docker compose -p incident-bot -f docker-compose.yml "$@"; }
dc exec -T app node --check - < "$TOOLS/cleanup-test-data.cjs"
bash -n "$TOOLS/wait-ready.sh"
```

Ожидается код 0. `node --check` только проверяет синтаксис, не выполняет очистку.
Если app остановлен, эту команду можно заменить на
`dc run --rm --no-deps -T --entrypoint node app --check - < "$TOOLS/cleanup-test-data.cjs"`;
бот при этом не запускается. Если TOOLS уже существует — не перезаписывать вслепую,
сверить его файлы с новой проверенной распаковкой.

Можно продолжать использовать исправленные START-HERE.md/CLEANUP.md прямо из
PKG: их `/ops` всегда монтирует `$PKG/config`, то есть новую редакцию. Если
используете установленный TOOLS, замените в командах только
`-v "$PKG/config:/ops:ro"` на `-v "$TOOLS:/ops:ro"`, а ожидание готовности — на
`bash "$TOOLS/wait-ready.sh"`. Запускать helper из ~/incident-transfer/project/.
Нельзя оставить в командной строке путь к config из старой распаковки.

wait-ready.sh ждёт до 120 секунд. Проверяются оба HTTP endpoint из контейнера;
каждый запрос имеет тайм-аут, недоступный контейнер не обрывает первую попытку.
При неготовности helper возвращает 1 с понятным сообщением. После этой ошибки
остановить процедуру, проверить контейнер/логи, при необходимости выполнить
описанный откат приложения. Сам helper ничего не запускает и не перезапускает.

## 3. Планы и журналы очистки

- Если старая очистка НЕ выполнялась: сохранить старый план как исторический,
  затем по исправленному CLEANUP.md остановить конкурирующую обработку,
  сделать актуальную копию и создать новый план version=2. Проверить состав и
  подтвердить новый отпечаток. Не менять version/fingerprint вручную.
- Если старый apply/retry УЖЕ выполнялся: прежние нулевые остатки нельзя считать
  доказательством удаления. Сохранить старый plan.json, его journal.json и
  соответствующую запись SystemSetting. Сопоставить изначальный messageIds с
  журналом и проверить карточки в MAX. Пропущенные operation.messageIds могли
  исчезнуть вместе с OutboundMessage; их искать в резервной копии в отдельной
  изолированной БД либо в ранее сохранённой выгрузке задания. Рабочую БД ради
  этого не восстанавливать. Такие результаты требуют отдельного согласованного
  плана ручной очистки; новый пустой план не заменяет аудит старого запуска.

Инструмент r2 отказывает в apply/retry планов и журналов version=1. Уже потерянные
ID он не выдумывает и автоматически «исправленными» старые остатки не объявляет.

Для новых запусков ID из operation.messageIds сохраняются в плане и в журнале
одной транзакцией с удалением задания. GET 404 и DELETE 404 остаются в
remainingMessages с разными стадиями в messageResults. Только явный success=true
от DELETE выводит ID из остатка. После потери ответа даже реально удалённая
карточка может остаться неразрешённой — нужна ручная проверка, а не ложный ноль.

Откат приложения не восстанавливает сообщения MAX. Никакая очистка при замене
инструментов не запускается автоматически.

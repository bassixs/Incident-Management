Проверка объединения с main после PR №6 приведена ниже в разделе от 03.10.2026.

## Что ожидает интерактивный переход

| Переход | Обязательное ожидание | Фоновая работа |
|---|---|---|
| Открыть распределение, сменить тему | Транзакция закрепления/темы; сохранение следующего экрана через `send` | Обновление прежних карточек |
| Взять из очереди распределения | Транзакция закрепления и создания задания карточки | Доставка карточки и обновление панели |
| Начать согласование или возврат на доработку | Транзакция закрепления, сохранение служебной сессии и следующего экрана | Обновление копий рабочих карточек |
| Взять/освободить сообщение исполнителя; перераспределить | Транзакция состояния, закрепления и заданий | Обновление карточек и уведомлений |
| Назначить исполнителя, отклонить сообщение | Существующие проверки, подтверждения, транзакция; адресная отправка, если она требуется текущему пути | Остальные обновления outbox |
| Открыть рабочую копию/обновить панель | Создание или переактивация задания в БД | Доставка и редактирование |

`send()` сохраняет сообщение и по возможности отправляет сразу. При занятом
адресате возвращается результат `queued`: следующий экран уже записан в БД,
а не оставлен только в памяти. Обязательный предшественник того же адресата
не обходится. Подтверждение кнопки не означает, что экран уже отрисован в MAX.

`wake()` вызывается после завершения транзакции. Он объединяет повторные сигналы
и пробуждает единственный worker, в том числе при свободных местах на фоне
постороннего медленного запроса. Освобождение занятого адресата и успешное
завершение доставки пробуждают готовые задания. Невыполненный предшественник
с retry/backoff не вызывает бесконечный повторный проход. Пустой опрос
очереди распределения и повторное получение своего закрепления без новой
карточки не подают сигнал worker: они не создают исходящих заданий. Интервал 5 секунд
сохранён как страховка, в частности для заданий из других фоновых сервисов,
пропущенного сигнала и наступившего срока повторной попытки.

Нет изменения параллелизма, ограничений MAX, порядка по адресату и числа
повторных попыток. `flush()` сохранён для технического ожидания всей очереди
и тестов; интерактивные переходы его не ожидают. Остановка завершает текущую
работу и оставляет неотправленные записи следующему запуску. Миграции нет.

До фонового редактирования старая клавиатура может оставаться видимой.
Права, текущее состояние, владелец закрепления, версия ответа и токен
подтверждения проверяются обработчиками по БД; изменение не обходит эти проверки.

## Безопасные измерения

Структурированные записи `module=latency`, `msg="latency measurement"`:

- `inbox-start`: `inboxId`, `receivedAt`, `waitMs`, номер попытки. Получение
  отсчитывается от входа в `reserve`, включая ожидание приёма по пользователю;
  начало обработки — перед захватом записи inbox.
- `callback-ack`: результат запроса подтверждения, его длительность и возраст
  события. Не содержит callback payload или текста уведомления.
- `screen-created`: созданный через `send` `outboxId`; возраст записи.
- `outbox-start`: `outboxId`, номер попытки, ожидание с момента готовности,
  полный возраст записи. Позволяет восстановить время создания также для
  заданий из бизнес-транзакций. Переиспользуемые панели сохраняют исходную дату
  создания; `waitMs` учитывает `nextAttemptAt` и подходит для текущего прохода.
- `outbox-sent`: длительность выполнения попытки и возраст записи до завершения.
- `max-request`: случайный `requestId`, статическое имя метода, номер попытки,
  `rateWaitMs` отдельно от `requestMs`, успех либо HTTP-статус ошибки.

Техническая связь inbox → outbox хранится в поле `trace` существующего JSON
задания и сохраняется при повторе/перезапуске. Разрешены только UUID и время;
поля произвольного объекта не копируются в журнал. Старые задания без trace
обрабатываются штатно и связываются по `outboxId`. Периодические задания могут
не иметь `inboxId`. Измеряются вызовы через MaxClient и существующие прямые
проверки членства через `observeMembership`; для членства политика повторов и
ограничения остались прежними. Остальные прямые вызовы SDK не покрываются
этой инструментализацией.

Нет текстов, телефонов, токенов, URL вложений и полных payload в новых замерах.
Успешный запрос MAX — серверное подтверждение, а не отрисовка на устройстве.
Скорость сети, самого MAX, backoff и обязательные предшественники одного
адресата по-прежнему могут задерживать экран. Неоднозначная сетевая ошибка
после принятого MAX сообщения сохраняет прежние ограничения доставки;
универсальная гарантия exactly-once для MAX не заявляется.

## Воспроизведение

`tests/integration/callback-latency.test.ts` запускает реальные приём inbox и
обработчики кнопок с отдельной PostgreSQL и имитацией MAX. Посторонний запрос
задерживается на 5000 мс; следующий экран должен отправиться до его завершения.
Повтор события не создаёт второе закрепление. Для сравнения этот же тест
копируется в исходный коммит и запускается с `LATENCY_BASELINE=1`; этот режим
ожидает старую задержку и не используется при проверке исправленной версии.

Для повторения нужны зависимости из lock-файла и отдельная PostgreSQL,
указанная в `TEST_DATABASE_URL`. Интеграционные фикстуры очищают тестовые таблицы;
основную базу указывать нельзя. Все вызовы MAX в этих сценариях имитируются.

```sh
npm run typecheck
npm run build
npm test -- tests/unit/latency.test.ts tests/integration/callback-latency.test.ts tests/integration/parallel-outbox.test.ts tests/integration/distribution-queue.test.ts
```

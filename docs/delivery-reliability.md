# Повторная и частичная доставка

Изменение относительно `8dcfa330183e47551446d10cabbd3b493a42ea0b`.
Схема Prisma и миграции не меняются. Рабочие данные не преобразуются при запуске.

## Запасная карточка после недоступного фото

Для `photo-recovery:<originalId>` проверяется исходное задание: обращение,
адресат, тип SECTOR_CARD и цикл назначения `sector-card:…`. Совпадения одного
чата недостаточно: возврат в тот же чат после перераспределения — другой цикл.
Проверка повторяется перед отправкой, после ожидания ограничителя MAX и при
сохранении результата. Устаревшая карточка до отправки получает FAILED с
причиной, а не фиктивный SENT.

Если назначение изменилось уже во время запроса MAX, подтверждённый MID
сохраняется, но карточка не становится карточкой нового назначения. Надёжное
задание обновления снимает прежние действия. Отменить уже принятый MAX запрос
нельзя; серверные проверки прав и состояния остаются обязательными.

Исходное задание с недоступным фото остаётся FAILED. Запасной текст не означает
полную доставку исходных вложений. Уже подтверждённые части и ссылки на исходные
вложения сохраняются. Недоступные фото не вырезаются из обращения; сохранённая
логика предлагает сотруднику восстановить вложения. Ранее ошибочно отмеченные
SENT без MID автоматически не переотправляются: они требуют отдельного аудита.

## Ручной повтор ответа

`/resend INC-…` сохраняет проверку полномочий, доступности рабочего чата и
видимости обращения. Повтор допускается только для последней согласованной,
ещё не доставленной версии ответа у RESOLVED. Перевод FAILED → PENDING
выполняется явно, под блокировкой обращения, для точного `answer:<answerId>`
и адресата-жителя. Обычная дедупликация FAILED не возобновляет.

PENDING сохраняет backoff, SENDING — действующую обработку. Доставленный ответ
не отправляется заново. Служебные задания, включая намеренно снятые приветствия,
не затрагиваются. Возврат на доработку или новая версия исключают отправку
прежнего ответа. Уже начатый сетевой запрос может завершиться после смены версии;
его MID сохраняется, но deliveredAt и история доставки актуального ответа не
подтверждаются этим результатом.

В историю добавляется ANSWER_DELIVERY_RETRY_REQUESTED: технические ID, автор
команды, время, прежнее число попыток и прежняя ошибка. До успешного завершения
прежняя ошибка сохраняется и в задании. Эти диагностические данные не следует
публиковать. Сотрудник получает сообщение об очереди только для продолжающейся
доставки; окончательный отказ показывается как требующий проверки причины.

## Подтверждённые части

Для обычных сохраняемых отправок в OutboundMessage.payload записывается
`deliveryProgress = { version: 1, planHash, totalParts, mids }`. Это SHA-256 плана
и последовательность MID, подтверждённых MAX и сохранённых в БД. В плане учтены
текст, подпись, клавиатура, адресат и ссылки на вложения. firstMessageId и
keyboardMessageId сохраняются отдельно. Каждая запись проверяет владельца
попытки/аренды; прогресс не перезаписывает работу другого обработчика.

После ошибки, перезапуска и ручного /resend продолжение начинается со следующей
неподтверждённой части. SENT, deliveredAt и ANSWER_SENT появляются только после
всех частей и проверки актуальности ответа. Несовпадение плана прекращает повтор
с явной ошибкой DELIVERY_PROGRESS_MISMATCH, а не начинает отправку с нуля.
Порядок по адресату, backoff и лимиты MAX сохранены. Операции обновления панелей
и карточек имеют собственную логику восстановления; этот формат не заменяет её.

Если MAX принял часть, но ответ с MID потерялся, или запись подтверждения в БД
не удалась, локально нельзя доказать доставку. Повтор такой части может создать
дубль. Изменение устраняет повтор **сохранённых подтверждённых** частей и не
обещает exactly-once на границе сети и БД.

## Совместимость и будущее обновление

Старые задания без deliveryProgress начинают обычную доставку. Все исходные
вложения, в том числе исторические наборы больше четырёх фото, сохраняются.
Миграции, очистка очереди, массовый retry и ручное выставление SENT не нужны.

Откат на `8dcfa330` с текущей БД **не является безусловно безопасным**. Старое
приложение игнорирует deliveryProgress и может повторить уже подтверждённые
части PENDING/SENDING, в том числе при последующем повторе FAILED. Старое
приложение также возвращает прежние дефекты запасной карточки и /resend.
В изолированной проверке прежний обработчик с сохранённым v1-префиксом
повторно отправил этот префикс: ограничение подтверждено запуском старого кода.

Перед будущей установкой нужны свежая проверенная копия, сохранённый образ,
штатная остановка одного app, финальный снимок и сверка ID/состояний после
запуска с текущей БД. Другие сервисы и webhook не требуют изменения.

Перед откатом остановить app и проверить незавершённый прогресс только чтением:

```sql
BEGIN READ ONLY;
SET LOCAL statement_timeout = '5s';
SELECT id, status, "trackingType", "firstMessageId",
       payload->'deliveryProgress'->>'version' AS progress_version,
       payload->'deliveryProgress'->>'totalParts' AS total_parts
FROM "OutboundMessage"
WHERE status <> 'SENT' AND payload ? 'deliveryProgress';
COMMIT;
```

При наличии строк обычный откат блокируется до отдельного решения по каждому
заданию. Предпочтительно завершить доставку новой версией; при невозможности
нужен совместимый обработчик прогресса, а не удаление JSON или старый дамп.
FAILED с частями тоже учитывать, даже если прямо сейчас он не повторяется.
Снимок БД поверх новых сообщений при откате не восстанавливать.

После обновления отдельно сверить очереди, связи/MID карточек, актуальные ответы
и полную доставку вложений. Проверка здоровья не доказывает доставку. Изменение
готовится для ревью; рабочий сервер и живой MAX при проверках не используются.

## Проверки

На исходном дереве `8dcfa330` все три проверки BASE-1/2/3 воспроизвели дефекты:
запасная карточка без MID, отсутствие ручного повтора и дублирование первого
фрагмента после перезапуска. Исправленная версия проходит все 28 сценариев
`tests/integration/delivery-reliability.test.ts`, включая имитацию потери ответа
MAX, окончательного FAILED, переназначения во время запроса и backoff 429.

Проверки выполняются на отдельной локальной PostgreSQL с подставным MAX:

```sh
npm run typecheck
npm run build
npx vitest run tests/unit
# TEST_DATABASE_URL должен указывать только на отдельную тестовую БД.
# Для foreign-greeting-retirement.test.ts также нужен TEST_PSQL_BIN.
npx vitest run tests/integration/delivery-reliability.test.ts
```

Typecheck и build успешны. Полный unit-набор: 545/545. Тестирование не является
живым прогоном MAX. В двух существующих тестах исправлена подготовка данных:
создан реальный согласованный ответ вместо фиктивных ID; в проверке сохранности
заимствованных файлов исключена преждевременная отметка доставки тестовым
транспортом. Проверки результатов и сохранности данных не ослаблены.

Расширенный интеграционный набор (15 файлов): 212/217, без пропусков.
Пять падений отдельно воспроизведены на неизменённом базовом дереве:

- `delivery-metrics`: расчёт статистики получает нулевую выборку;
- `parallel-photo-flow`: три прежних сценария создания/подтверждения фото;
- `transactional-workflow`: регистрация с подготовленным тестом черновиком
  получает «Черновик уже подтверждён или устарел».

Эти проверки не исключены и не ослаблены; изменение метрик и ActionGuard в
задачу не входит. В одном предварительном прогоне на базе также наблюдалось
падение восстановления регионального ответа; в итоговом расширенном прогоне
оно не повторилось. Четыре первоначальные ошибки запуска `psql` устранены
настройкой **локального тестового окружения**, после чего все 14 проверок
служебных приветствий прошли. Первый общий запуск без итогового отчёта не
засчитывался. Сырые журналы и настройки тестового окружения в репозиторий не
включены.

После финального уточнения отказа по состоянию повторены полный unit-набор
(545/545) и 57 интеграционных проверок доставки, фотографий, карточек и порядка
очереди (57/57); typecheck и build также успешны.

# Синхронизация теста доставки и условия отката

База: `d8dfa7d193e4551a8ea4b5c6e7bfbb43ba5dff94`. Это результат изолированной
проверки и план для отдельного согласования, **не разрешение на установку**.
Runtime, схема, миграции, образы и настройки приложения этим PR не меняются.

## Установленная причина нестабильного теста

В `transactional-workflow` прежний `MaxMessageService` оставался действующим
при создании `restartedWorker`, затем оба оставались при создании `inviteWorker`.
Для фоновой работы не обязательно вызывать `start()`: `send()` и завершение
отправки вызывают `wake()` через `setImmediate`. `afterEach` восстанавливал
моки, но не останавливал эти worker и не ждал их перед следующим TRUNCATE.

`flush()` ждёт drain **своего экземпляра**. Он не является глобальным барьером
для всей БД. При действующей чужой аренде SENDING новый worker корректно
не забирает уведомление. Второй вызов `flush()` ничего в этом не меняет.

Управляемое воспроизведение `delivery-worker-lifecycle.test.ts`:

1. Настоящие сервисы создают прямой региональный ответ; имитация MAX отказывает.
2. Прежний worker получает `wake()`, успешно доставляет ответ и захватывает
   единственное уведомление сотруднику. Ответ на этот запрос удерживается
   Promise-барьером (без sleep).
3. Новый worker выполняет два `flush()`. `deliveredAt` установлен,
   `ANSWER_SENT=1`, уведомление в `SENDING`, attempts=1, подтверждённых
   уведомлений **0** — ровно условие прежнего падения.
4. После освобождения запроса и ожидания прежнего worker уведомление становится
   SENT, подтверждённых уведомлений **1**, повторной доставки ответа нет.

Этот сценарий воспроизведён одинаково на main и прежней вершине `7219464`.
Наблюдаемая ошибка — граница перезапуска и ожидания в тесте. Дефект runtime
из этого сценария не следует: worker не должен ждать чужую аренду бесконечно
или присваивать её себе. Штатный shutdown приложения уже останавливает
производителей и ждёт обработчики и отправки; производственную остановку здесь
не выполняли и её фактический результат не проверяли.

Исправление теста:

- `stop()` + `waitForIdle()` прежнего worker **до** запуска следующего;
- завершение всех созданных worker в `afterEach`, до сброса БД следующего теста;
- ожидание собственных drain, без выключения фоновых wake в этом сценарии;
- барьер перед ACK подтверждает, что `deliveredAt=null`, `ANSWER_SENT=0` и
  успешного уведомления нет; после ACK проверяются единственная история,
  единственное уведомление, неизменность deliveredAt при повторном drain и
  порядок «ответ → оценка → приглашение подписаться».

Ожидания результатов не ослаблены, произвольные задержки и увеличенные тайм-ауты
не добавлены. Отдельное старое падение регистрации черновика в том же файле
к этой причине не относится и этим изменением не исправляется.

## Что проверяет предварительный просмотр

`tools/delivery-rollback-preview.sql` выполняется в REPEATABLE READ READ ONLY,
с `statement_timeout=5s`. Выводит только технический ID, статус, попытки,
аренду, количество частей и классификацию. Нет текстов, телефонов, адресатов,
секретов или полного payload. Ничего не обновляет, не отправляет и не запускает.
Пустой результат означает отсутствие записей outbox, а не доказательство
отсутствия входящих событий или сетевых запросов.

SQL проверяет **структуру** progress, но не пересчитывает planHash. Корректный
внешний вид hash не доказывает соответствие тексту, кнопкам и вложениям. Перед
возобновлением это проверяет совместимый обработчик; неоднозначный ACK или
ошибка сохранения MID также требуют отдельной оценки.

Пример будущего запуска из checkout этого PR, после согласованной остановки
всех обработчиков приложения. Параметры заранее берутся из проверенной
фактической установки; не использовать POSTGRES_DB как выбор рабочей базы:

```sh
DB_CONTAINER='<контейнер PostgreSQL текущей установки>'
WORKING_DB='<имя текущей рабочей базы>'
docker exec -i "$DB_CONTAINER" sh -c '
  export PGPASSWORD="$POSTGRES_PASSWORD"
  exec psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$1"
' sh "$WORKING_DB" < tools/delivery-rollback-preview.sql
```

Команда рассчитана на существующий контейнер с POSTGRES_USER/POSTGRES_PASSWORD;
другой способ авторизации нужно согласовать с фактической конфигурацией.
Не выводить env или URL подключения. Ошибка/тайм-аут/недоступность БД означает
**отсутствие результата проверки**, а не разрешение отката. Результат сохранять
в приватном каталоге администратора; это не материал для GitHub.

## Матрица решения для прежнего 8dcfa330

| Состояние после остановки | Допустимое действие |
|---|---|
| Нет незавершённых отправок; только корректные SENT | Ограничение повторения progress не обнаружено. После остальных проверок ниже допустима замена только app на старый образ с **текущей** БД. Это не доказательство отсутствия других регрессий старого кода. |
| PENDING/SENDING с `0 < mids.length < totalParts` | Обычный откат заблокирован. Исправная совместимая версия продолжает со следующей части; соблюдает backoff/аренду/порядок. Затем повторить preview. SENDING не означает разрешение немедленно переотправить. |
| FAILED с подтверждёнными частями | Обычный откат тоже заблокирован: сейчас повторов нет, но старый ручной или последующий механизм повтора отправит сначала. Сохранить запись, ошибку, прогресс и вложения. Отдельно выяснить причину; адресный повтор — только после её устранения и отдельного разрешения, совместимым обработчиком. Не возобновлять служебные снятые приветствия. |
| Все части подтверждены, но статус ещё PENDING/SENDING/FAILED | Обычный откат заблокирован. Совместимый обработчик сверяет план, владельца попытки, актуальность версии и завершает учёт **без новых отправок этих частей**. deliveredAt/ANSWER_SENT/уведомление создаются транзакционно и идемпотентно. При FAILED требуется отдельное разрешение на возобновление; все ACK сами по себе не разрешают ручной SENT. |
| Неизвестный/испорченный progress или противоречивый SENT | Откат и автоматическое продолжение заблокированы до индивидуальной проверки. Нельзя стирать JSON или считать части доставленными по предположению. |
| Нет progress либо сохранено 0 ACK, но задание не SENT | Требуется проверка: отсутствие MID не исключает принятый MAX запрос с потерянным ответом. Лишь подтверждённо не начатое совместимое задание можно передать старому обработчику. Ошибки/lease/неоднозначный ответ и FAILED рассмотреть по ID; не выполнять общий retry. |

В изолированной БД старый runtime **действительно** повторяет первый фрагмент
для PENDING и просроченного SENDING; для FAILED — после явного тестового
возобновления; при всех ACK повторяет весь текст вместо одного завершения учёта.
Старый runtime не трогает обычный SENT и не возобновляет FAILED сам.
Истечение lease в тестовой фикстуре не заменяет доказательство остановки
прежнего владельца на настоящем сервере.

Известные снятые служебные приветствия без progress сохраняются FAILED с
причиной retirement. Их классификация NO_PROGRESS_REQUIRES_REVIEW требует
сверить назначение и причину, а не возобновить отправку. Подтверждённо снятое
служебное задание без частей само по себе не требует доведения до SENT.

## Конкретная последовательность будущего отката

1. Зафиксировать фактический образ/REV, конфигурацию, mounts, идентичность БД,
   состояние процессов, очередей и резервирования. Проверить сохранённый старый
   образ по digest и схему. Создать свежую копию действующей БД, вложений и
   настроек, проверить восстановление отдельно. Не подключать восстановленное
   приложение к MAX. Подготовить возврат на текущий образ при отказе создания
   контейнера и проверить его на временной конфигурации.
   Учесть, что 8dcfa330 возвращает прежние дефекты photo-recovery и /resend;
   даже при пустой очереди это отдельный риск, требующий принятого решения.
2. Остановить **только app** штатным SIGTERM в пределах заранее проверенного
   grace period; не запускать второй экземпляр. Требуются успешное завершение
   обработчиков/отправок, отсутствие живого процесса и подтверждение shutdown.
   Само истечение тайм-аута, старый lockedAt или отсутствие контейнера в списке
   running не доказывают завершение сетевых запросов. При kill/OOM/нештатном
   завершении зафиксировать неоднозначность, не обходить защитные проверки.
3. После остановки сделать финальный согласованный снимок БД/вложений и
   технический снимок inbox/outbox, ответов, назначений, истории, черновиков и MID.
   Повторить read-only preview на **текущей**, а не восстановленной БД.
   Проверить также оставшиеся PROCESSING inbox и фоновые операции: продолжение
   старой версией должно быть совместимо с их payload и бизнес-состоянием.
4. Применить матрицу. При любом BLOCK не запускать 8dcfa330. Не менять статусы
   SQL-командами ради прохождения проверки. Если новая версия исправна в части
   доставки, отдельным решением вернуть её и дать очереди штатно продолжиться,
   затем повторить остановку/снимок/preview. Глобальный drain production и
   массовый retry здесь не предлагаются: они могут разослать рабочие сообщения.
5. Только если ограничения сняты и прочая совместимость подтверждена — заменить
   образ одного app. БД и все хранилища остаются текущими, runtime.env,
   PostgreSQL, Caddy, webhook и ротация журналов не меняются. Старый дамп не
   восстанавливается. Проверить ограниченным ожиданием health/ready; при
   превышении сначала диагностировать, не пересоздавать контейнер циклически.
6. Сверить исходные ID/связи/вложения с учётом новых штатных событий истории,
   состояния inbox/outbox, актуальные deliveredAt/ANSWER_SENT, успешные
   уведомления по ключам, карточки и закрепления. Особо проверить незавершённые
   ответы и файлы. Health/ready не доказывают доставку и отсутствие дублей.
   Ручная проверка сотрудником — отдельно, без обработки реальных обращений
   агентом ради теста. После технического успеха обновить метаданные и проверить
   итоговое резервирование; резервирование не держать заблокированным в ожидании
   ручной проверки.

## Если новая версия неисправна и завершить доставку ею нельзя

Наличие старого образа не решает несовместимость. При BLOCK **готового безопасного
отката на 8dcfa330 нет**. Сохранить БД, snapshots, MID, ошибки и очередь, объявить
перерыв обработки и причину. Не запускать заведомо несовместимый worker ради
доступного health. На время перерыва сохранность уже принятых inbox/outbox
обеспечивает БД; новые события, не принятые приложением, зависят от повторов MAX.
Их бессрочное хранение на стороне MAX здесь не доказано — обещать отсутствие
потерь таких событий нельзя. Отдельный режим приёма без обработки тоже не
считается готовым решением без разработки и проверки.

Варианты отдельного исправления для ревью:

- починить неисправный участок новой версии, сохранив совместимый delivery worker;
- подготовить backport на старый runtime либо ограниченный восстановительный
  обработчик, который понимает текущие задания. **Такой образ/обработчик в этом
  PR не создан и не проверен.**

Минимально необходимый объём совместимости — не только чтение массива MID:

- идентичный план разбиения/отпечаток и v1-прогресс, ACK каждой части и CAS по
  попытке/аренде/payload; остановка при неизвестном формате или несовпадении;
- продолжение с подтверждённой границы, транзакционное завершение всех ACK без
  повторных отправок, exactly-once **учёт** deliveredAt/ANSWER_SENT/ключа уведомления;
- защита версии ответа, цикла назначения и photo-recovery, безопасное снятие
  старых кнопок и обновление подтверждённого фрагмента; обработка failed во всех
  вызывающих сценариях, включая личную работу;
- сохранение backoff, лимитов, порядка адресата и полномочий ручного /resend;
  сохранение FAILED и служебных retirement-причин, без общего retry;
- полноценный shutdown и отсутствие конкурирующих владельцев при переключении.

До признания такого решения готовым нужны проверки всей матрицы ниже, CAS и
перезапуска между ACK/записью/завершением, двойного /resend, 429/5xx, смены
версии/назначения, длинных карточек/кнопок/фото, старых и неизвестных payload,
учёта доставки, сохранности данных и сохранения очередности. Затем отдельный
план установки и ревью. Нельзя заменять эти проверки удалением progress,
фиктивным SENT, массовым retry или восстановлением старой БД.

Потерянный сетевой ACK или незафиксированный MID остаётся неоднозначным даже
для совместимого кода: абсолютное отсутствие дублей на этой границе не обещается.

## Воспроизводимые проверки

Использовать только отдельную PostgreSQL и тестовые настройки с имитацией MAX:

```sh
npx vitest run tests/integration/delivery-worker-lifecycle.test.ts
npx vitest run tests/integration/delivery-rollback.test.ts
npx vitest run tests/integration/transactional-workflow.test.ts
npx vitest run tests/integration/delivery-reliability.test.ts tests/integration/delivery-review-regressions.test.ts tests/integration/parallel-outbox.test.ts
npx vitest run tests/unit
npm run typecheck
npm run build
```

Матрица rollback использует синтетические записи. Изменение FAILED→PENDING
внутри одной фикстуры — демонстрация риска будущего повтора, **не команда для
рабочей очереди**. SQL-preview проверен на тех же состояниях; неизменность
записей проверяется до/после. Запуск прежнего runtime производится отдельно
с тем же тестом и той же изолированной БД; ожидаемые отрицательные результаты
старого кода не скрываются изменением ожиданий теста.

Итог проверки этой редакции:

- управляемое воспроизведение гонки — 1/1 на main и 1/1 на `7219464`;
- одинаковый окончательный тест с остановкой worker и ACK-барьером — оба пути
  (региональный/согласованный), по 3 отдельных прогона на каждой версии, 12/12;
  это адресные запуски двух сценариев, остальные тесты файла в них не выбирались;

  тест — 2/7, пять ожидаемых отказов защиты от дублей (включая окончательное
  завершение согласованного ответа); старые ожидания не адаптировались ради успеха;
- итоговый полный прогон шести интеграционных файлов — 92/93, без пропусков:
  worker lifecycle, rollback, delivery-reliability, delivery-review-regressions,
  parallel-outbox и transactional-workflow. В последнем 21/22: прежний отказ
  регистрации подготовленного черновика, отдельно подтверждённый ранее на

Сырые отчёты остаются локально, персональные и эксплуатационные материалы не

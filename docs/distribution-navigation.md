# Навигация распределения

## Воспроизведение и причина

База исправления: `70cac4c7bc31831f96719b17d31b9126d3d9ed65`.
Рабочий runtime для изолированного сравнения: `59149006a7b3d30d01218fad84360e7d71e6d79e`.
Производственный сервер и MAX в этой работе не использовались.

На обеих неизменённых версиях через `handleCallbackUpdate`, с настоящей тестовой
PostgreSQL и имитацией MAX, воспроизведены три отказа в рабочем чате:

| Переход | Ожидание | Фактический результат до исправления |
|---|---|---|
| Темы: страница 1 → 2 → 3 → «Назад» | Страница 2 | Остаётся страница 3 |
| Организации: страница 1 → 2 → 3 → «Назад» | Страница 2 | Остаётся страница 3 |
| Тип организации → список → «К выбору типа организации» | Типы организаций | Остаётся список |

`actionLease` оставлял успешный навигационный callback заблокированным на 120 секунд.
Ключ включал действие и страницу, но не конкретный экран. Возврат вызывал уже
использованное действие; сотрудник получал «Уже обрабатывается», хотя работа
предыдущего перехода закончилась. Это не истечение закрепления и не отказ в правах.

Первое доказательство: [Actions 37652952888](https://github.com/bassixs/Incident-Management/actions/runs/37652952888),
3 ожидаемых падения на каждой базе. Расширенное сравнение:
[Actions 37655277527](https://github.com/bassixs/Incident-Management/actions/runs/37655277527).
В каждой baseline-задаче проверены ровно 3 падения в чате и 3 успешных аналогичных
сценария в личном режиме. Успех baseline-job означает проверенное воспроизведение,
а не работоспособность исходного кода.

В личном режиме эти три перехода не блокируются: там отдельная блокировка только
на время обработки. Буквальной кнопки «Вернуться к выбору организации» в исходном
коде нет. Есть «К выбору типа организации» в списке и «Назад» в личном подтверждении;
последняя отменяла выбор и открывала общую карточку, теряя страницу списка.
Связать конкретную жалобу с этим экраном без его вида/названия нельзя. Тексты
обращений, персональные данные или нажатия на рабочем боте для этого не нужны.

## Карта переходов

- Карточка → «Изменить тему» → страницы тем → выбор темы/«Иное»: тема сохраняется,
  временный экран закрывается; назначение не выполняется. Затем «Распределить»
  в карточке открывает типы организаций.
- Карточка → «Распределить» → тип организации → список организаций с пагинацией
  → выбранная организация → подтверждение → явное «Подтвердить» назначает её.
- В списке «Назад»/«Вперёд» меняют страницу. «К выбору типа организации» возвращает
  типы. В подтверждении «Вернуться к выбору организации» открывает прежний раздел
  и страницу. Совместимая выбранная организация остаётся указана на экране, но
  прежнее подтверждение больше не действует: можно повторно выбрать её или другую.
- «Отмена» не назначает организацию и не освобождает закрепление. Тему, территорию,
  текст, телефон и вложения навигация не сбрасывает. Изменение темы делает ранее
  открытый список/подтверждение несовместимым: его нужно открыть заново.
- В рабочем чате и личной работе используются одни и те же переходы; личный
  адаптер сохраняет проверки членства, выбранного обращения и закрепления.

## Защита

Навигация имеет отдельную блокировку только на время запроса, с проверкой владельца
при освобождении. В существующей `SystemSetting` хранится одна запись
`distribution-navigation:<operator>:<working-chat>`: технические ID, версия экрана,
MID клавиатуры, разрешённые переходы, страница, текущая тема и точный срок закрепления.
Текста обращения, телефона или файлов в записи нет. Новых таблиц и миграций нет.

Каждый экран получает новый случайный токен. Его условное потребление в БД происходит
до действия; повтор, чужой MID, старый токен, другой режим/оператор, смена темы,
закрепления или завершённое распределение отказывают без назначения. Запись нового
экрана также условная: поздний ответ MAX не может оживить уже заменённый экран.
После перезапуска актуальность проверяется по сохранённой записи.

Только явные входные кнопки карточки могут взять обращение по прежним правилам.
Служебные карточки чата сверяются с сохранёнными MID/outbox. Навигационные шаги не
перезакрепляют обращение. В транзакциях изменения темы/назначения повторно проверяются
точное закрепление и тема. Открытие списка, возврат и предпросмотр не создают `ASSIGNED`.

Для длинного подтверждения используется подтверждённый MID части с клавиатурой,
который доставка уже вычисляет. Разбиение, порядок частей и `deliveryProgress` не меняются.
Временные экраны отправляются с существующими ограничениями MAX и проверкой перед
попыткой. При отказе/неизвестном результате новый экран не считается действующим;
нужно заново открыть распределение. Повтор назначения автоматически не выполняется.

## Совместимость и ограничения

- После будущей установки уже открытые промежуточные списки и старые подтверждения
  следует закрыть/отменить и открыть заново из актуальной карточки. Обращение и
  действующее закрепление сохраняются. Старое подтверждение без снимка навигации
  не применяется автоматически.
- Новые записи служебные; старый код их не использует. Резерв не изменён, исправление
  навигации в нём отсутствует. При возврате на него новые кнопки не поддерживаются;
  рабочие экраны нужно открывать заново. Это не подтверждение совместимости резерва
  со всеми прочими изменениями текущего main.
- MAX и БД нельзя обновить одной транзакцией. При сетевой неопределённости возможно
  видимое, но уже недействующее сообщение. Его кнопки откажут; сотрудник открывает
  новый экран. Дубли при потерянном ACK не объявляются невозможными.
- Пагинация старой личной версии работала в воспроизведённых сценариях. Причины иных
  живых жалоб без технической привязки к экрану не установлены.
- Нет merge, установки, производственного образа или изменений очереди на сервере.

## Проверки

`tests/integration/distribution-navigation.test.ts` проверяет обычный входящий
callback в обоих режимах: границы страниц, повторный/задержанный callback, пустой
список, возврат из подтверждения, единственное назначение, истечение/смену
закрепления, смену темы, перезапуск обработчика, конкуренцию переходов, поздний
HTTP-результат, ошибку редактирования, права, отмену и сохранение полей/вложений.
Проверяется также смена закрепления между асинхронным чтением и транзакцией назначения.

Существующие тесты, вызывавшие `assign-group` без показанного экрана, переведены на
настоящую последовательность открытия/выбора через сохранённые кнопки. Проверки
бизнес-результатов не удалены и не ослаблены. Unit отдельно проверяет MID клавиатуры
длинного сообщения. Итоговые результаты и SHA фиксируются в описании PR и Actions.

### Разбор прежней нагрузочной фикстуры

На неизменённом main `70cac4c` исходный `concurrent-staff-load` отдельно упал:
ожидался `RESOLVED`, фактически корректный `REJECTED`. Номер синтетического сценария
вычислялся из последнего слова текста, который штатное отклонение заменяет на
«Содержание отклонённого сообщения удалено.». Получался `NaN`, и проверка выбирала
ветку ожидания доставленного ответа вместо отклонения. Индекс теперь вычисляется
из неизменяемого синтетического ID пользователя; проверки итогов сохранены.

В той же БД пять заданий панелей имели `this.max.getMe is not a function`:
старый mock не реализовывал новый протокол панелей. Дополнены именно методы
имитации: identity, история сообщений, однократная отправка панели, полные сведения
о сообщениях/закреплении, удаление временного сообщения. Production runtime панелей
не менялся. Доказательства — артефакт `unchanged-load-baseline` запуска
[37658437393](https://github.com/bassixs/Incident-Management/actions/runs/37658437393).

Нагрузочная фикстура также теперь ждёт фактического MID карточки через ограниченную
проверку условия, прежде чем имитировать её нажатие. Один `flush()` не гарантирует,
что конкретная карточка уже получила ACK при параллельных производителях очереди.
Новые проверки безопасности не обходятся, фиктивные MID и `SENT` не подставляются.

# Восстановление экранов черновика

Исправление подготовлено от main `d927df7860dcad06b1887afd36ac852a159e50de`.
Историческая причина серии отказов U14 остаётся неустановленной: версия нажатой
кнопки не была записана. Изолированно воспроизведён другой подтверждённый дефект:
после исчерпания отправки следующий токен сохранялся без доставленного экрана.

## Поведение

В `OperatorSession.data` вместе с версией экрана сохраняется `draftScreenDelivery`:
готовый экран, ссылки на фото MAX, число попыток, срок следующей попытки и
техническая корреляция inbox. Запись и версия экрана сохраняются одной операцией.
Восстановление отправляет этот экран, не исполняет callback повторно и не
регистрирует сообщение. Текст, телефон, территория и фото остаются в черновике.

Для каждой версии допускаются первоначальная отправка и три фоновых повтора с
задержками 5, 30 и 120 секунд после ошибки. Каждая отправка использует существующие
ограничитель MAX и до четырёх транспортных попыток. Sweep — раз в пять секунд,
не более 20 экранов за проход, по два независимых адресата. Незавершённая попытка
после аварийного завершения процесса доступна вновь по окончании пятиминутной
аренды. При исчерпании попыток автоматическая отправка прекращается; через меню →
«Создать сообщение» → «Продолжить черновик» можно показать новую версию экрана.

Перед каждой попыткой MAX (также после ожидания адресата и rate limit) проверяются
владелец сессии, её существование, срок, тип, draftToken, screenToken и наличие
актуального задания. Принятое действие отменяет восстановление прежнего экрана.
Номер попытки и срок её аренды также проверяются: запоздавшая попытка не может
продолжить отправку или записать результат поверх новой попытки той же версии.
Новый экран, отмена, регистрация или замена черновика не должны оживлять старый.
Результат доставки фиксируется через compare-and-swap; у известного сообщения,
присланного слишком поздно, снимаются кнопки. Фоновые попытки не продлевают 24 часа
хранения черновика. Worker включён в штатные pause/drain/shutdown приложения.

Экран черновика не занимает головное задание общей очереди уведомлений. При этом
отправка соблюдает существующее исключение одновременных запросов одному адресату.
Глобальный параллелизм и лимиты MAX не изменены.

## Прежние страницы

При перелистывании одного и того же выбора прежний экран получает спокойную
подсказку: «Эта страница больше не активна. Выберите тему кнопками в новом сообщении
ниже ↓» либо «Эта страница больше не активна. Выберите территорию кнопками в новом
сообщении ниже ↓». При смене этапа — «Эта страница больше не активна. Продолжите
оформление в новом сообщении ниже ↓». Новых сообщений ради подсказки нет.
В JSON черновика запоминается только вид выбора у известных подтверждённых MID;
он удаляется вместе с записью об успешно снятой клавиатуре. Для прежних экранов
без этих метаданных используется нейтральная формулировка. Миграция не требуется.
Подсказки отказа при фактическом нажатии устаревшей кнопки остаются прежними.

Только после подтверждения нового сообщения сохраняется его MID и снимаются
кнопки с известных предыдущих экранов этого черновика. Старый текст заменяется
подсказкой; фотографии и остальные распознанные вложения сохраняются. Неизвестное
вложение не удаляется ради успешного редактирования. Нет поиска по истории чата,
подстановки MID из callback или редактирования карточек зарегистрированных сообщений.
При явном «Начать заново» только известные ID сбрасываемого черновика того же
владельца передаются на снятие клавиатуры после доставки нового первого экрана.

Неудачное снятие кнопок не отменяет новый экран: ID остаётся в `screenRetireIds`,
выполняются ограниченные повторы. Серверная защита старых версий работает независимо
от результата редактирования MAX. После отмены/истечения сессии повторная очистка
её сохранённого списка прекращается; неудачная очистка позднего ответа отмечается
безопасным событием с MID для отдельной проверки. Не гарантируется успешное
редактирование недоступного сообщения.

Если MAX принял отправку, но потерял ответ с MID, возможны несколько одинаковых
экранов одной версии. Их неизвестные MID невозможно надёжно снять без механизма
обнаружения в MAX. Подтверждение до подтверждённой доставки предпросмотра отклоняется
без уничтожения задания восстановления. После доставки регистрация требует явного
нажатия; повторные события не создают второе сообщение.

## Подсказки

- Старая страница: «Это действие устарело: открыта старая страница. Используйте
  последнее сообщение бота или нажмите „Создать сообщение“ → „Продолжить черновик“».
- Отсутствующий/истёкший черновик: «Сохранённого черновика нет или истекли 24 часа
  с последнего действия. Нажмите „Создать сообщение“, чтобы оформить новое».
- Занятое действие: «Предыдущее действие ещё выполняется. Дождитесь следующего
  экрана бота».
- Недоставленный экран: «Не удалось показать следующий экран. Черновик сохранён,
  сообщение не отправлено. Бот повторит показ. Также можно открыть меню →
  „Создать сообщение“ → „Продолжить черновик“».

## Диагностика и совместимость

События `draft action refused`, `draft screen delivery`, `draft screen recovery`
содержат enum причины, тип сессии/поле редактирования/страницу, inboxId, хеши корреляции версий, номер попытки,
безопасный HTTP-код и известный MID. Текст, телефон, полный callback и секреты не
записываются. Одинаковые отказы одной версии/причины подавляются на 10 секунд;
это ограничивает шум, поэтому количество строк не равно количеству нажатий.

Схема PostgreSQL и зависимости не изменены, миграций нет. Существующие черновики
остаются действительными. Новые поля появляются при следующем показе; потерянные
ID старых страниц из предыдущих версий автоматически не восстанавливаются.
У старого черновика без нового задания остаётся ручной маршрут продолжения.
Сохраняемый экран может содержать номер в итоговой карточке; он хранится только в
той же ограниченной сроком сессии, не в общем outbox. Ничего не переносится в профиль.

## Проверки

`tests/integration/draft-screen-recovery.test.ts` преобразует диагностическое
воспроизведение в регрессию: 26 активных тем на пяти страницах, прежние кнопки,
двойные/задержанные события, ошибки и перезапуск, исчерпание повторов, отмена/
истечение/замена/регистрация, поздний ответ MAX и отказ снятия клавиатуры.
Названия, порядок и активность каталога воспроизведены с синтетическими ID;
данных жителей в fixture нет. Проверки телефона/фото и unit-проверки сохранения
медиа и безопасной диагностики дополняют этот набор. MAX имитируется.

Тесты запускаются только с отдельной `TEST_DATABASE_URL`: helper очищает тестовую
схему. Рабочая БД для них недопустима. Живой прогон MAX, производственный образ,
установка и merge не входят в подготовку этого PR.

Первоначальная редакция PR `94d4df2`: 780/780 без пропусков (543 unit и 237 интеграционных проверок
в 11 файлах), включая 56 новых интеграционных сценариев и 2 unit-проверки
механизма восстановления. Typecheck и build успешны.

В более ранних прогонах были нестабильные ожидания inbox/outbox. На неизменённой
базе `d927df7` отдельно воспроизвелись три тайм-аута `parallel-outbox`: пробуждение
свободных слотов, преемника адресата и гонка выбора задания. В итоговом прогоне
все 19 проверок этого файла прошли; его код не изменялся. Это не доказательство
устранения прежней нестабильности и не исправление других дефектов доставки.

В проверках телефона ожидание наступления сохранённого `nextAttemptAt` добавлено
перед однократным `kick()`: в локальном PostgreSQL округление до миллисекунд может
дать срок на 1 мс позже текущего времени Node. Это не меняет задания и не ослабляет
проверки конечного статуса, содержимого рабочего ответа и сохранности черновика.
Код inbox/outbox ради этого не изменяется.

## Исправление по ревью: недоступная фотография в фоне

На исходной вершине PR `94d4df2` обработка `isUnavailablePhoto` находилась только
в `showIncidentDraftPreview`. Фоновый worker вызывал доставку напрямую, поэтому
после временного сбоя и последующего отказа фото сохранялись `exhausted` и
`previewDeliveryPending`, а экран замены не появлялся.

Переход теперь общий для первоначальной и фоновой доставки. Только распознанная
ошибка недоступного фото в предпросмотре с изображениями переводит актуальный
черновик в ввод новых фотографий. Новый токен, состояние и восстанавливаемый
экран замены сохраняются одним CAS до отправки. Сохраняются текст, телефон, тема,
территория и срок хранения; фоновый переход не считается действием пользователя
и не продлевает 24 часа. Неизвестные ошибки не превращаются в отказ фотографии.

Экран замены использует тот же механизм ограниченных повторов. Отмена, истечение,
новая версия экрана или новый черновик во время запроса исключают запоздавший
переход. Выбор фотографии, её пропуск и подтверждение не выполняются автоматически.
Общие функции формирования текста и привязки кнопок вынесены без изменения
поведения в `draft-screen-content.ts`, чтобы не создавать циклические импорты.

Добавлены шесть интеграционных случаев: четыре транспортных 503 → новый worker →
ошибка фото → замена/явный пропуск → явное однократное подтверждение; повторный
503 при отправке самого экрана замены и его восстановление новым worker; отмена,
истечение, смена экрана и создание нового черновика при находящемся в полёте запросе.
Два основных сценария отдельно запущены на `94d4df2`: оба воспроизводят дефект
(остаётся `WAITING_INCIDENT_CONFIRMATION` вместо `WAITING_INCIDENT_EDIT_VALUE`).
На исправлении целевой набор из 72 проверок прошёл без пропусков. Расширенный
прогон: **786/786**, 59 файлов, без пропусков (543 unit и 243 интеграционные
проверки). Typecheck и build успешны. MAX имитировался, PostgreSQL — локальная
изолированная база. Миграций и изменений производственных данных нет.

# Посторонние чаты и старые приветствия

## Граница маршрутизации

Рабочий чат определяется `workingChatFor`: `DISTRIBUTION_CHAT_ID`, `REVIEW_CHAT_ID`,
`DELIVERY_ALERT_CHAT_ID` или `ResponsibleGroup.maxChatId` **активной** группы.
Название, публичность, статус администратора MAX и каналы проверки подписки не
расширяют этот список. Миграция не нужна.

Ранее `bot_added` безусловно отправлял приветствие. Команды могли отвечать в любом
чате, а callback канала мог ошибочно трактоваться как личный. Теперь проверка
стоит до разрешения/сохранения профиля, отказов по ПДн/контакту, распознавания
callback, его подтверждения, создания блокировки и выполнения бизнес-действий.
Посторонние события проходят технический inbox и завершаются без исходящих
сообщений; обработанный payload очищается существующим механизмом inbox.
Удаление участника из постороннего чата не меняет сохранённые сессии.

Личные диалоги, контекстные права настроенных чатов, рабочие сценарии и их
ограничения сохраняются. Канал не является личным диалогом. При изменении или
отключении привязки новые действия проверяются по актуальным настройкам.
Бот не покидает чаты, не меняет права и подписки MAX.

## Подключение

1. Администратор **бота** открывает личный диалог; его роль должна быть в `ADMINS`
   или `User.roles`. Одних прав администратора группы MAX недостаточно.
2. В новом чате отправляет `/chatid` без аргументов и вложений. Это единственное
   исключение: ID придёт ему в личный диалог. Профиль/чат этим не подключаются.
   Неуполномоченный пользователь не получает ответа; остальные команды и кнопки
   остаются заблокированными даже для администратора бота.
3. В личном диалоге выполняет прежнюю `/group_chat <КОД> <CHAT_ID>` для активной
   группы. Команда также доступна из уже настроенного рабочего чата. Проверка
   `admin.manage` и аудит назначения сохраняются.
4. Для системных чатов действуют прежние настройки окружения; их изменение
   требует отдельно согласованного перезапуска. После привязки проверить `/info`
   и `/queue`. Если личный диалог администратора недоступен MAX, выдачу ID надо
   разбирать как адресную ошибку доставки, не рассылать ответ в посторонний чат.

## Отдельная процедура для накопившихся приветствий

Обновление **не меняет** старые задания автоматически. Вне Git хранится явный
список полных UUID, согласованный владельцем. Нельзя выбирать все 403, все
`FAILED` или все сообщения в каналы. Не включать частные ID/дампы в PR.

`node dist/scripts/preview-foreign-greetings.js <private-ids.json> <new-private-directory>`
использует эффективное окружение приложения и только читает БД; приложение,
workers и MAX API не запускаются. JSON-вход — массив полных UUID. Каталог должен
быть новым, непубличным; POSIX-права 0700/0600, на Windows дополнительно проверить
ACL. Выход: `preview.json` с полными ID заданий/адресатов и `retire.sql`.
Никакого режима автоматического применения у генератора нет.

Для каждого задания проверяются: `PENDING`/`FAILED`, отсутствие активной блокировки,
`targetType=chat`, отсутствие связей с обращением/ответом/tracking/dedupe,
отсутствие `sentAt` и `firstMessageId`, точное совпадение исторического приветствия
с ID адресата, пустые вложения, отсутствие клавиатуры/операции, точная ошибка
`403: Insufficient access rights to perform this action`, обработанный источник
`bot_added` через `trace.inboxId`, отсутствие текущей рабочей привязки.
Предпросмотр не делает GET MAX: группу и канал он сам не различает. Тип адресата
сверить с отдельно разрешённой проверкой/сохранёнными фактами. Если источник inbox
уже удалён по сроку хранения или содержание отличается — отказ, не обходить его.

Порядок после **отдельного разрешения** на операцию:

1. Получить свежий предпросмотр на действующем окружении. Проверить каждый полный
   ID, числовой ID адресата, тип и происхождение; сохранить приватную копию строк.
2. Сделать проверенную резервную копию, штатно остановить/drain **только app**,
   исключить другие workers. Повторить предпросмотр после остановки: попытки,
   статус или привязки могли измениться. Ошибки остановки — повод прекратить работу.
3. Проверить `retire.sql` и применить его через штатный локальный доступ PostgreSQL
   с `psql -X -v ON_ERROR_STOP=1 -f <private-retire.sql>`. Подключение передавать
   через защищённый service file/окружение, не печатать URL с паролем.
   Не менять конфигурацию между последним предпросмотром и применением.
4. Транзакция блокирует ровно перечисленные строки (`NOWAIT`), сверяет хеш полной
   строки, адресата и текущие привязки. Любое расхождение откатывает **весь** набор.
   При отказе заново исследовать состояние, не расширять `WHERE`.
5. Меняются только `status=FAILED`, `lockedAt=NULL`, явный `lastError` с префиксом
   `MANUALLY_RETIRED_FOREIGN_BOT_ADDED`, `updatedAt`. Payload, attachments, attempts,
   история ошибок в сохранённом снимке и сами записи сохраняются. `sentAt`,
   `firstMessageId`, `trackingApplied`, `deliveryAlertedAt` не выставляются как
   доказательство успешной доставки. Существующее `trackingApplied=true` у
   нетрекируемого приветствия не является подтверждением отправки.
6. Проверить ровно согласованное число изменённых строк, отсутствие `SENT`, затем
   вернуть один app и проверить обычное продвижение очередей, без общего retry.

`FAILED` не выбирается автоматическим worker и не блокирует следующий адресный
job; это проверено с реальным PostgreSQL и fake MAX, в том числе после пересоздания
worker. Это **не доставка**. Существующие `/delivery_errors`, мониторинг и alert
могут показать эти строки; `deliveryAlertedAt` намеренно не подделывается.
Существующий ручной `/delivery_retry`, особенно без ID, способен вернуть `FAILED`
в работу: не применять его к снятым приветствиям. Постоянный запрет ручного retry
или новый статус очереди в это исправление не входят.

SQL не восстанавливает дамп и не изменяет обращения. Откат кода не возвращает
снятые приветствия в `PENDING`; это отдельное решение, не часть отката приложения.

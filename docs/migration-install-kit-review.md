## 1. Массовые файловые ключи

Полный перенос проверен: **35 000 разных storageKey**, по 5000 записей в семи защищённых таблицах, журнал удаления, состояние unknown, постоянная отметка и JSON deliveryProgress v1. БД источника после всех миграций; два восстановления в новые пустые БД: обычный pg_restore и --single-transaction. Сравнены все строки всех таблиц через количество/детерминированный digest, последовательности, 23 записи миграций, определения семи триггеров и функции. Каждый восстановленный триггер принимает свежий ключ и отказывает для retired-key. Пробные транзакции откатываются, данные повторно сверены.

**36/36 проверок**. PostgreSQL: max_connections=100, max_locks_per_transaction=64, max_prepared_transactions=0. Лимиты не повышались. В процедуре восстановления защита не отключалась: полный custom dump сам создаёт post-data триггеры после данных. В негативном тесте установочного комплекта один триггер намеренно отключался только в одноразовой БД, чтобы проверить отказ установки при дрейфе схемы.

Проверенный способ: `pg_dump -Fc` → **пустая БД без заранее развёрнутой схемы** → `pg_restore --no-owner --no-privileges --exit-on-error [--single-transaction]` → сверка данных/миграций/guards. Приложение при восстановлении этой копии не запускалось. Это не data-only импорт и не инструкция восстановления старого дампа поверх действующих данных.

Проверка путей кода:

- IncidentService.create/attachMedia: до 4 фотографий жителя, одна регистрация на транзакцию.
- AnswerService.submit/attachMedia: все вложения одного ответа в одной транзакции; отдельного универсального лимита количества у сотрудников нет. Набор в тысячи/десятки тысяч вложений нельзя считать безопасным. MAX клиент с таким набором не проверялся; ограничения MAX не выдумываются.
- OperatorSession/PrivateWorkItem и enqueue: один экран/черновик/исходящее задание. Один необычно большой JSON также может содержать много новых ключей. Разбиение SQL внутри одной большой транзакции не освобождает advisory locks.
- Inbox сохраняет одно входящее событие. Обычная обработка не объединяет историю многих пользователей в одну транзакцию. Пакетные уведомления/справочники не создают много новых storageKey.
- В src/scripts нет штатного массового импорта файловых ключей. Импорт через произвольный SQL/сторонние инструменты не гарантируется.
- tools/restore-check.cjs, tools/handover-smoke.cjs и локальная сохранённая редакция действующего механизма резервирования используют полный custom dump в пустую изолированную БД. Исходники прочитаны локально, текущее состояние сервера не проверялось. Старый deploy/backup.sh выбирает другую конфигурацию через POSTGRES_DB и не предлагается вместо действующего резервирования.

**20 000 не порог.** Предыдущее воспроизведение SQLSTATE 53200 для одной транзакции с 20 000 новых ключей остаётся действительным. Для подготовки источника здесь использованы транзакции по 250 ключей: это конкретный проверенный размер партии, не универсальная гарантия при любой конкуренции. Полный перенос закрыт без изменения runtime/миграций. Для массового импорта в уже защищённую схему нужны отдельные ограничения партии и испытание конкретного импорта. Не подтверждено, что произвольные огромные прикладные наборы проходят.

## 2. Установочный комплект с миграциями

Обязательная проверка использует ту же DATABASE_URL из неизменного runtime.env и сеть, что одноразовый Prisma CLI. Сверяются identity PostgreSQL/БД, история и checksum миграций, колонки, индексы, ограничения, определения/включённость триггеров и guard-функция. Эталон схемы получен на стенде из точных исходников: 21 старая миграция → 23 новые.

До запуска Prisma сохраняется общий migration-intent.json с fsync. Наличие записи (включая повреждённую/неполную) запрещает resume старого образа. Проверяются также оставшийся контейнер миграций и фактическая схема: отсутствие applied.json/старый Compose не разрешают старый запуск. Для main/reserve нужны точный новый schema fingerprint, завершённый exit=0 контейнер миграций и complete-запись. Неясный/частичный результат не исправляется автоматически.

**13/13 сценариев, настоящий Linux/Docker/PostgreSQL/flock**, 313.575 сек:

1. Отмена до миграций: тот же контейнер; повторный resume отказан; apply до миграций отказан.
2. Миграции завершены, Compose ещё старый: old запрещён, совместимый резерв запускается.
3. Контролируемый отказ запуска: реальный контейнер exit=17 → защищённый recover → настоящий резерв.
4. Контролируемый отказ создания команды Compose → защищённый recover → настоящий резерв.
5. Другая identity БД: старое приложение остаётся работающим.
6. Реальная ошибка DDL второй миграции после применения первой: Prisma фиксирует незавершённую миграцию; old/main запрещены.
7. Реальный Prisma заблокирован на DDL, имитирована потеря ответа CLI. После позднего успешного завершения запись остаётся started; автоматический запуск по-прежнему отказан.
8. Основная → резерв → основная с одной БД; штатные stop/apply/start, readiness, один экземпляр.
9. Контейнер миграции существует без локальной записи: old запрещён.
10. Частичная схема без локальной записи: old запрещён.
11. Обрезанная локальная запись: old запрещён.
12. Дрейф guard-триггера после миграций: apply запрещён.
13. Второй экземпляр: stop запрещён; миграция при работающем app также запрещена.

После каждого сценария реальный flock доступен снова. Контрольные 8 FAILED, черновик и файл сохранены. Для old использован синтетический HTTP/SIGTERM контейнер с ролью old; основная и резервная версии — настоящие закреплённые образы. Отказ самой команды создания Docker и потеря ответа CLI управляемо имитируются; БД/DDL, контейнеры, SIGTERM, flock, последующие запуски и HTTP readiness настоящие. Намеренные отказы не моделировались на рабочей установке.

Дополнительно **4/4 и 4/4 с Python -O** локально: новый gate перед обновлением метаданных резервирования, отказ без миграций/при частичной схеме/неожиданных исходных REV/IMAGE, успешная замена ровно трёх строк и отказ повторного обновления. Здесь Docker/БД/flock имитировались; временные файлы настоящие. Старые 64/40/11 проверки R4 и прежние 201 контейнерных проверок не объявляются заново выполненными.

## Что остаётся перед установкой

1. Ревью новой редакции операционных скриптов/diff и плана. R4 не подменена незаметно: этот комплект добавляет новые обязательные условия.
2. Отдельное разрешение на подготовку реальных настроек: текущие образ/БД/сеть/права/перезапуск/ротация, точные Compose/runtime hashes, identity и соответствие манифесту. Текущая рабочая версия в этом задании не проверялась.
3. Отдельное разрешение на установку: свежая проверенная копия, штатная остановка только app, финальная копия, миграции, main/резерв, сверка данных и очередей, метаданные резервирования и итоговая проверенная копия. См. PLAN.md.
4. При неизвестной или частичной миграции **нет автоматического безопасного старта** ни old, ни main/reserve: требуется разбор. Резерв не исправляет общие ошибки inbox/enqueue/retention/guards, потерянный ACK и неизвестный результат удаления. Политика FAILED/progress/fences сохраняется; старый дамп не восстанавливается.
5. Проверка схемы использует Prisma CLI основной версии; если сам этот образ/CLI недоступен, автоматическое переключение также откажет. Такой случай требует отдельного проверенного диагностического пути. Проверка pg_control_system требует прав; отсутствие прав — отказ, не повод снять проверку.
6. Реальная нагрузка/MAX и онлайн-согласованность внешних файлов здесь не перепроверялись. Работоспособность продолжения сохранённых частей/журнала подтверждена предыдущим стендом точных 5914900/1a7a0f5 (Actions 37532929239), а не новым повтором всех старых сценариев. Известные 11 падений старого набора (включая обсуждавшиеся девять) остаются отдельно; эти тесты здесь не менялись/не перезапускались.

Сервер, рабочий бот, вебхук, рабочее резервирование, очереди и PR №5 не затронуты. На этом подготовка остановлена для ревью.

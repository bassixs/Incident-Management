# Сохранение установки при подготовке передачи и возврата

Это перечень условий для подготовки отдельной инструкции, а не команды текущего
развёртывания. Он выделен из локальных материалов передачи; приватные параметры,
факты старых снимков и заявления о выполненных проверках не переносились.

Перед выполнением конкретного плана оператор определяет свои параметры:
`INSTALL_ROOT` — корень установки; `PROJECT_DIR` — каталог Compose;
`BACKUP_DIR` — закрытый каталог копии; `COMPOSE_PROJECT` и `COMPOSE_FILES` —
действующие имя проекта и набор файлов; `APP_SERVICE`, `DB_SERVICE` — имена
сервисов; `SOURCE_REVISION` и `ROLLBACK_IMAGE` — проверенные коммит и образ;
`NEW_BOT_TOKEN`, `PUBLIC_DOMAIN`, `WEBHOOK_SECRET` — частные значения нового
окружения, которые передаются отдельно и не записываются в эту инструкцию.

## Обновление той же установки

Сначала сверить текущую версию и реальные mounts. Сохранить исходники, настройки,
базу, вложения и предыдущий образ. Окно остановки обработки согласовывается
отдельно; согласованный снимок требует отсутствия конкурирующих писателей.
Сохраняются существующие .env, данные, имя Compose-проекта, права и привязки.
Не удалять тома и не восстанавливать базу отправителя поверх данных получателя.
Не считать изменение пароля в .env изменением пароля пользователя существующей БД.

План проверок должен включать ограниченное ожидание health/ready, действующий
вебхук, очереди и сопоставление прежних ID панелей с закреплениями. Нельзя выводить
полный docker inspect/Compose config или сырые логи в публичный отчёт.
Не включать очистку тестовых данных в обычные шаги обновления.

## Перенос с другим ботом

Это отдельная процедура, а не замена одного токена. Сначала инвентаризировать
сохранённые ID карточек и панелей, inbox/outbox, незавершённые доставки, локальные
и MAX-медиа, доступ нового бота к рабочим чатам и личным диалогам. Старые message ID
не должны автоматически становиться адресами редактирования нового бота.
SENT не переводят в PENDING; неоднозначную доставку проверяют до повторной отправки.
Не выполнять массовый сброс SystemSetting или очередей по шаблону из старого снимка.
Получатель предоставляет свой токен, домен, секрет вебхука и параметры БД.
Снимок работающего экземпляра обозначается как предварительный; финальный снимок
согласовывается на момент переключения. В этом PR нет нового мигратора или
универсальных команд преобразования данных между ботами.

## Возврат

Сверить совместимость прежнего приложения с текущей схемой и сохранить состояние,
появившееся после переключения. При обычном откате приложения возвращаются
совместимые файлы и сохранённый образ, а база и вложения остаются текущими.
Восстановление старой базы — отдельное решение с учётом новых сообщений.
Подписка возвращается только согласованному обработчику; два экземпляра не должны
одновременно принимать одну рабочую очередь. Удалённые в MAX сообщения не
восстанавливаются откатом приложения или возвратом дампа.

Действующие сценарии жителя описаны в `manual-phone-review.md` и
`resident-draft-safety.md`; исторические шаги r2 с системным контактом их не заменяют.

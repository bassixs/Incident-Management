## Причина и поведение

При обновлении карточки MAX отвергал возвращённое им share-вложение. Постоянный
HTTP 400 оставлял головное задание `staff-refresh` в механизме повторов; порядок
доставки по адресату удерживал следующие задания чата согласования за ним.
Причина, по которой MAX признал собственные token/url непригодными, не установлена.
Исправляется подтверждённый отказ API, а не предполагаемая внутренняя ошибка MAX.

`editCardWithKeyboard` сначала использует обычный путь сохранения вложений.
Только при одновременном выполнении следующих условий допускается одна повторная
попытка редактирования без необязательного предпросмотра ссылки:

- ошибка является `MaxError`, HTTP status равен 400;
- точный текст `error.message` равен
  `400: No valid url or token provided for share attachment`;
- в запросе присутствует хотя бы одно вложение `share`;
- каждое такое вложение содержит пригодный URL: HTTP/HTTPS, без учётных данных
  и пробельных символов;
- полный текст с сохраняемыми ссылками укладывается в 4000 символов.

Исключаются только вложения `share`. Текст, фотографии, другие поддержанные
вложения и актуальная клавиатура сохраняются. Если URL отсутствует в тексте,
добавляется строка `Ссылка из предпросмотра: URL`. Повтор того же обновления и смена
закрепления той же полной карточки согласования сохраняют этот суффикс после
частичного успешного выполнения. Новый смысловой
текст, в частности очистка содержания при отклонении, не наследует старый суффикс.
Суффикс не добавляется в сохранённый текст ответа в БД.

Ответ `success: false` не считается успешным редактированием. Неизвестные вложения,
отсутствие пригодной ссылки, переполнение лимита, другие ошибки и отказ повторной
попытки не скрываются. Текст не обрезается, задания не помечаются выполненными
в обход штатной доставки. Порядок по адресату, rate limit, retry/backoff и
восстановление очереди после перезапуска остаются прежними.

### Дополнение по ревью: служебное обновление без share

Первоначальный `preserveShareFallbackText` узнавал лишь точный повтор текста.
После успешного fallback MAX мог вернуть карточку без share, и новая строка
закрепления нарушала сравнение: добавленная ссылка исчезала при следующем edit.
Два новых теста воспроизвели дефект до исправления: 19/21 прошли, 2 упали.

Теперь разбирается только завершающий суффикс из пригодных URL. Для полной карточки
`📝 ОТВЕТ НА СОГЛАСОВАНИЕ` сравнение исключает исключительно её начальный служебный
блок `Свободно` / `Закреплено за` с московским сроком. Вся остальная часть обязана
совпадать: номер сообщения, текст проблемы и ответа, история, подпись, вложения и
версия ответа. Похожие строки внутри содержимого не исключаются из сравнения.

Смена/снятие закрепления и точный повтор сохраняют ссылки без кэша процесса.
Новый текст, версия (в том числе с тем же текстом), другое сообщение и намеренная
очистка не получают прежние ссылки. Если увеличенный заголовок вместе со ссылками
превысит 4000 символов, до запроса edit возникает явная ошибка; прежняя карточка
остаётся доступной. Произвольные заголовки и другие форматы карточек не нормализуются:
для них остаётся только точное совпадение содержимого. Это намеренно узкое правило.

Проверки этой правки выполняются локально, с имитацией MAX и настоящим renderer
`reviewCard`; БД и рабочий сервер не используются. Предыдущие 109/109 и подтверждение
живой проверки относятся к установленному `f100949`, а не к этой новой правке.

Результат нового прогона: **133/133**, 6 unit-файлов, 0 пропущенных; typecheck и build
успешны. Node 24.19.0, Vitest 4.1.11, TypeScript 5.9.3. Наборы: `share-preview-fallback`,
`max-client`, `api-rate-gate`, `incident-cards-status`, `resident-delivery-status`,
`answer-signature`. Из них 23 проверки относятся к share fallback. Для новой правки
интеграционный набор с PostgreSQL и живой прогон MAX не выполнялись.

## Порядок восстановления для оператора

Этот порядок применяется только после разрешения владельца конкретной установки.
Не подставлять параметры другой установки и не выбирать БД по случайному значению
`POSTGRES_DB` контейнера.

1. Установить точные app/image/revision, Compose, рабочую БД, uploads и настройки
   резервирования. Сохранить образ отката и закрытую копию конфигурации. Проверить
   принадлежность карточек боту, URL share-вложений и длину актуального текста.
2. Собрать точный одобренный коммит отдельно от рабочей установки. Не включать
   несвязанные PR. Проверить образ до остановки app.
3. Создать свежую копию БД, вложений и настроек с контрольными суммами и проверкой
   восстановления в изолированную БД. Зафиксировать ID и состояния всех заданий
   затронутого адресата, включая завершённые; сохранить контрольные признаки
   сообщений, ответов, назначений и вложений. Не публиковать эти снимки.
4. Корректно остановить только app, проверить завершение текущей обработки и ExitCode.
   Сделать финальную копию и повторный снимок очереди. PostgreSQL, proxy, Docker service,
   webhook, данные и привязки сохранять. `pg_restore -l` подтверждает читаемость,
   но не заменяет выполненную отдельно проверку восстановления.
5. Если требуется ускорить очередную попытку, проверить головное задание повторно
   в транзакции с блокировкой строки и ограниченными таймаутами: точный ID/адресат,
   `PENDING`, отсутствие активной блокировки, `staff-refresh`, точная известная
   ошибка, отсутствие более раннего `PENDING`/`SENDING` у того же адресата.
   Только при совпадении менять `nextAttemptAt` и служебный `updatedAt`.
   Не менять status, attempts, payload, tracking или sentAt. `SENT` не повторять;
   `FAILED`, новая ошибка или несовпадение условий требуют отдельного разбора.
6. Заменить только образ app; запустить только app без сборки и зависимых сервисов.
   Ограниченно ожидать health/ready: например, 60 попыток с паузой 2 секунды
   и timeout 2 секунды на каждый HTTP-запрос. При исчерпании срока явно сообщить
   об ошибке и перейти к диагностике, без автоматических циклических рестартов.
7. Наблюдать штатное прохождение очереди по ID, добавляя задания, появившиеся во
   время восстановления. Не выполнять массовый retry, очистку или фиктивный `SENT`.
   Если следующая карточка блокируется, сохранить данные и установить причину.
8. Проверить актуальность текста и действий карточек по текущей БД и последней
   версии ответа, снятие устаревших действий, закрепления и панель. Одна лишь
   доступность сообщения или health=200 не доказывает восстановление доставки.
9. Сверить сохранность записей и объяснить штатные изменения по истории и доставке.
   Обновить привязанные к образу IMAGE/REV резервирования; копируемые исходники
   должны соответствовать новой версии. Проверить новую копию восстановлением.
   Получить отдельное подтверждение ручной работы согласующего.

При откате сохранить свежую диагностику, штатно остановить только app и вернуть
сохранённый образ и соответствующую конфигурацию резервирования. Запустить только
app и так же ограниченно ожидать готовности. Использовать текущую БД: восстановление
старого снимка поверх новых сообщений недопустимо. Откат не отменяет уже отправленные
сообщения MAX и возвращает прежний дефект share; он не гарантирует восстановления
очереди согласования.

## Ограничения

- Это узкий fallback для конкретного отказа MAX; произвольные 400/403/429/5xx
  не превращаются в успешную операцию.
- Без пригодного URL или при превышении лимита нужна отдельная диагностика карточки.
- MAX может снова сформировать предпросмотр ссылки. Исправление не обещает его
  постоянного отсутствия; текстовая ссылка сохраняется.
- Подтверждение запроса MAX не равно измерению отрисовки в клиенте пользователя.
- Копия ссылок на файлы MAX не является независимой копией самих файлов.
- Публикация PR не меняет работающую установку; дальнейшие установки и откаты
  требуют отдельного решения оператора.

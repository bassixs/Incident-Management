# Технические проверки перед пилотом

## Задержки без изменения рабочих данных

На сервере из `/opt/incident-bot`:

```sh
docker compose exec -T app node dist/scripts/delivery-metrics.js
docker compose exec -T app node dist/scripts/delivery-metrics.js 2026-09-09T08:00:00+03:00 2026-09-09T17:00:00+03:00
```

Без аргументов - последние 24 часа. Даты должны содержать часовой пояс; начало включается, конец исключается. JSON не содержит текста обращений, телефонов или токенов. Команда только читает БД в согласованном снимке. Для каждой метрики указаны число завершённых событий, среднее, p50, p95 и максимум в миллисекундах. При нуле событий значения пустые, а не нулевые задержки. Незавершённые события вынесены в состояние очередей, их возраст и число готовых недоставленных ответов.

Метрики: приём webhook → обработка; постановка исходящего задания → отправка; регистрация → публикация в распределении; регистрация → публикация в профиле (включает ручное распределение); согласование/прямая подготовка → доставка жителю. Это серверные временные отметки; отдельно измерять появление на экране MAX по журналу пилота. Выборка формируется по началу соответствующего интервала. Текущее состояние очередей относится к моменту запуска отчёта, а не к историческому концу интервала.

## Восстановление и перезапуск

`tools/restore-check.cjs --run-isolated` запускается на Linux-сервере из копии проекта с установленными зависимостями. Имена контейнера и каталога доказательств закреплены за проверкой 09.09.2026; повторный запуск откажется перезаписывать существующие материалы. Для нового прогона явно выбрать новые имена в коде.

Скрипт экспортирует согласованный снимок PostgreSQL, создаёт дамп production и манифест всех таблиц, восстанавливает их в отдельном контейнере `--network none` без публикации портов. Сравнивает количество и хеш содержимого строк каждой таблицы. Пароль исходной БД читается только на сервере; дамп и манифест остаются в закрытом каталоге backups. Восстановленная БД называется `incident_restore_check`; рабочая БД не изменяется. Проверка БД не восстанавливает внешние медиа MAX и файлы хранилища.

Для проверки процессов скрипт создаёт ещё одну пустую БД `incident_test` в этом изолированном контейнере. Применить миграции из проверяемого образа, затем выполнить `tools/recovery-drill.cjs` внутри одноразового контейнера того же образа, с сетевым пространством PostgreSQL (`--network container:iskra-restore-check-20260909`), `DATABASE_URL=postgresql://postgres@127.0.0.1:5432/incident_test`, `ISOLATED_RECOVERY_DRILL=1`, `NODE_ENV=test`, `BOT_MODE=polling`, `BOT_TOKEN=isolated-drill`, `LOG_LEVEL=silent`. Смонтировать каталог tools в `/drill:ro`. Не запускать index.js или настоящий транспорт MAX. После проверки удалить только созданный изолированный контейнер; дамп и отчёты сохранить.

Проверяются реальные классы очередей с имитацией внешнего транспорта: SIGTERM на активных заданиях; SIGKILL до внешнего приёма; SIGKILL после внешнего приёма, но до фиксации в БД. Истечение двухминутной аренды исходящих заданий ускоряется только правкой времени в тестовой БД. Это не замер реальной длительности аварийного восстановления.

После аварии обработка входящего сообщения могла уже изменить данные: такие незавершённые задания становятся FAILED для ручного разбора, без опасного автоматического повторения. Сначала сверить историю обращения и результат действия; не переводить все FAILED в PENDING массово. Если внешний сервис принял исходящее сообщение, но подтверждение не сохранилось, повторная отправка может создать дубль. Сам факт SENT в БД не доказывает прочтение. Эти ограничения нужно учитывать при разборе инцидента.

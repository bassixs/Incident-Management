# Восстановление закреплённых панелей

Панели обрабатываются отдельным `PinnedPanelService` через существующее единственное задание OutboundMessage на чат. Как и прежде, поддерживается один рабочий экземпляр приложения.

## Протокол

1. Известный ID проверяется чтением сообщения с проверкой автора, чата и структуры панели. Ошибка редактирования, включая 404, не означает, что сообщение отсутствует.
2. При 404 чтения проверяются закрепление и история чата. Если панель найдена, используется её ID. Новый экземпляр создаётся только после повторного отсутствия на следующем проходе и полного просмотра доступного окна истории.
3. Перед POST сохраняется намерение отправки в `SystemSetting` с ключом `panel-recovery:<ключ панели>`. На этой стадии известный ID не стирается.
4. POST выполняется без автоматических повторов. Сообщение создаётся без клавиатуры. Затем в одной транзакции сохраняются ID в SystemSetting и OutboundMessage и состояние восстановления. Только после этого добавляются кнопки и закрепление.
5. Если процесс завершился между POST и записью ID, следующий запуск ищет собственную панель в истории, сохраняет найденный ID и активирует её. Найденные лишние собственные панели получают текст «Панель устарела. Используйте закреплённую панель» без кнопок. Карточки жителей не подходят под проверку структуры и не изменяются.
6. `complete()` завершает задание, но больше не переписывает SystemSetting панели. Сбой закрепления или завершения задания не теряет уже сохранённый ID.

## Неоднозначная отправка и ограничения

Если MAX вернул 503/таймаут после POST, нельзя доказать, был ли он принят. Намерение сохраняется, повторный POST автоматически не выполняется. Последующие проходы пытаются найти сообщение. Если история не показывает результата, требуется ручная проверка; намерение нельзя просто стирать ради повторной отправки. Нельзя обещать exactly-once без гарантии самого API.

История читается страницами до 100 сообщений, максимум 10 страниц за попытку. Для восстановления прерванного POST достаточно полного окна с момента намерения; для неизвестного/утраченного ID требуется полный доступный просмотр. Неполная история, отсутствие доступа или отсутствие прогресса пагинации блокируют создание, а не трактуются как отсутствие панели. Временные сообщения без кнопок могут оставаться при длительной рассинхронизации MAX; они не дают лишнего доступа к действиям.

По [документации MAX](https://dev.max.ru/docs-api/methods/GET/messages/-messageId-/), 404 чтения может означать как отсутствие сообщения, так и отсутствие доступа. [История чата](https://dev.max.ru/docs-api/methods/GET/messages) доступна боту-администратору; время задаётся в миллисекундах.

## Диагностика

Модуль `pinned-panel` записывает `chatId`, `panelId`, `jobId`, `operation` и HTTP `status` ошибки. Для создания и восстановления фиксируются этапы `create-intent`, `created`, `reconcile`, `save-id`. Текст сообщений, вложения жителей, телефон, токен и полное тело ошибки не журналируются этим модулем.

Состояние `retire` хранит только ID подтверждённых прежних панелей. Временно недоступные копии проверяются повторно. Удаление сообщений не требуется.

## Исследование шести панелей 29.09.2026

До исправления подтверждены два собственных сообщения с активной клавиатурой в каждом из шести указанных чатов. Старые панели созданы около 12:19 UTC, новые — 19:29 UTC. Актуальные SystemSetting и закрепления совпадали.

Исторический триггер нельзя установить однозначно: прежние логи не связывали ошибку чтения/редактирования и повтор POST с ID панели, чатом и заданием. Единственная окончательная ошибка 503 с известным jobId относится к панели распределения, а не к одному из шести профильных чатов. Наличие отдельных повторов `sendMessageToChat` не доказывает принятую MAX отправку.

Подтверждены и устранены риски в коде: общий catch для 404 чтения и редактирования, сохранение ID только после закрепления, автоматический повтор неидемпотентного POST без сверки с историей. Точный исторический запрос не объявляется установленной причиной.

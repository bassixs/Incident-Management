# Подпись в ответе жителю: REGION_KALUGA

Автоматическая подпись `Ответ подготовлен …` (либо `Ответ подготовлен:` с названием на следующей строке) не добавляется в публичный ответ только при `ResponsibleGroup.code = REGION_KALUGA`. Это Администрация Губернатора. Отображаемое название и `bypassReview` не используются для выбора исключения. Другие организации, включая остальные группы с прямой отправкой, сохраняют подпись.

Блок исключается при формировании сообщения целиком, вместе с его разделителем. Текст сотрудника, в том числе похожие фразы и ссылки, не разбирается и не обрезается. Фотографии, кнопки оценки, права и прямой маршрут без согласования не меняются. Автор ответа, ответственная организация, история, внутренние карточки и отчётность сохраняются.

## Где сохраняется текст и что происходит со старыми заданиями

`queueAnswer` сохраняет готовый текст в `OutboundMessage.payload.text` в момент создания задания. `ReviewService.deliverApprovedAnswer` использует тот же форматтер. Поэтому изменения одного форматтера недостаточно для уже существующих заданий.

Перед первой отправкой worker дополнительно проверяет актуальный ответ и код группы. Для ещё не начатого задания он сверяет весь сохранённый текст с точным прежним шаблоном и атомарно сохраняет новый текст до обращения к MAX. Условие обновления включает владельца попытки и исходный payload. Вложения, метаданные и идентификатор задания сохраняются; новое задание не создаётся.

| Состояние на момент переключения | Поведение |
| --- | --- |
| Ответ подготовлен раньше, но outbox ещё не создан | Новое задание создаётся сразу без подписи. |
| PENDING, attempts=0, lastError/firstMessageId/sentAt отсутствуют, нет deliveryProgress и keyboardMessageId | При первой захваченной попытке (attempts=1) точный старый шаблон заменяется на новый до первой отправки. Уже новый шаблон остаётся без изменений. |
| Те же условия, но текст не совпадает ни со старым, ни с новым шаблоном или нет даты ответа | FAILED с `REQUESTER_SIGNATURE_REVIEW_REQUIRED`, без отправки и без фиктивной доставки. Нужен отдельный разбор; автоматическое вырезание фрагментов запрещено. |
| Предыдущая попытка уже была, даже без сохранённого MID, либо есть lastError | Сохраняется прежний текст: отсутствие MID не доказывает, что MAX ничего не принял. |
| Есть deliveryProgress, включая частичную доставку или все ACK без итогового учёта | Исходный текст и хеш плана не меняются. Продолжение только с неподтверждённой части, либо завершение учёта без повторной отправки. Старый блок подписи может остаться. |
| FAILED | Самостоятельно не возобновляется. При штатном разрешённом `/resend` сохраняются прежний текст и progress; lastError сохраняется при постановке на повтор и исключает ошибочную переклассификацию в новую отправку. |
| SENT | Не редактируется и не переотправляется. |

Таким образом, граница «отправки после установки» применяется к новым и доказанно ещё не начатым заданиям. Для начатых/неопределённых отправок безопасное исключение — завершить сохранённый план с прежним оформлением. Без отдельной сверки фактических сообщений нельзя одновременно обещать удаление подписи из всех старых заданий и отсутствие повторов уже принятых частей. Потерянный ACK остаётся неопределённостью существующего механизма доставки.

Перед будущей установкой нужен отдельный разрешённый просмотр старых `ANSWER_TO_REQUESTER` этой группы по указанным условиям. Этот PR не выполняет никаких операций с производственной очередью. Для несовпавшего шаблона требуется отдельный план адресной корректировки после подтверждения отсутствия отправки; слепой `/resend` не исправляет формат и не заменяет такую сверку.

## Совместимость

Новых полей, миграций и изменений `deliveryProgress v1` нет. Совместимый резерв `1a7a0f54217ef33bf4d7fac92f69e8ddfe46ec66` не изменён: уже сохранённый текст без подписи он отправит как записано, но новые ответы и старые неадаптированные задания при работе резерва сохранят прежнюю подпись. Это ограничение оформления, а не обещание полной проверки переключения образов в этой задаче.

## Проверки

Unit проверяют стабильный код, отсутствие лишнего разделителя, сохранение похожих фраз сотрудника и внутреннего авторства. Интеграционные проверки используют настоящую изолированную PostgreSQL и имитацию MAX: прямой ответ, другая прямая группа, старое неотправленное задание, фото/ссылки/кнопки, повтор и перезапуск, частичные PENDING/FAILED, все ACK без завершения, неизвестный старый шаблон и уже доставленное задание. Workflow запускается только по push в тематическую ветку, без deploy и производственных секретов.

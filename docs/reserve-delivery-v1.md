# Резерв совместимости deliveryProgress v1

Это отдельная ветка `codex/reserve-delivery-v1` для ревью резервного приложения.
База: **8dcfa330183e47551446d10cabbd3b493a42ea0b**.
Новая версия, с которой проверяется обмен состоянием:
**bbfa7b91c3a149d8951d36a28aefbe9b8e3ffa6c**.
В main эту ветку как обычную доработку не сливать. Образ не собран,
производственное переключение не выполнено и этой инструкцией не разрешается.

## Назначение и ограничения независимости

Прежний неизменённый 8dcfa330 не читает сохранённые подтверждения частей.
Запускать его поверх незавершённого `deliveryProgress` небезопасно:
он может повторить уже доставленные части. Наличие старого образа само по себе
не обеспечивает безопасный откат.

Резерв сохраняет разделённые циклы отправки текста и дополнительных вложений
из 8dcfa330. К ним добавлены совместимый план v1, сохранение каждого ACK и
пропуск подтверждённых частей до загрузки вложений. В main используется
единый цикл по индексу части. В резерве также строже проверяются сохранённые
MID и владение попыткой непосредственно перед отправкой.

**Это не независимая реализация доставки.** Большая часть защиты, учёта и
связанных вызывающих методов перенесена из новой версии. Десять из одиннадцати
изменённых runtime-файлов совпадают с bbfa7b9; отличается
`src/max/max-message.service.ts`. Сам этот файл также содержит значительные
общие участки. Разделение циклов не доказывает, что резерв исправит любой
будущий дефект нового цикла: нужна конкретная воспроизводимая неисправность.

Резерв подходит для продолжения текущей очереди при дефекте, изолированном
в новом едином цикле отправки, если тот же сценарий проходит в резерве.
Проверена совместимость сохранённого состояния при временных отказах MAX,
остановке обработчика и сбое итогового учёта. Не покрываются общие дефекты
планирования, загрузки файлов, SDK, БД, CAS, учёта результата, обновления
карточек, проверок прав или самого формата v1. Не устраняются недоступность
MAX, отказ прав, повреждение данных или недостаток ресурсов.

Если причина новой неисправности относится к общему коду или неизвестна,
переключение на резерв нельзя считать исправлением. Минимальная альтернатива —
локализованный совместимый фикс поверх v1 с отдельным воспроизведением;
очередь и текущую БД сохраняют. Повтор с нуля, удаление progress и фиктивный
SENT альтернативой не являются.

## Объём backport относительно 8dcfa330

| Файлы | Необходимая зависимость |
| --- | --- |

| `src/max/max-client.ts` | Проверка перед фактической попыткой, в том числе после ожидания ограничителя MAX |
| `src/delivery/requester-delivery.service.ts`, `delivery-status.ts` | Терминальный `failed`, безопасный индивидуальный повтор актуального ответа, отличие подтверждения от постановки в очередь |
| `src/review/review.service.ts`, `src/answers/answer.service.ts` | Нет успешного уведомления при failed; учёт актуальной доставки |
| `src/bot/callbacks/incident.callbacks.ts`, `commands/index.ts`, `handlers/operator.handler.ts` | Те же результаты в общем и личном рабочем сценарии, защищённый /resend |
| `src/incidents/incident-history.service.ts`, `src/bot/views/history.ts` | Тип и отображение уже существующей в main записи запроса повтора доставки; новая подсистема истории не вводится |

Помимо этого добавлены/перенесены относящиеся к доставке тесты и настоящий
двухверсионный тест переключения. Общие правила shutdown, claim/wake,
порядок адресата, backoff, лимиты, права и остальные сценарии 8dcfa330
сохранены. Схема Prisma, миграции, зависимости, lock-файл, Dockerfile и
Compose не изменены. Другие материалы main и PR №5 не переносились.

## Инварианты формата и учёта

- `deliveryProgress = {version: 1, planHash, totalParts, mids}` хранится в JSON
  задания; миграция не требуется. План и его хеш совместимы с bbfa7b9.
- Проверяются версия, хеш, число частей, массив непустых уникальных MID и
  согласованность с известными `firstMessageId`/`keyboardMessageId`.
  Явный `null` вместо progress не равен старому заданию без этого поля.
- Отправка и запись ACK защищены состоянием, номером попытки, lease и
  сохранённым payload. При утрате владельца чужой прогресс не перезаписывается.
- Все ACK без итогового учёта позволяют завершить учёт без повторной отправки.
  `deliveredAt`, `ANSWER_SENT` и уведомление об успехе возникают только после
  подтверждённого результата актуального ответа, а не просто после enqueue.
- При смене ответа/назначения старая отправка прекращается. Обновление
  частичной карточки использует подтверждённую часть текста с клавиатурой;
  полный длинный текст не записывается в первый фрагмент. Если кнопки уже
  отправлены, устаревшие действия снимаются и при недоставленных вложениях.
- FAILED автоматически не возобновляется, в том числе служебные задания с
  `MANUALLY_RETIRED_FOREIGN_BOT_ADDED`. Индивидуальный /resend применим только
  по обычным правам и проверкам актуальности, после устранения причины.
- Неизвестный/повреждённый progress останавливается без отправки по догадке.
  Данные сохраняются; требуется отдельный разбор. Продолжение очереди не
  означает успешную доставку этого задания.

**Потерянный ACK остаётся неопределённостью.** Если MAX принял часть, а ответ
потерян либо подтверждение не удалось сохранить из-за смены владельца,
эта часть может повториться. Сохранённый подтверждённый префикс не повторяется,
но exactly-once для всей внешней отправки без идемпотентности MAX не обещается.
Проверены оба окна: потерянный ответ и отказ CAS после принятой отправки.

## Результаты и воспроизведение

Среда: локальные Node 22.12.0, PostgreSQL 16.15, имитация MAX, синтетические
данные. Не использовались рабочий сервер, токен, обращения или MAX API.
`reserve-switch.test.ts` загружает настоящий собранный класс отправителя
bbfa7b9 из отдельной чистой копии; второй класс — код резерва. Между фазами
БД не очищается, старый worker останавливается и ожидается `waitForIdle()`.
Границы сбоев синхронизированы барьерами, без произвольных sleep.

Матрица переключения: **20/20**. Проверены:

1. Старые задания без progress; снятое служебное FAILED не изменяется.
2. Длинный текст, девять фото и файл: main → частичные ACK → резерв → новые
   частичные ACK → main; сохранены порядок, backoff и следующее задание.
3. SENDING после сбоя записи ошибки: действующий lease не отбирается;
   после остановки владельца и моделирования истечения lease отправка продолжается.
4. Частичный FAILED остаётся терминальным; два конкурентных разрешённых
   /resend не удваивают отправку, историю и успешное уведомление.
5. Все ACK записаны, итоговая транзакция не завершена: учёт без повторных частей.
6. Восемь вариантов повреждённого progress/MID: отправок нет, payload сохранён.
7. Новый ответ и новое назначение прекращают старую доставку; очередь продолжается.
8. Потеря владельца до MAX и после принятого MAX сообщения; чужой прогресс сохранён.
9. Остановка во время отправки действительно дожидается ACK, затем переключение.
10. Частичная карточка с кнопками и недоставленными фото: смена закрепления,
    доработка, обновление нужного MID и снятие старых действий; FAILED сохранён.
11. Потерянный ACK: проверено возможное повторение только неподтверждённой части.

Unit: **545/545**. Typecheck и build проходят. Расширенная интеграция:
**114/115**, семь файлов. Единственное падение —
`commits registration, history, consumed draft and both outgoing messages together`
в `transactional-workflow` с `Черновик уже подтверждён или устарел`.
Тот же тест отдельно повторён на неизменённом bbfa7b9 в той же среде и падает
с той же ошибкой. Это отдельный сценарий регистрации, не тест региональной
доставки; его ожидания не изменены. Полный набор не объявляется зелёным.

| delivery-reliability | 28/28 |
| delivery-review-regressions | 16/16 |

При общем прогоне найден также дефект подготовки готовых заданий: PostgreSQL

Проверки будущего backoff сохранены. Runtime-часы и задержки не изменялись.

Для повторения сначала подготовить чистую копию bbfa7b9 и собрать её локально
по lock-файлу. В отдельной копии резервной ветки установить зависимости по
lock-файлу и сгенерировать Prisma Client. Затем, например в PowerShell:

```powershell
# Только выделенная тестовая БД: тесты сбрасывают её синтетические данные.
$env:TEST_DATABASE_URL = '<URL_ИЗОЛИРОВАННОЙ_POSTGRESQL>'
$env:DELIVERY_REFERENCE_ROOT = '<ЧИСТАЯ_СОБРАННАЯ_КОПИЯ_bbfa7b9>'
$env:BOT_TOKEN = 'test-token'
npm run typecheck
npm run build
npx vitest run tests/unit
npx vitest run tests/integration/reserve-switch.test.ts tests/integration/delivery-reliability.test.ts tests/integration/delivery-review-regressions.test.ts tests/integration/transactional-workflow.test.ts tests/integration/parallel-outbox.test.ts tests/integration/sector-card-status.test.ts tests/integration/max-photo-delivery.test.ts
```

Интеграционные тесты без TEST_DATABASE_URL пропускаются общей тестовой
инфраструктурой — такой запуск не подтверждает готовность резерва.
Для матрицы обязателен DELIVERY_REFERENCE_ROOT; чистота исходников и точный
SHA проверяются тестом. Перед запуском нужно заново собрать reference dist,
чтобы не использовать случайно устаревшие скомпилированные файлы.

## Порядок будущего переключения

Это контрольный порядок, а не готовая команда установки на конкретный сервер.
До разрешённой установки нужны проверенные образы и отдельный PLAN с
фактическими путями/ID. Настоящий резерв пока проверен на уровне кода и БД.

1. Подтвердить, что воспроизведённый дефект новой версии отсутствует в резерве.
   Если причина общая или не установлена, не объявлять переключение лечением.
2. Проверить точные SHA/digest обоих образов, схему, конфигурацию запуска,
   текущую БД, хранилища и возможность возврата. Сохранить конфигурацию,
   свежую проверенную копию и технический снимок очереди без публикации секретов.
   Снимок включает ID заданий, статусы, attempts/lease, план/MID, версию ответа,
   назначение и соответствующие записи учёта. FAILED также включаются.
3. Штатно завершить **только app**, дождаться завершения обработчиков и worker.
   В исходниках shutdown ждёт производителей и исходящую очередь. Действующий
   grace period необходимо проверить: тайм-аут процесса нельзя заменять
   предположением об успешной остановке. Не запускать одновременно два приложения.
4. После подтверждённого завершения снять финальную текущую БД и вложения,
   зафиксировать очередь повторно. Проверить таблицу решений ниже. При
   некорректном progress, неизвестном владельце, неоднозначной отправке либо
   незавершившемся shutdown остановить переключение и разбирать конкретный ID.
   Это не разрешение стирать progress или произвольно освобождать lease.
5. Заменить только образ app с текущей БД. Сохранить runtime.env, webhook,
   токен, mounts, журналы и резервирование; не запускать миграции. Не брать
   репозиторный Compose как замену фактическому: его значения по умолчанию
   могут выбрать другую БД, а command содержит автоматический migrate deploy.
   PostgreSQL и прокси не пересоздавать. Использовать заранее проверенную
   временную конфигурацию с единственным изменением образа.
6. Ограниченно ждать health/ready (например, до 120 секунд с шагом 2 секунды
   в эксплуатационном скрипте). При исчерпании времени — ошибка, диагностика
   контейнера/БД и shutdown, а не бесконечное ожидание или автоматический
   запуск ещё одного экземпляра. Тайм-аут сам по себе не доказывает дефект.
7. Сверить ID и сохранность обращений, ответов, истории, вложений, прогресса,
   рабочих карточек и очередей. Штатные переходы и новые события проверять по
   истории. Убедиться, что очередь продолжает порядок адресата, подтверждённые
   MID не отправляются снова, а FAILED не ожили. Health/ready этого не заменяют.
8. Проверить разрешённый ручной сценарий и обновить метаданные резервирования
   только после технического успеха. Старый дамп поверх текущих данных не восстанавливать.

| Состояние после остановки | Допустимое действие |
| --- | --- |
| Нет незавершённой отправки, нет неподтверждённого учёта | Запуск проверенного совместимого образа; исторические данные сохранить. Старый 8dc не считать автоматически проверенным для этой БД |
| PENDING с корректным подтверждённым префиксом | Резерв продолжает после `nextAttemptAt`; не сдвигать backoff вручную ради ускорения |
| SENDING с корректным префиксом | Подтвердить завершение прежнего владельца; дождаться штатного истечения lease и захвата. Не отбирать живой lease |
| FAILED с префиксом | Оставить FAILED. После установления причины — только индивидуальный авторизованный повтор актуального ответа. Снятые приветствия не повторять |
| Все ACK, итоговый учёт отсутствует | Совместимый обработчик завершает учёт без новых отправок; проверяются deliveredAt/ANSWER_SENT/уведомление |
| Неизвестная версия, план не совпал, MID повреждён | Не отправлять по догадке. Сохранить состояние, блокировать автоматическое переключение до оценки конкретного задания |
| MAX принял часть, но ACK не сохранён | Признать неопределённость. Нужна отдельная проверка конкретной отправки/возможности повтора; не обещать отсутствие дубля |

Возврат **резерв → bbfa7b9** выполняется теми же шагами на текущей БД. Формат
корректного v1 общий, двунаправленное продолжение проверено. Это не разрешение
запускать исходный 8dcfa330 с незавершённым progress. У main менее строгий
разбор некоторых повреждённых значений; терминальное повреждённое задание
нельзя затем вслепую повторять вручную на main. Невалидные состояния требуют
отдельного решения до допуска переключения, их нельзя «исправить» удалением поля.

## Что ещё проверить на готовых образах

- Чистая сборка обоих кандидатов из зафиксированных SHA/lock, ревизия образа,
  фактические файлы dist, Node/Prisma/SDK, CA и доступ к вложениям. Никакой
  проверки производственного образа в рамках этой работы не выполнено.
- Повторить матрицу той же PostgreSQL между **контейнерами**, включая SIGTERM,
  реальный stop grace, исключение второго процесса и отказ запуска нового.
- Проверить HTTP-границу SDK с локальным mock MAX, 429/5xx, сетевой обрыв и
  потерянный ACK. Здесь использована имитация методов клиента, не живой MAX.
- Проверить readiness, права/mounts/сеть, сохранение текущих настроек и ротации,
  сверку финальной копии восстановлением и возврат при ошибке создания app.
- На предполагаемом дефекте новой версии отдельно доказать, что резерв его
  обходит. Без этого подготовлен совместимый кандидат, а не универсально
  безопасный аварийный выход.

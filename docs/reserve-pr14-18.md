## Объём и независимость

Перенесён прикладной diff PR №14–18 поверх прежнего резерва, включая обе миграции,
служебные состояния экранов, отображение телефона, исправления карточек и навигации.
Исходный механизм резерва сохранён: отдельный цикл текста, отдельный цикл групп
вложений, общая фиксация ACK после каждой части. Подтверждённые части пропускаются
до загрузки файлов. Дополнительно проверяются пустой/неизвестный progress, повтор MID,
соответствие firstMessageId/keyboardMessageId и точное владение payload/lease.
Прикладной diff против основного кандидата ограничен max-message.service.ts.

Это вариант для локализованного дефекта единого цикла отправки частей основной
версии, если резерв прошёл конкретный воспроизводящий сценарий. Он не независим
от общего планировщика частей, planHash, MAX SDK, загрузчика, rate limits,
учёта deliveredAt/ANSWER_SENT, схемы, прав, UI, сроков и файловых защит. Общие
ошибки этих механизмов он не исправляет; переключение без диагноза не гарантирует
восстановления. Неизвестный ACK остаётся неопределённым и может дать физический дубль.

## Схема и политика

После схемы 59149006 нужны ровно:
- 20261007120000_working_hour_policy;
- 20261007160000_working_deadline_disposition.

Старые строки остаются LEGACY с прежними сроками. Новая таблица IncidentAssignmentCycle,
поля политики/доставки, DEFERRED/CANCELLED и причины отмены обязательны обеим версиям.
Миграции и runtime не запускают самостоятельную активацию V1. INCIDENT_SLA_POLICY
сохраняется при смене образа; резерв читает ту же конфигурацию. Для новых регистраций
V1 включается только отдельным явным решением владельца. Старые черновики получают
политику на явном подтверждении регистрации, не при просмотре. 24/22/2 рабочих часа,
понедельник–пятница 08:00–17:00 МСК — как в принятом PR №15, без новых правил.
FAILED и CANCELLED терминальны; DEFERRED не удерживает обычные сообщения до своего
срока, но после наступления срока подчиняется сериализации адресата. Progress v1
и порядок частичных обычных отправок сохранены.

## План будущего переключения — не команды применения

1. Отдельно подготовить эксплуатационный комплект для этих точных SHA/image ID,
   актуального installed 59149006 и двух эталонов схемы. Повторно сверить фактическую
   установку и решить, остаётся LEGACY или явно активируется V1. Оба образа должны
   использовать одинаковый policy env, mounts, webhook и БД. Один бот в каждый момент.
2. Проверенная свежая копия БД + вложений + конфигурации; состояние очередей по ID
   (включая progress, FAILED, DEFERRED, CANCELLED), истории, черновиков и файловых fences.
   Под проверенным flock штатный SIGTERM только app; дождаться drain без SIGKILL.
   Пока остановка не доказана, другой контейнер не запускать. Финальный снимок.
3. До миграции записать/fsync намерение. С этого момента прежний 59149006 НЕ является
   разрешённым автоматическим откатом, даже без applied.json и со старым Compose.
   Выполнить две миграции один раз и строго проверить identity, историю (включая только
   две известные CRLF-альтернативы), завершённость и новый эталон структуры.
   Неизвестный/частичный результат — остановка для разбора; не migrate resolve наугад.
4. После подтверждённой схемы заменить только образ, запуск одного app, ограниченное
   ожидание health/ready с диагностикой. Проверить очереди, записи/циклы/черновики,
   фотографии/панели, подтверждения доставки и изменения от новых пользователей.
   При доказанном отказе новой версии и успешной остановке — совместимый резерв,
   та же текущая БД/политика. Старый дамп поверх новых данных не восстанавливать.
5. Отказ создания/старта требует доказать отсутствие работающего кандидата. Неизвестный
   результат запуска/миграции/отправки не превращать в успех. Не удалять progress,
   служебные записи, задания и fences; не возобновлять FAILED/CANCELLED вручную.
6. После технического успеха обновить metadata резервирования на реальный image/SHA,
   освободить backup.lock и сделать итоговую проверенную копию. Ручные проверки владельца:
   REGION_KALUGA, распределение/возвраты, сроки новых и старых записей, фото/телефон/история.

## Инструменты установки и резервирования

Старый комплект 60a9056 / R4 сам по себе НЕ готов для этих версий. migration_guard.py
закрепляет old=8dcfa330, main=59149006, reserve=1a7a0f5 и соответствующие manifest old/new.
Нужно отдельно переиздать проверенный комплект с правильной тройкой SHA и эталонами,
расширить снимки/сверки таблицей циклов, полями SLA и состояниями очереди, проверить
migration-intent до применения, отказ старого resume и возврат при ошибке запуска.
Эксплуатационные скрипты в этой ветке не меняются. Полный pg_dump/pg_restore сохраняет
новые записи и защитные триггеры; выборочный старый SQL-снимок может пропустить циклы.
Старые проверки только PENDING/SENDING/SENT/FAILED недостаточны. Нужно считать
DEFERRED отдельно с nextAttemptAt, CANCELLED отдельно с причиной, без фиктивного SENT.
Реальные server paths, Compose, права и таймер проверяются только будущим разрешённым
этапом; лабораторный запуск не аттестует их автоматически.

## Проверки и ограничения

Actions: real PostgreSQL + local HTTP MAX mock; основной/резервный runtime images
собираются из git archive закреплённых SHA по package-lock. dist, Prisma и lock внутри
runtime сравниваются с build stage; допустимое compiled различие — только transport.
Изменённые сценарии PR №14–18 и прежние целевые progress/retention/inbox регрессии
проверяются на резерве; полные старые матрицы R4 и bulk benchmark не повторяются.
Контейнерный стенд переиспользует проверенный isolated internal network; readiness
проверяется внутри namespace через настоящий HTTP, опубликованных внешних портов нет.
Для ночного/понедельничного сценария только тестовый preload задаёт часы процесса;
runtime image не содержит preload и не модифицируется. Данные полностью синтетические.
Сохранённые состояния экранов проверяются при переключении, клики — интеграционным MAX
mock в целевых файлах. Фактическая доступность старых сообщений в живом MAX не проверяется.
Результаты и image ID публикуются отдельным отчётом после прогона. Установка не разрешена.

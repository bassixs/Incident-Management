# Ежедневная копия: только закрытый локальный архив

ROOT — фактический закрытый каталог новой установки; KIT — эта новая проверенная редакция. Команды ниже выполняются в `sudo -i`, без `set -x`. Не применять их на исходной установке со старыми settings. Шифрование и выдача — отдельные этапы. Не создавать HTTP-раздачу, отдельный сервис скачивания, SFTP-пользователя или GPG-ключ автоматически.

## После завершения передачи

```bash
python3 "$KIT/scripts/operations.py" --root "$ROOT" backup --manual
```

Создаётся новый `$ROOT/backups/UTC-МЕТКА-СЛУЧАЙНЫЙ-ID/` и единый `$ROOT/backups/UTC-МЕТКА-СЛУЧАЙНЫЙ-ID.tar.gz`, рядом `.sha256`. ROOT 0700, архив 0600/root. Внутри dump, все файлы и конфигурация (СЕКРЕТЫ), v2 индексы/отпечатки всех полей, точная схема и доказательства изолированного восстановления. Публично не передавать. Отдельный каталог свидетельств сохраняется вместе с архивом — автоудаления нет, расход места растёт. Для свободного места учитывать dump, два SQLite-индекса, восстановленную PG, исходный каталог и итоговый архив; недостаток места — отказ, не очистка.

Снимок dump и отпечатков единый. Проверка всех строк/полей, истории миграций/триггеров и файлов обязательна. При изменении файла во время работающей копии попытка может быть отвергнута; автоматически повторять или ослаблять проверку нельзя. CPU/RAM экспортёра 0.5/384m, проверочной PG 0.5/768m; снимок не запускает восстановленный бот. backup.lock общий с start/stop/supervise; занятая блокировка означает отказ текущего запуска, не ошибку бота.

## Проверить последний результат

```bash
sudo python3 -m json.tool "$ROOT/state/backup-last-attempt.json"
sudo python3 -m json.tool "$ROOT/state/backup-success.json"
```

`backup-last-attempt.json` показывает последнюю начавшуюся попытку; `backup-success.json` — последнюю подтверждённую успешную (при отказе не перезаписывается). Проверить UTC `at`, `status=SUCCESS`, `restoreDifferences=0`, `archive`, `sha256`, `elapsedSeconds`. Не путать старый успех с сегодняшним отказом. При отказе до входа в операцию (например, занятый lock) факт находится в журнале systemd, а last-attempt может остаться прежним. Проверять оба источника и свежесть — успех должен быть не старше 26 часов для ежедневного режима.

```bash
cd "$ROOT/backups"
sha256sum -c ИМЯ_ТОЧНОГО_АРХИВА.tar.gz.sha256
# Полный dump не выводить в терминал. Проверка доказательств внутри:
tar -xOf ИМЯ_ТОЧНОГО_АРХИВА.tar.gz backup/restore-result.json
tar -xOf ИМЯ_ТОЧНОГО_АРХИВА.tar.gz backup/restore-differences.json
```

Ожидается databaseRows/schema/files=`exact`, differenceCount=0. Ошибка, отсутствие или неполный архив не являются копией. `.partial` сохраняется для разбора; удалять или переименовывать его вручную в успешный архив нельзя.

## Расписание и доступ

Таймер создаётся командой `operations.py ... units`, устанавливается только после передачи по RECOVERY.md. Расписание 03:15 Europe/Moscow; `Persistent=true` выполняет пропущенный запуск после загрузки. Включённый таймер сам по себе не даёт разрешения: требуется host-ownership. Перед плановым переносом сначала отключить ownership/таймер, дождаться окончания текущей копии, не прерывать её.

```bash
systemctl list-timers "${PROJECT}-backup.timer"
systemctl status "${PROJECT}-backup.service" --no-pager
journalctl -u "${PROJECT}-backup.service" --since '2 days ago' --no-pager
```

Ответственный специалист получает доступ через согласованный sudo. Обычным пользователям доступ к ROOT не давать, права 0700/0600 не расширять. Конкретный приватный лист содержит подтверждённую учётную запись и путь. Если нужен перенос архива в личный каталог, из root-shell создать НОВЫЙ приватный каталог 0700, скопировать только выбранные `.tar.gz` и `.sha256`, назначить владельца получателя и 0600 файлам. Не выдавать доступ ко всей конфигурации другим пользователям и не публиковать каталог. Архив содержит токены; дальнейшая выдача наружу только после согласования защищённого канала/шифрования.

Обязательных SFTP/GPG для ежедневной копии нет. Настраиваемый этап шифрования — ENCRYPTION.md; до согласования не исполнять. Вечерняя финальная передача через согласованное облачное хранилище остаётся отдельной процедурой, с шифрованием и отдельным ключом. Локальная ежедневная копия на том же диске не защищает от потери всего сервера: подтверждённое скачивание ответственным необходимо учитывать отдельно, автоматически его успех не объявлять.

# Отдельная защищённая передача финальных данных

Сейчас финальный пакет не создаётся. Программный ZIP содержит только проверенные образы, инструменты, эталон и синтетические протоколы. runtime.env, дамп, SQLite-отпечатки/ID записей и реальные вложения — только в шифрованном пакете.

После вечерней команды: штатная остановка источника по его актуальному 40967e2 плану, capture финальной копии и изолированный verify. Под штатным backup.lock сверить тот же CID и отсутствие обработки. Для источника используются его действующие приватные settings и реальный новый stop-receipt; команда seal:

```bash
python3 "$KIT/scripts/seal-source.py" --backup "$FINAL" --stop-receipt "$STOP_RECEIPT" --output "$STAGE/source-fence.json"
```

STAGE — новый закрытый каталог, FINAL — только что проверенная копия. В STAGE/final поместить саму FINAL, без старых комплектов/журналов установки. Не переносить settings/install receipts, ключи SSH, старый PGdata или сертификаты старого домена. Не считать дневную копию финальной. Приватный исходный план остаётся у владельца.

Предпочтительно получить публичный GPG-ключ специалиста и подтвердить полный fingerprint независимым каналом. В закрытом staging, с umask 077 и pipefail:

```bash
set -o pipefail
umask 077
tar -C "$STAGE" -czf - final source-fence.json effective-runtime.env | gpg --encrypt --recipient "$VERIFIED_FINGERPRINT" --output "$OUT/final-transfer.tar.gz.gpg"
sha256sum "$OUT/final-transfer.tar.gz.gpg" > "$OUT/final-transfer.tar.gz.gpg.sha256"
```

Если согласована симметричная передача: вместо --encrypt/--recipient использовать `--symmetric --cipher-algo AES256`; вводить сильную случайную парольную фразу интерактивно через pinentry, передавать отдельно от Диска. Не указывать passphrase в аргументах/файле workflow/чате. Не отключать MDC/проверку целостности, не использовать ZIP-пароль. На Диск — только .gpg и .sha256, ключ/пароль отдельным каналом. SHA-256 дополнительно сообщить независимо от Диска.

На цели: umask 077; sha256sum -c .sha256; расшифровать в НОВЫЙ закрытый каталог. Сначала `gpg --output "$IMPORT/final-transfer.tar.gz" --decrypt ...` и проверить exit 0; только после успешной аутентификации распаковывать. Не соединять decrypt напрямую с tar: повреждённый шифротекст не должен начать восстановление. Список tar заранее проверить (только относительные final/... и source-fence.json/effective-runtime.env, без ссылок, абсолютных путей, ..); распаковать без сохранения владельцев/прав в закрытый IMPORT. Внешние суммы не заменяют внутренние checksums.json и сверку после восстановления.

После передачи хранение/удаление открытых временных файлов согласовать отдельно; текущая процедура ничего на исходном сервере не удаляет. Обратная передача использует такую же схему и свежую копию ТЕКУЩЕЙ целевой БД.

GnuPG: https://www.gnupg.org/documentation/manuals/gnupg24/gpg.1.html

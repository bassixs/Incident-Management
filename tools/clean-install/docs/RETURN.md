# Возврат и выбор совместимого резерва

Резерв 3c5c38b0 сохраняет текущую схему, SLA V1 и раздельный цикл отправки. Он разделяет с основной версией проверку progress, ACK, права, триггеры, inbox и значительную часть runtime; не лечит общие дефекты, инфраструктуру, MAX 403 или неизвестный ACK. При потерянном ответе MAX возможен дубль неподтверждённой части; сохранённые ACK повторять нельзя.

## Отмена ДО любой попытки старта целевого приложения

На цели `clean.py --root ROOT status`; только verified/start-failed при everStartAttempted=false допустимы. `clean.py --root ROOT abandon` создаёт окончательный abandon-proof.json, блокирует дальнейший start этой операции. Передать доказательство и подтверждение специалиста владельцу; один JSON не доказывает фактическое отключение другого хоста. Если CREATE/START имеет неизвестный результат или остался intent/partial record — остановиться на разбор, не создавать новую операцию для обхода.

Владелец на источнике под прежним backup.lock проверяет: тот же полный CID из source-fence, прежний image/start/restart/config, clean stop, отсутствие второго экземпляра; целевой оператор подтвердил abandon и отсутствие запуска. Вернуть подписку на исходный URL, если её меняли, проверить GET /subscriptions. Затем разрешённое владельцем `docker start ПРЕЖНИЙ_ПОЛНЫЙ_CID` без пересоздания и восстановления БД; проверить health/ready. Это отдельная явная команда оператора, не автоматический эффект target abandon. Источник использует свою текущую БД. После возобновления все ранее подготовленные финальные пакеты устаревают: следующий перенос требует новой остановки/копии/fence. На стенде проверены фактический start того же CID и повторный SIGTERM, а также отказ старта abandoned цели. Межсерверный запрет обеспечивает согласование двух операторов.

## Ошибка основной версии после создания/попытки запуска

При известном отказе create/start и `start-failed` можно явно выбрать резерв с текущей БД:
`clean.py --root ROOT start --role reserve --confirm-source-stopped HANDOFF`.
Если приложение ещё работает (включая timeout ready), сначала диагностика; затем только штатный `clean.py --root ROOT stop` и подтверждение clean exit. Никаких SIGKILL и принудительного обхода state. Возврат на основную: stop, затем start --role main. Обе используют одну текущую БД/uploads. FAILED/CANCELLED не изменяются вручную.

## Возврат ПОСЛЕ любой попытки запуска на цели

Даже если ready не наступил, могли появиться новые данные или уйти сообщения. Запуск прежней исходной БД запрещён. Сначала штатно остановить цель, `snapshot.py --root ROOT --output НОВЫЙ_КАТАЛОГ --final` с успешным восстановлением. `seal-source.py --backup КОПИЯ --stop-receipt ROOT/state/stop-receipt.json --output НОВЫЙ_ENVELOPE` формирует новое ограждение для обратного переноса. Рабочие настройки сохраняются в зашифрованной копии, старые install receipts не импортируются.

На исходном сервере используется НОВАЯ пустая БД в отдельном окружении; старую БД не перезаписывать и старый app не запускать. Присоединение к существующему Caddy описано ниже; второй Caddy с конфликтующими портами не создавать. Неизвестный результат отправки/удаления остаётся неизвестным; progress не сбрасывать, фиктивный SENT запрещён.

## Обратный перенос с действующим Caddy, без остановки остальных сервисов

Все команды будущие, только после отдельного разрешения владельца. Реальные параметры источника находятся в приватном листе, не в публичном архиве. Проверить их чтением непосредственно перед операцией: CID/image/start/restart существующего Caddy, Mounts конфигурации/сертификатов, его Docker-сеть и все текущие upstream/маршруты. Другие сайты, документы, контейнеры, тома и БД сохранять. При расхождении приватного листа остановиться; прежний файл не считать текущим автоматически.

1. На цели выключить host-ownership и таймеры (RECOVERY.md), дождаться текущих handlers/копии, штатно stop. Создать НОВУЮ финальную snapshot.py --final, полное восстановление/сверка=0, seal-source.py. Сохранить disabled на целевом сервере через перезагрузку; проверить, что там не действует иной restart/watchdog. Неизвестный stop или непроверенная свежая копия запрещают продолжение.
2. Передать зашифрованные текущие данные/настройки/fence с SHA, не дневную копию. Проверить полученные файлы. На источнике новое пространство ROOT_RETURN и уникальный алиас EDGE_ALIAS, свободный loopback PORT. Старую БД/приложение оставить остановленными. Использовать ТОЧНЫЕ main/reserve образы и эту редакцию KIT.

```bash
python3 "$KIT/scripts/clean.py" --root "$ROOT_RETURN" init --domain "$SOURCE_DOMAIN" --pg-image "$PGID" --caddy-image "$CADDYID" --port "$PORT" --edge-network "$EDGE_NETWORK" --edge-alias "$EDGE_ALIAS"
python3 "$KIT/scripts/clean.py" --root "$ROOT_RETURN" infra
python3 "$KIT/scripts/clean.py" --root "$ROOT_RETURN" restore --backup "$IMPORT/final" --envelope "$IMPORT/source-fence.json"
```

edge mode запускает только новую PG, создаёт собственные db/front сети; приложение дополнительно подключается к существующей сети Caddy с уникальным алиасом. Не подключать новую PG к сети чужих приложений. Проверить отсутствие совпадающего алиаса. Новые данные/файлы/схема проверяются полностью. app пока не запускать; Caddy ещё без изменений.

3. Подготовить только три точные директивы bot upstream (число сверить с фактическим файлом). Программа не применяет конфигурацию:

```bash
python3 "$KIT/scripts/prepare-route.py" --config "$CADDYFILE" --sha256 "$CURRENT_CADDY_SHA" --old "$OLD_UPSTREAM:3000" --new "$EDGE_ALIAS:3000" --count "$BOT_ROUTE_COUNT" --output "$NEW_ROUTE_REVIEW_DIR"
diff -u "$NEW_ROUTE_REVIEW_DIR/Caddyfile.before" "$NEW_ROUTE_REVIEW_DIR/Caddyfile.candidate"
```

Должны меняться только upstream /webhook/*, /health, /ready. Никаких изменений /documents/* и других сайтов. Сходные строки, дополнительные параметры или неизвестное число директив приводят к отказу; вручную не ослаблять проверку. Проверить candidate штатным `caddy validate` на текущем Caddy image, без публикации портов; validate должен учитывать все import/env/сертификаты реальной конфигурации. Если присутствуют неучтённые зависимости, сначала дополнить приватный план и ревью, не подменять их пустыми.

4. Владелец повторно подтверждает остановку цели. По WEBHOOK.md выполнить согласованное переключение подписки на SOURCE_DOMAIN, GET сверку. При неизвестном результате — GET/reconcile, не повторять вслепую. Запустить новое приложение на ТЕКУЩИХ восстановленных данных:

```bash
python3 "$KIT/scripts/clean.py" --root "$ROOT_RETURN" start --role main --confirm-source-stopped "$NEW_HANDOFF"
```

Проверить 127.0.0.1:PORT/health и /ready, единственный BOT_TOKEN экземпляр и точный образ. При известной ошибке создания/старта — совместимый reserve на этой же БД. После любой попытки запуска здесь также возможны новые записи, даже без readiness.

5. Перед применением candidate ещё раз сверить SHA активного файла с route.json.beforeSha256 и CID/start/restarts Caddy. Сохранённый before — отдельный файл, не старый неизвестный backup. Записать candidate в существующий bind-файл **с сохранением inode**, fsync, проверить SHA candidate. Затем `docker exec "$CADDY_CID" caddy reload --config /etc/caddy/Caddyfile`. Это reload конфигурации, не restart контейнера. Подробные команды с закрытыми путями — в приватном листе. При отказе reload: сначала прочитать/сверить активную конфигурацию Caddy локально, без публикации. Если результат точно не применён, вернуть сохранённый before только при всё ещё совпадающем candidate SHA; если неизвестен или файл изменён посторонним — остановиться и разобрать, не затирать.
6. С другого подключения проверить TLS /health /ready, webhook подписку GET, поступление реальных событий и движение очереди; прочитать неизменный /documents/* и проверить другие сервисы. Зафиксировать неизменность CID/start/restarts Caddy и прочих контейнеров. Не создавать обращения ради теста. Закрепления и MID панелей берутся из свежей БД, не пересоздаются массово.
7. После технического успеха — новая проверенная копия, согласованная активация автозапуска/ежедневного таймера именно ROOT_RETURN. Старый таймер бота с прежней БД требует отдельного адресного отключения/согласования; таймеры других проектов не менять. Назначить внешний мониторинг.

Если обратный перенос неудачен ПОСЛЕ попытки запуска ROOT_RETURN, нельзя включить прежнюю БД на цели: штатно остановить ROOT_RETURN, снять его ТЕКУЩУЮ проверенную копию и выполнить ещё один защищённый перенос. История не откатывается. До любой попытки старта ROOT_RETURN можно abandon и явно возобновить тот же cleanly stopped целевой контейнер с его текущей БД, вернув подписку и сохранив fence на источнике. Сам Caddy rollback не является откатом данных.

При неизвестной остановке/невозможности сделать проверенную текущую копию обратный перенос не разрешать. Сохранить диагностику и согласовать восстановление доступности; старый dump не использовать поверх новых данных.

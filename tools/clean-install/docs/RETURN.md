# Возврат и выбор совместимого резерва

Резерв 3c5c38b0 сохраняет текущую схему, SLA V1 и раздельный цикл отправки. Он разделяет с основной версией проверку progress, ACK, права, триггеры, inbox и значительную часть runtime; не лечит общие дефекты, инфраструктуру, MAX 403 или неизвестный ACK. При потерянном ответе MAX возможен дубль неподтверждённой части; сохранённые ACK повторять нельзя.

## Отмена ДО любой попытки старта целевого приложения

На цели `clean.py --root ROOT status`; только verified/start-failed при everStartAttempted=false допустимы. `clean.py --root ROOT abandon` создаёт окончательный abandon-proof.json, блокирует дальнейший start этой операции. Передать доказательство и подтверждение специалиста владельцу; один JSON не доказывает фактическое отключение другого хоста. Если CREATE/START имеет неизвестный результат или остался intent/partial record — остановиться на разбор, не создавать новую операцию для обхода.

Владелец на источнике под прежним backup.lock проверяет: тот же полный CID из source-fence, прежний image/start/restart/config, clean stop, отсутствие второго экземпляра; целевой оператор подтвердил abandon и отсутствие запуска. Вернуть подписку на исходный URL, если её меняли, проверить GET /subscriptions. Затем разрешённое владельцем `docker start ПРЕЖНИЙ_ПОЛНЫЙ_CID` без пересоздания и восстановления БД; проверить health/ready. Это отдельная явная команда оператора, не автоматический эффект target abandon. Источник использует свою текущую БД. После возобновления все ранее подготовленные финальные пакеты устаревают: следующий перенос требует новой остановки/копии/fence. На стенде проверены фактический start того же CID и повторный SIGTERM, а также отказ старта abandoned цели. Межсерверный запрет обеспечивает согласование двух операторов.

## Ошибка основной версии после создания/попытки запуска

При известном отказе create/start и `start-failed` можно явно выбрать резерв с текущей БД:
`clean.py --root ROOT start --role reserve --confirm-source-stopped HANDOFF`.
Если приложение ещё работает (включая timeout ready), сначала диагностика; затем только штатный `clean.py --root ROOT stop` и подтверждение clean exit. Никаких SIGKILL и принудительного обхода state. Возврат на основную: stop, затем start --role main. Обе используют одну текущую БД/uploads. FAILED/CANCELLED не изменяются вручную.

## Возврат ПОСЛЕ любой попытки запуска на цели

Даже если ready не наступил, могли появиться новые данные или уйти сообщения. Запуск прежней исходной БД запрещён. Сначала штатно остановить цель, `snapshot.py --root ROOT --output НОВЫЙ_КАТАЛОГ --final` с успешным восстановлением. `seal-source.py --backup КОПИЯ --stop-receipt ROOT/state/stop-receipt.json --output НОВЫЙ_ENVELOPE` формирует новое ограждение для обратного переноса. Рабочие настройки сохраняются в зашифрованной копии, старые install receipts не импортируются.

На исходном сервере подготовить НОВОЕ пустое окружение чистой установки, не перезаписывая старую БД и архивы. После передачи текущей копии повторить init/infra/restore, точную сверку всех данных/файлов, смену подписки и start с новым fence. Для запуска Caddy не должно быть конфликта 80/443 со старым Caddy: конкретное согласованное переключение существующего proxy или освобождение портов — отдельный план оператора. Нельзя автоматически менять старый Caddy этим комплектом. На стенде проверено восстановление в новом пустом окружении и запуск с сохранённой записью, появившейся ПОСЛЕ первой передачи. Неизвестный результат удаления/отправки остаётся неизвестным; не выставлять фиктивный SENT и не сбрасывать progress.

При неизвестной остановке/невозможности сделать проверенную текущую копию обратный перенос не разрешать. Сохранить диагностику и согласовать восстановление доступности; старый dump не использовать поверх новых данных.

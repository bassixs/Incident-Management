# Чистая установка: два этапа

Использовать только комплект, чей ZIP SHA-256 передан владельцем отдельно, и успешный протокол соответствующего toolCommit в VERSION.json. Это новая процедура для пустого сервера, а не повтор установки обновления. Ни один старый applied.json, stop-receipt.json или settings.json не становится разрешением на запуск здесь.

Команды выполняет согласованный администратор из `sudo -i`, без `set -x`. Python >=3.11, Docker с Compose, поддерживающим env_file format:raw (>=2.30), curl, unzip, tar и свободное место обязательны. GnuPG используется отдельно для зашифрованной вечерней передачи; для создания ежедневной локальной копии он не требуется. Путь ROOT должен быть новым пустым каталогом; KIT — распакованный программный комплект. Значения ROOT, DOMAIN и KIT задаются в приватном листе владельца. Пароли и токены в командную строку не вставлять. До второй части runtime.env с рабочим токеном отсутствует.

## 1. Заранее — приложение не запускать

1. Получить программный ZIP и отдельную .sha256; `sha256sum -c clean-install-reviewed.zip.sha256`; распаковать в новый KIT; `cd "$KIT" && sha256sum -c SHA256SUMS`. Прочитать REVIEW.md и проверить успешный report.json. Не извлекать старые установочные пакеты поверх него.
2. Снять показания: `uname -m; cat /etc/os-release; python3 --version; docker version; docker compose version; docker info; df -hT / /home; df -i / /home; free -h; docker ps -a; docker volume ls`. Проверить время/NTP, порты `ss -lntp`, права sudo, свободное место под распаковку, образы, БД, две проверочные копии и SQLite-индексы. Никакой очистки. При неизвестных контейнерах выяснить принадлежность.
3. Фактически проверить DockerRootDir, mount этого каталога (`findmnt -T ПУТЬ`), containerd (`systemctl cat containerd`, его конфигурацию и mount корня хранилища). Docker 29 может держать слои в /var/lib/containerd даже при data-root на /home. Указания администратора о /home/docker-data недостаточно. Не менять daemon/containerd и не перезапускать их по этой инструкции. Если слои идут на малый / — сначала решение администратора, до загрузки.
4. `docker load -i "$KIT/main-and-reserve.tar.gz"`; `docker load -i "$KIT/postgres-and-caddy.tar.gz"`. Сверить два приложения с IMAGE-IDS.json и допустимыми config/manifest ID в scripts/clean.py, revision labels и linux/amd64. PG/Caddy загружаются из того же проверенного архива; сохранить их фактические полные IDs и версии. При несовпадении происхождения/версии — остановка, не скачивать замену по плавающему тегу.
5. Получить PGID и CADDYID через `docker image inspect postgres:16.15-alpine --format '{{.Id}}'` и аналогично `caddy:2-alpine`. Выполнить:

```bash
python3 "$KIT/scripts/clean.py" --root "$ROOT" init --domain "$DOMAIN" --pg-image "$PGID" --caddy-image "$CADDYID"
python3 "$KIT/scripts/clean.py" --root "$ROOT" infra
python3 "$KIT/scripts/clean.py" --root "$ROOT" status
```

Ожидается `infra-ready`, app отсутствует. Создаются новые роли/пароли PostgreSQL, отдельные db/front сети, новые Caddy и persistent mounts. PostgreSQL наружу не публикуется. app позднее публикуется только на 127.0.0.1:3001. Все рабочие данные остаются внутри ROOT. Проверить реальные Mounts и Image через `docker inspect` приватно, права записи, политику Astra/MAC; не отключать защиту ОС. Caddy получает публичный сертификат; хранение /data и /config постоянно. Домен /handover-check должен возвращать challenge из settings.json.
6. Выполнить NETWORK.md, включая внешний HTTPS с другого подключения. На этой стадии не запускать приложение, не регистрировать вебхук, не отправлять сообщения. 502 на маршруте бота до старта ожидаем; `/handover-check` должен давать 200 с правильным challenge. Записать результат, версии, реальные storage paths и запас места, передать владельцу без паролей.
7. До остановки исходного бота подтвердить: успешные пункты 1–6, исправный HTTPS снаружи, сетевой доступ к MAX, возможность безопасно получить архив/ключ, ответственного за резервирование и место второй копии, согласованный способ переключения подписки и обратного переключения. Ключи и внутренние адреса передавать отдельно защищённо.

## 2. Только после команды владельца вечером

1. Владелец штатно останавливает исходный app и делает НОВУЮ финальную копию по действующему комплекту 40967e2. SIGKILL запрещён. Нужны подтверждённое завершение обработчиков, полный dump, файлы, конфигурация, v2 отпечатки и успешное изолированное восстановление с нулём расхождений. Дневную копию не использовать. Seal-source.py создаёт отдельный source-fence.json из финальной копии и фактического stop-receipt; исходные установочные журналы на целевой сервер не переносить.
2. Получить зашифрованный пакет и SHA-256 (ENCRYPTION.md), проверить, расшифровать в новый закрытый IMPORT. В нём каталог final, source-fence.json и effective-runtime.env. Не запускать скрипты из данных. Не копировать runtime.env вручную в Compose.
3. `python3 "$KIT/scripts/clean.py" --root "$ROOT" restore --backup "$IMPORT/final" --envelope "$IMPORT/source-fence.json"`. Требуется пустая БД. Команда восстанавливает без миграций, проверяет точную новую схему/историю, все записи/поля и файлы, создаёт новую identity, сохраняет LEGACY/V1, progress, FAILED/CANCELLED, панели. runtime.env адаптируется только к новой БД, домену, локальному storage, TLS и уже действующей V1; значения старого токена/секрета и бизнес-настроек сохраняются. WEBHOOK_AUTO_REGISTER=false. При отказе не повторять restore поверх частичного результата, журнал не удалять; передать безопасную диагностику владельцу.
4. Пока app ещё отсутствует, выполнить GET /me и получение одобренного вложения из контейнера (NETWORK.md). Проверить реальный публичный сертификат, значения URL/пути webhook и секрет конфиденциально. Старый источник должен оставаться остановленным. Согласовать подписку: сохранить существующий GET /subscriptions приватно, по отдельной команде владельца настроить новый URL с тем же составом update_types и секретом, проверить GET; убрать только прежний URL, если он остался, и снова проверить. Не удалять неизвестные подписки. Если результат POST/DELETE неизвестен — сначала GET, без слепого повтора. Комплект сам подписки не меняет. См. WEBHOOK.md.
5. Вновь получить подтверждение владельца об остановке источника. Взять handoffCode из envelope без публикации. `python3 "$KIT/scripts/clean.py" --root "$ROOT" start --role main --confirm-source-stopped "$HANDOFF"`. Ограничение readiness 120 секунд; не считать один timeout дефектом. Статус `APP_READY_MAIN` и health/ready 200. Проверить один экземпляр, его exact image, время старта, restart count, отсутствие неизвестных ошибок. При отказе — RETURN.md; не запускать старую БД параллельно.
6. Владелец выполняет ручную проверку: личный диалог, регистрация и четыре/пять фото, распределение и возвраты, профильный чат/личная работа, согласование/доработки, контакты/история, прямой REGION_KALUGA, внешние события. Это выполняется человеком по согласованию, не автоматически. Проверить поступление событий и движение очередей, 54 панели/закрепления по фактическому финальному снимку (число может измениться), исторические фото, новые V1 и старые LEGACY. Изменения после старта объяснять историей; FAILED/CANCELLED не оживлять.
7. Только после подтверждения завершения передачи: выполнить DAILY.md и RECOVERY.md. Сначала `operations.py --root "$ROOT" backup --manual`: единый закрытый архив, полное изолированное восстановление, ноль расхождений. Затем отдельное явное разрешение автозапуска и установка подготовленных таймеров. До этого app остаётся `restart=no`, host-ownership выключен. Получатель ежедневной копии использует согласованный sudo; отдельного веб-сервиса/HTTP-авторизации нет. Перед любой отменой/обратным переносом сначала отключить ownership и таймеры, затем штатная остановка.


Условия остановки: недоказанный source-off, неизвестный image/config/schema/restore outcome, повреждённые суммы, недостаток места/прав/TLS, занятая блокировка, другой экземпляр или отсутствие подтверждения финальной копии. Не использовать прежние 59149006/8dcfa330 с новой БД. Не запускать migrate deploy, migrate resolve, prune, общий retry, down -v.

Начало фактического переноса — только после возвращения специалиста, проверки принимающего сервера и отдельной команды владельца. Ожидание времени само по себе не является разрешением остановки источника.

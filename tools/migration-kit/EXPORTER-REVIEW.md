# Разбор экспортёра: редакция pr14-18-exporter-v2

Это исправление операционного резервирования для ревью. Runtime, SQL миграций,
образы, схема settings, ежедневный backup и правила переключения не изменены.
На рабочую установку эта редакция не загружалась и не применялась.

## Причина и границы доказательств

В прежней попытке наблюдался exit 139 контейнера экспортёра и `BACKUP_REFUSED:TypeError`.
Docker OOM и запись ядра с причиной не были обнаружены в сохранённых доказательствах.
139 совместим с SIGSEGV, но не устанавливает его первопричину. Прежний код передавал
EOF (`None`) в `json.loads`, не сохранял фазу и exit code и не читал stderr.
По имеющимся журналам неизвестно, отсутствовала первая строка с snapshot ID
или вторая строка с отпечатками. Новые операции на рабочем сервере не выполнялись.
Исходные приватные доказательства сохранены отдельно; в комплект они не включены.

Baseline: коммит `797c7978597e7f64d175db2eba1f255f960218a6`,
[Actions 37699430487](https://github.com/bassixs/Incident-Management/actions/runs/37699430487).
Неизменённый data-snapshot.cjs из e1c15c7 (SHA-256
`db3087ca263bd2f52e104ab1f924ec7309079c01cabbb10e3828610cc1a5cc23`)
на точном main image выполнил три экспорта: 13,44 / 13,53 / 14,21 с,
две JSON-строки, exit 0, без OOM, вывод 94 838 610 байт каждый.
Объём: 26 474 входящих, 31 099 исходящих, 700 обращений, 700 ответов,
6 000 записей истории; остальные контрольные записи — в baseline-summary.json.
Это сопоставимый синтетический объём, не копия рабочей БД или её распределения данных.

Baseline-среда: Linux/amd64, Docker 28.0.4, Compose 2.38.2, Python 3.12.3,
Node 22.23.3, Prisma 6.19.3, PostgreSQL 16-alpine. Сохраняются лимиты
экспортёра 0,5 CPU / 384 МиБ / pids 128, ожидания строк 30/90 с,
транзакция 180 с, statement_timeout 10 с, pg_dump 120 с.
Среда отличается от рабочего Docker 29.1.3 и его ядра/нагрузки. Успех baseline
не доказывает отсутствие инфраструктурного или зависящего от данных сбоя.
Первопричина серверного exit 139 остаётся НЕУСТАНОВЛЕННОЙ; ресурсы не увеличены.

## Минимальное исправление

- `backup-data.py` использует новый `snapshot_exporter.py` для двухстрочного протокола.
- Разные ошибки `EXPORTER_SNAPSHOT_EOF` и `EXPORTER_DATA_EOF`, отдельно timeout,
  malformed JSON, non-object, ненулевое завершение после двух строк.
- stderr непрерывно читается ограниченными блоками, чтобы не блокировать процесс.
  В журнал попадают только разрешённые технические сигнатуры/коды и счётчики.
  Произвольный текст, SQL, URL, секреты и тексты жителей не сохраняются.
- Контейнер создаётся с уникальными именем/меткой, подтверждается inspect, затем
  запускается attached. Проверяется код самого контейнера, а не только Docker CLI.
  `--log-driver none` применяется только к временному экспортёру.
- На выходе контейнер с подтверждённой идентичностью останавливается, ожидается
  завершение CLI/читателей, удаляется только этот временный контейнер.
  `exporter-result.json` сохраняет фазу, CLI/container exit, OOM и результат cleanup.
  Отказ cleanup не маскируется успехом: `EXPORTER_CLEANUP_UNCONFIRMED`.
- Неудачный каталог сохраняется. Он не получает `backup.json`/`checksums.json`/
  `restore-result.json`, даже если успел появиться частичный dump.
  Копия считается проверенной только после отдельного успешного verify.

## Проверки этой редакции

Точные результаты и версии — `review/unit.log`, `review/operational.log`,
`review/environment.txt`, `review/operational-result.json` и
`review/backup-restore-result.json`. Архив создаётся только при успешных проверках.
Восемь новых unit проверяют исходный TypeError, EOF/timeout обеих фаз, невалидный
JSON, корректный протокол, фильтрацию stderr и отказ при неизвестном create/чужом контейнере и завершение CLI при отказе inspect; запускаются также с Python -O.

Настоящий Docker: SIGSEGV до первой / после первой строки; большой stderr;
невалидная вторая строка; все строки и последующий exit 17; зависание в каждой
фазе. Внедрение только тестовое, код экспортёра/образ не исправляется под тест.
Каждая ошибка должна отклонить копию, освободить настоящий flock, убрать свой
контейнер и сохранить прежние app, FAILED, черновик, файлы и тома.
Затем выполняются полный pg_dump в том же экспортированном snapshot, архивы
вложений/конфигурации, изолированный pg_restore, точная сверка всех полей,
истории миграций, схемы и файлов. Восстановленное приложение не запускается.

## Перед будущим применением

Требуются ревью и отдельное разрешение загрузить новый комплект и подготовить
новые приватные пути/settings. Старый комплект и неудачную попытку сохранить.
Никакого автоматического продолжения установки по старому разрешению.
Выполнить новую свежую копию только в новом каталоге; дождаться verify до stop app.
Повторный отказ — сохранить `exporter-result.json`, не увеличивать лимиты,
не пропускать восстановление, не переходить к остановке или миграциям.

Docker daemon недоступен, потеря питания или SIGKILL самого управляющего Python
не дают гарантии cleanup; это явная граница, а не разрешение продолжить.
Освобождение flock проверяется для управляемых выходов и ошибок дочернего процесса;
файл backup.lock не удаляется. При `cleanup=unknown` сначала чтением установить
состояние указанного контейнера. Не удалять чужие контейнеры или доказательства.
Ротация приложения, его процессы и системные сервисы этим исправлением не меняются.

Первый исправленный прогон Actions 37700151155: полный capture/restore прошёл,
но семь аварийных сценариев не достигли внедрённых сбоев (MODULE_NOT_FOUND).
Причина стенда: bind mount включал родительский временный каталог mode 0700,
недоступный непривилегированному пользователю образа. Фикстуры перенесены в
отдельный синтетический каталог 0755, файлы 0644; ожидания не ослаблялись.
Неудачный прогон не считается проверкой аварийных сценариев, его журнал сохранён.

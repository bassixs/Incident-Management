# Ограничения и массовая запись

Уникальная блокировка берётся для каждого нового storageKey на транзакцию,
включая ключи внутри JSON. Бюджет общий PostgreSQL; 20000 не является порогом.
Сохраняется доказанный SQLSTATE 53200 для одной синтетической записи 20000 ключей
на конфигурации предыдущего стенда. Повышение лимитов/отключение guard не решение.

Полный перенос проверяется как pg_dump -Fc → новая пустая БД → pg_restore
--no-owner --no-privileges --exit-on-error [--single-transaction]. Все разделы
дампа сохраняются. Данные загружаются до создания post-data триггеров средствами
самого формата полного дампа; существующие guards не выключаются. Проверка
после переноса обязательна: все таблицы/строки, последовательности, миграции,
определения функций/триггеров, запрет ссылок на защищённые ключи по всем 7 таблицам.
Это не инструкция data-only импорта в уже мигрированную БД и не откат на старый дамп.

Проверенный синтетический объём: 35000 различных ключей, 5000 строк каждой из
семи защищённых таблиц; источник создаётся транзакциями по 250 новых ключей.
250 — размер проверенной партии, не универсальная гарантия при иной конкуренции.
Для массовой загрузки в существующую схему нужны отдельный тест объёма и короткие
READ COMMITTED транзакции с ограниченными партиями. Один огромный JSON с ключами
нельзя сделать безопасным простым разбиением INSERT на строки той же транзакции.

Ревизия кода: регистрация жителя ограничена 4 фото; ответ сотрудника хранит набор
одного ответа в одной транзакции, произвольный огромный набор не гарантируется.
enqueue пишет одно задание, inbox — одно событие; session/private-workspace —
один черновик/карточку. Общего штатного импорта миллионов storageKey в одну
транзакцию в src/scripts нет. Каталоги/роли и служебные пакетные уведомления
не вносят новые файловые ключи. Обнаруженные restore-check/handover-smoke и
локальная сохранённая редакция backup-active.py используют полный custom dump
в пустую БД; последняя копия кода резервирования прочитана локально, текущий сервер
не проверялся. Пользовательские SQL/сторонние импорты не проверены.

Резерв сохраняет отдельный цикл доставки, но разделяет guards, inbox, enqueue,
retention и значительную часть доставки с основной версией. Общие дефекты,
потерянный ACK MAX и неизвестное завершение удаления он не устраняет. FAILED
не оживляется, progress/fences/журнал не удаляются. Старый 8dcfa330 несовместим
с частично подтверждёнными отправками и новыми гарантиями после миграций.

Стенд — Linux/amd64, синтетическая БД, локальный HTTP MAX mock. Он не доказывает
скорость/доступность живого MAX, текущие серверные ресурсы/права и сохранность
данных при физическом отказе хранилища. Операционные проверки доверяют единому
оператору с backup.lock; root вне этого протокола может менять БД/файлы.

# Изолированная проверка готовых образов

Основная версия: `bbfa7b91c3a149d8951d36a28aefbe9b8e3ffa6c`.
Резерв: `3479a893e98addf51509cdb331ba371c2c5aaabc`.
Эта ветка содержит только стенд и отчёт. Исходники приложений берутся через
`git archive` из этих коммитов. Резерв не сливается в main.

Workflow разрешён только для push в `codex/container-reserve-validation`.
У него `contents: read`, нет deployment jobs, environments, SSH, MAX secrets
или публикации в registry. Сборочные стадии используют сеть для получения
базовых образов и зависимостей. После сборки PostgreSQL, приложения и mock
работают в Docker `--internal` сети без маршрута во внешний MAX.
Артефакты Actions хранятся 14 дней; это не бессрочный архив образов.

`run.py` запускается на выделенном одноразовом runner. Не запускать его на
рабочем сервере. Он создаёт исключительно синтетическую БД `reserve_lab`,
контейнеры/том `reserve-lab-*`, не использует production конфигурацию.
Не подставлять в ENV рабочие токены и адреса. Никаких дампов жителей в стенде нет.

Проверка кода: runtime `dist`, Prisma и lock сравниваются по SHA-256 с build
stage из точных исходников. Записываются tree SHA, image ID, размер и сведения
Docker; единственное ожидаемое различие компилированного runtime между
основной и резервной версиями — `max-message.service`.

Проверяется настоящий `node dist/index.js` под tini с обычным production mode,
но синтетическим токеном и `MAX_API_BASE_URL=http://mock:8080`.
DB helper только создаёт/читает тестовые записи и не запускает второго бота.
Между фазами сохраняются одна БД, журнал принятого mock и один том вложений.
Проверки готовности ограничены 90 секундами; stop grace — 75 секунд.

Моделирование:

- Частичный ACK создаёт настоящий SDK/HTTP запрос; 503 исчерпывает встроенные
  попытки. В тестовой БД `nextAttemptAt` явно переводится в прошлое, чтобы
  проверить продолжение без многочасового ожидания. Это **не** эксплуатационная
  инструкция ручного ускорения очереди.
- SENDING моделируется из реально сохранённого main префикса после штатной
  остановки владельца; только в синтетической БД ему задаётся истёкший lease.
  Это не испытание SIGKILL, потери питания или параллельных живых владельцев.
- Для окна «все ACK, нет итогового учёта» временный PostgreSQL trigger
  отклоняет завершение одного синтетического задания; затем trigger удаляется.
  В обеих версиях используется неизменённый код приложения.
- Потерянный ACK: mock принимает запрос и обрывает сокет до ответа. Повтор
  внешней отправки учитывается явно. exactly-once при этом не обещается.
- Для SIGTERM mock держит HTTP-ответ барьером. Проверяется, что процесс не
  завершается до освобождения ответа, затем штатно завершает учёт и выходит.
- При недопустимой конфигурации новый app должен завершиться; основной образ
  запускается с той же текущей БД, без восстановления старого дампа.

Отчёт запуска и образы публикуются как Actions artifacts. Не считать наличие
workflow или успешную сборку достаточным: нужны `report.result=passed` и
артефакт образов соответствующего успешного run. При падении стенда сохраняются
его синтетические журналы; причину нужно отличать от дефекта приложения.

## Будущая установка — только после отдельного разрешения

1. Сохранить артефакты образов вне временного Actions storage. Проверить SHA-256
   архива, загрузить в разрешённом окружении и сверить image ID/ревизии обоих
   образов с отчётом. Не пересобрать незаметно из плавающего `node:22-alpine`.
2. Отдельно, только после разрешения на доступ к рабочей установке, сверить
   её фактическую версию, платформу, текущую БД, mounts, конфигурацию запуска,
   health/ready, очереди и доступное место. Эти данные стенд не подтверждает.
3. Выбрать основной образ. Резерв допустим при установленном дефекте,
   воспроизводимо отсутствующем в резерве. Общие части формата, проверки
   актуальности и учёта у них совпадают; резерв не исправляет общий дефект.
4. Подготовить временную конфигурацию с заменой только app image, сохраняя
   runtime.env, токен, webhook, БД, вложения и ротацию. Проверить ветку возврата
   при отказе создания контейнера. Не использовать дефолтный Compose вместо
   конфигурации действующей установки и не запускать автоматические миграции.
5. Свежая копия с проверенным восстановлением → технический снимок очереди и
   данных → SIGTERM только app → подтверждение завершения обработчиков →
   финальный снимок текущей БД и вложений. Нештатное завершение и неизвестный
   владелец попытки требуют отдельной проверки конкретных заданий.
6. Проверить `deliveryProgress`, планы, MID и статусы, включая FAILED. При
   неизвестном/повреждённом progress или неоднозначном результате MAX не
   удалять прогресс, не выставлять SENT и не запускать массовый retry.
7. Запустить один app, ограниченно дождаться готовности. Превышение срока
   означает остановку дальнейших действий и диагностику, а не доказанный
   дефект. БД и прокси не перезапускать. Если новая версия подтверждённо
   неисправна, выбирать резерв только в пределах проверенного покрытия.
8. Сверить сохранность существующих ID, ответов, истории, назначений,
   черновиков, вложений, планов/MID, панелей и очередей. Учитывать новые
   обращения и штатные переходы. Подтверждение ACK/учёта проверять отдельно
   от health/ready. Снятые служебные FAILED не возобновлять.
9. После технического успеха обновить метаданные резервирования и проверить
   итоговую копию. Живую проверку распределения, согласования и ответа
   согласовать отдельно, не использовать реальные обращения как тесты.

Откат совместимого приложения использует текущую БД. Неизменённый 8dcfa330
не является безопасным резервом при незавершённом progress. Возврат между
проверенными основным и резервным образами требует той же штатной остановки,
снимка, проверки progress и единственности процесса. Старый дамп не восстанавливать.

Не проверяются этим стендом: живой MAX и его клиент, реальные права чатов,
сертификаты/прокси рабочей установки, восстановление её копии, рабочая
нагрузка, S3, поведение при потере питания и общие дефекты двух реализаций.
Историческое падение теста регистрации из предыдущего отчёта не исправляется
и не скрывается проверками образов.
